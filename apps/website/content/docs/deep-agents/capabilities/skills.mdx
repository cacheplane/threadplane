# Skills

A skill is a folder with a `SKILL.md` whose YAML frontmatter carries a `name` and a `description`, following the [agentskills.io](https://agentskills.io) specification. `SkillsMiddleware` scans a mount for those folders, and puts a short metadata index into the system prompt: a short entry per skill giving the name, the description, and the path to read for the full instructions. The body stays on the backend until a request matches. That two-stage load is what progressive disclosure means, and the running example is built to make both stages visible. Supported metadata can also contain optional license, compatibility, allowed-tools, and arbitrary metadata annotations; the React index displays these when present.

## What the demo does

The Run tab shows the prebuilt `<chat>` composition beside a panel titled Skill Index, which is empty until a run begins. The welcome suggestion asks whether a mid-size jet can operate out of KASE, and the panel fills in before the answer does: both skills are listed, `runway-analysis` and `weather-brief`, each with its description and a line reading "body not read", because both metadata entries are in the prompt and no read has yet been requested.

For the welcome scenario, the agent requests one skill. `runway-analysis` picks up an outline, the path of its `SKILL.md` appears under it, and the path of the margin table that the `SKILL.md` sends the agent to appears a step later. The Angular weather card has no matching requested path in the welcome scenario; this does not establish that its body was absent from all model context. It is in the index so that a different question, the conditions at KSFO for example, has somewhere else to route.

## How it is built

Both the Angular and React examples share the Python graph and `skills_readonly.py` enforcement module. The graph seeds the skill mount, builds the agent, and announces `skills_metadata` and `skills_load_errors`. Angular renders an index and requested paths; the React preview additionally distinguishes successfully inspected reads from requests, failures, and unavailable evidence. Open the Code tab to read the selected frontend alongside the complete shared backend.

### A skill on disk

The name, description, and instruction path form the index the model sees first, so the `description` is written as a matching rule rather than as a summary, and its `name` must match the directory the file sits in, which is what makes the folder the unit rather than the file. This is the whole of `skills/runway-analysis/SKILL.md`:

```markdown
---
name: runway-analysis
description: Decide whether a runway is long enough for a given aircraft at a given field elevation. Use when the user asks about runway suitability, takeoff or landing distance, or operating out of a high-elevation field.
license: MIT
---

# Runway Analysis

## When to use

The user is asking whether an aircraft can safely operate from a specific
runway, or is comparing two airports for a trip.

## Procedure

1. Get the field elevation and the longest runway length with
   `lookup_field_elevation` and `lookup_runway_length`.
2. Read `/skills/runway-analysis/reference/margins.md` for the required margin
   table. Do not work from memory — the table is the authority.
3. Compare the runway length against the required distance for the aircraft
   class at that elevation.
4. State the verdict in one sentence, then give the two numbers you compared.

## Reporting

Always name the margin you applied. A verdict without the margin is not
reviewable.
```

Step 2 is the second stage of disclosure: the margin table body is loaded only when requested. Scanning the metadata index itself still requires backend reads.

### Seeding the skill mount

`SkillsMiddleware` reads through the agent's backend, and which backend is a deployment decision. This demo runs on a shared public deployment, so a host-filesystem backend is out. The bundled folders are read once at import into a process-local `InMemoryStore`, which keeps the skill content in version control without giving the agent the host.

<ExampleCode file="graph.py" region="seed-store" title="graph.py — seeding the store" />

The seed uses a writable `StoreBackend` only at import. Runtime access goes through `ReadOnlySkillsBackend`, which denies writes, edits, and uploads synchronously and asynchronously. This keeps the shared `/skills/` mount stable across threads; the default `StateBackend` remains writable for thread-local notes. Merely asking the model not to write would not enforce this boundary.

<Callout type="warning" title="CompositeBackend strips the route prefix">
Seed the store at `/runway-analysis/SKILL.md`, not `/skills/runway-analysis/SKILL.md`. The composite removes the matched prefix before delegating and re-adds it to the paths it returns, so a store seeded with the prefix surfaces to the agent as `/skills/skills/runway-analysis/...` and the scan finds nothing.
</Callout>

### Mounting the skills beside the thread's own files

`skills=["/skills/"]` is what installs `SkillsMiddleware`, and it is installed with the agent's own backend, so where the skills live is decided by the `backend` argument rather than by the `skills` argument. `CompositeBackend` matches by path prefix, longest first: `/skills/` resolves to the seeded store, and everything else falls through to `StateBackend`, so notes the agent writes stay on the thread and never touch the skill mount.

### Telling the model the index is an index

The middleware appends its own guidance to the system message, including an instruction to read a skill's path with `read_file` before following it. The demo's own system prompt in `prompts/skills.md` says the same thing in the voice of the task, because a dispatcher that answers from recollection instead of from the margin table is the failure this example is about:

```markdown
You are a dispatcher. Your procedures are not in this prompt — they are skills on
your filesystem under `/skills/`, and each one is a folder with a `SKILL.md`.

You have been given the name, description, and instruction path of every skill up front. That index
is deliberately short. When a request matches a skill, read its `SKILL.md` with
`read_file` before you start, and follow the procedure it gives you. If the
`SKILL.md` points at another file, read that too — the numbers in a reference
file are the authority, and your recollection is not.
```

### Announcing Skills metadata

`SkillsMiddleware` annotates `skills_metadata` and `skills_load_errors` with `PrivateStateAttr`, excluding them from the declared input and output schemas. That does not hide the keys from every stream: the pinned Skills graph exposes `skills_metadata` in root `values` snapshots and saved checkpoints. The optional `skills_load_errors` key can appear when load errors are produced, and normal successful loads can omit it. `SkillsVisibilityMiddleware` always includes both keys in its named `custom` event, using an empty-list fallback for load errors and guarded because `get_stream_writer` raises outside a streaming context. This application event provides an explicit live signal; it is not proof that root values omit Skills metadata.

<ExampleCode file="graph.py" region="visibility-middleware" title="graph.py — republishing skills_metadata and skills_load_errors" />

This is an application-side visibility event rather than a framework feature. The Skills contracts establish this behavior for the pinned Skills graph; they make no inference about the separate Memory capability.

### Two sources for one index

A custom event is a live signal and is not replayed when a thread is reopened. Root values can also carry the index during a run, and the saved checkpoint carries it for hydration. The Angular panel prefers the named custom event and otherwise reads `agent.value()`. Its `checkpoint` label identifies that fallback, without proving the value came only from a reopened thread.

<ExampleCode file="skills.component.ts" region="skills-sources" title="skills.component.ts — the two readers" />

`agent.customEvents()` holds the custom events of the current run, cleared when a new run starts, so the live reader walks it newest first and takes the most recent payload under the event name the graph emits, while `agent.value()` is the agent state the adapter projects from the latest checkpoint, which may include the key from root values or a checkpoint.

### Requested paths and successfully inspected reads

The Angular `live` label means the visibility middleware announced the index; `checkpoint` means the value fallback supplied it. Its path projection reads `read_file` arguments from the runtime-neutral `agent.toolCalls()` Signal. These are requested paths: a failed read can still appear, and the panel does not inspect the result or establish successful body disclosure. The React preview separates requests from successfully inspected matching tool results and exposes failed or unavailable evidence explicitly.

<ExampleCode file="skills.component.ts" region="opened-paths" title="skills.component.ts — the opened paths" />

Each metadata entry carries its `SKILL.md` path. Angular derives the directory prefix and attributes requested paths under it to that skill. This prefix match associates the margin-table request with `runway-analysis`; it does not validate returned content. React validates canonical paths and matching successful tool results before marking content inspected.

### The panel

The sidebar renders the source label, then one card per skill: the name, the description the model was given, and either the requested paths or the words "body not read". An opened card carries `data-opened="true"`, which is what draws the outline.

<ExampleCode file="skills.component.ts" region="skills-panel" title="skills.component.ts — the skill index panel" />

In Angular, "body not read" means no matching read request was observed. It is not evidence that the body was absent from all model context. In React, read evidence is independent of index authority: archived evidence does not authorize another Send, and body content is shown as inspected only after a successful matching result.

## The skill that stays closed

A useful routing check is that an unrelated skill has no matching read request or successful result in the observed root run. If every skill's files are read on every request, the index is not routing anything and the descriptions are doing no work. That makes the descriptions, not the procedures, the part to iterate on: they guide selection alongside the name and instruction path in the index.

<Callout type="tip" title="Assert the closed skill as well as the open one">
The Angular end-to-end test checks both markers: `runway-analysis` has a matching requested path and `weather-brief` carries `data-opened="false"` when the run is over. The negative means no matching weather path request was observed; it does not prove body absence from model context or successful inspection of the selected skill.
</Callout>
