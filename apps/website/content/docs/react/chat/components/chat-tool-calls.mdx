# React chat tool calls preview

Show the lookups behind an answer without asking readers to infer them from prose. Tool calls have stable identities, so parallel requests to the same function can retain their own arguments and results.

The native React APIs on this page are experimental, private source-build packages. Run the repository example to use them; they are not an npm installation recipe.

## Observe the call the backend already made

`ToolActivity` displays a readable app-authored label and explicit phase with literal technical evidence under collapsed **Details**. `ToolActivityGroup` collects related calls into one borderless, initially collapsed activity row. Rich results and approval actions belong in their `children` slot, outside the disclosure. Neither component executes, approves, resumes, or persists work. Omitted phase is shown as unavailable; output text alone does not imply success.

`ToolObservation` remains the literal inspector for applications that need it. The example associates observations with the requesting assistant and confirms the saved root conversation before another submission. Tool completion and successful business or persistence outcomes remain separate.

```tsx
import { ToolObservation } from '@threadplane/react/chat';

export function RouteLookup({
  argumentsText,
  resultText,
}: {
  argumentsText: string;
  resultText?: string;
}) {
  return (
    <ToolObservation
      name="find_routes"
      argumentsText={argumentsText}
      resultText={resultText}
    />
  );
}
```

For readable activity:

```tsx
import { ToolActivityGroup } from '@threadplane/react/chat';

<ToolActivityGroup
  activities={[
    {
      id: 'call-1',
      name: 'find_routes',
      label: 'Finding flight routes',
      phase: 'running',
      argumentsText: '{"from_code":"LAX"}',
    },
  ]}
/>;
```

`MessageList` and `Chat` group built-in tool activity within each assistant message by default, including a single call. Pass `toolLabel(name, args)` for app-authored activity wording that names what each call did, such as **Read toSorted**, so repeated calls to one tool get their own labels. Without a label, a row reads the tool name as words, so `search_documents` becomes **Search documents**. Pass `groupRelatedTools={false}` to render separate activities. Inside a group, a failed row shows only its **Failed** status word; the failure message appears once, in the panel below the group. A custom `renderMessage` retains presentation ownership.

While a tool is running, its provided label has a subtle text shimmer; the fallback is **Running tools…**. Settled activity reads **Used 4 tools**, with the appropriate count, without an additional completion-count line. When some calls failed it reads **Used 4 tools · 1 failed**. This describes tool activity, not a confirmed business outcome. Opening the row reveals individual calls and their technical Details. Your expansion choice is retained as calls arrive or settle.

While the group runs, the elapsed time and a **Stop** button sit on its line; in `Chat`, **Stop** stops the run like the composer's Stop. Open the running group and the heading reads **Working · 1 of 3 done**: finished calls show a tick, the running call carries the shimmer and pending calls are dimmed. When the session declares a plan (`snapshot.plan`), its pending steps follow the calls, dimmed. The LangGraph session reads that plan from a `todos` list in graph state, the shape a deep-agents style to-do tool writes. The AG-UI session reads the same `todos` list from its shared state, so pass its `snapshot.plan` to `MessageList` or `ToolActivityGroup` the same way. `MessageList` takes `plan` and `onStop` and hands them to the current turn only; `ToolActivityGroup` takes the same two props. A browser client tool runs after the model message that requested it has finished. Pass `running` to `MessageList` while the session works, as `Chat` does, so such a call shows as running and its group gets the progress view; without it, or once the session settles, a call still marked running reads **Status unavailable**.

An explicit `ToolActivityGroup` `label` overrides the automatic summary wording. Omit it to follow the active call's human label.

Queued, paused, stopped and unavailable states keep static wording. **Tool activity paused** does not imply approval; the application owns approval-specific wording and controls. A failed call can coexist with running work, so the row retains a static failure cue while the active label shimmers. Reduced motion and forced colors use readable static text. A polite status region preserves meaningful state updates without announcing raw payloads or timer ticks.

Pending finalized arguments are distinct from streaming argument fragments. Unresolved calls from an aborted delivery show Stopped; paused deliveries remain paused without claiming approval, and interrupted deliveries show an unavailable status.

## Show confirmed outcomes and sources

Supply `ToolActivityInfo.outcome` to preview a validated result without opening technical Details:

```tsx
<ToolActivityGroup activities={[{
  id: 'reference-1', name: 'read_reference', label: 'Reading reference sources',
  phase: 'complete', resultText: '{"id":"angular-signals"}',
  outcome: {
    text: 'Checked the Angular signals reference.',
    sources: [{ title: 'Angular signals', url: 'https://angular.dev/guide/signals' }],
  },
}]} />
```

Only explicitly complete activities expose outcome previews. Related groups show deduplicated result summaries outside the collapsed technical subtree, with the first three visible and the rest in **More results**. An outcome may declare sources alone by leaving `text` empty.

Inside `MessageList` and `Chat`, declared sources join the message's one **Sources** panel, which is closed until opened and lists each source once beside the message's own citations. A source whose URL the message already cites is not added again. `ToolActivity` and `ToolActivityGroup` used on their own have no message panel, so they keep the sources as links, with the first three visible and the rest in **More sources**. A collapsed group lists every source below it. Open the group and each source moves under the call that produced it, while the result text stays below the group. An application that composes its own message can send them to its own panel instead: pass `sources="panel"` to the activity and render `Citations` with `citationsWithToolSources`.

```tsx
<ToolActivityGroup activities={activities} sources="panel" />
<Citations
  citations={citationsWithToolSources(message.citations ?? [], activities)}
  collapsible
/>
```

A source may also carry a `snippet` and an `iconUrl`, which the panel shows on its card. The library never fetches an icon itself. Sources accept absolute HTTP(S) URLs without credentials; unsupported links are omitted. Mixed groups retain meaningful activity and failure or pause cues in their status sentence. Raw payload streaming stays out of that region.

Pass a stable `toolOutcome(activity)` callback to `MessageList` or `Chat` to supply the same metadata for default rows. Validate your tool's result schema and author the summary in your application; the library does not infer business success from arbitrary payloads. Custom message renderers retain ownership. Keep approval actions in the persistent rich-content slot, and route explicit retry through the session owner. A failed write with uncertain acknowledgment needs reconciliation before another attempt.

## Declare a failed result

A tool can finish delivery and still report that it failed.
`lookup_flight` returns `{"error": "Flight UA999 not found in dataset"}` for an unknown flight, and the call still completes.
By default the row stays complete, because the library does not guess what a payload means.

Decode the tool's declared schema in `toolOutcome` and return `status: 'failed'` only for its declared error shape.

```tsx
import type { ToolActivityInfo, ToolActivityOutcome } from '@threadplane/react/chat';

function toolOutcome(activity: ToolActivityInfo): ToolActivityOutcome | undefined {
  if (activity.name !== 'lookup_flight' || !activity.resultText) return undefined;
  try {
    const result = JSON.parse(activity.resultText);
    if (typeof result?.error === 'string') {
      return { status: 'failed', text: result.error };
    }
  } catch {
    return undefined;
  }
  return undefined;
}
```

A failed call shows as failed, its `text` becomes the error explanation, and a settled group counts it.
For example, a group of three calls with one failure reads **Used 3 tools · 1 failed**.
Values such as `false`, `0`, `""`, `[]` and `null` are literal results, not failures.
Returning `undefined` keeps the call as it was.
Only a call that completed can be marked failed, so a running or stopped call is never rewritten.

This changes what is shown, not what the model receives.
The model still sees the original tool result.
If a tool should tell the model that it failed, set the error flag your protocol provides on the tool message.
The cost is that you maintain a decoder per tool, and a decoder that drifts from the tool's real schema shows the wrong state.
`ToolActivity` and `ToolActivityGroup` apply the same resolution to a failed outcome you pass them directly.
`resolveToolOutcome(activity, outcome)` is exported if you render activities with your own markup and want the same resolution.

## Add content to one call

Pass `renderToolResult` to `MessageList` or `Chat` to add content to a single call's row, such as a retry button or a rich result.

```tsx
import { useCallback } from 'react';
import type { AgentSession } from '@threadplane/core';
import { Chat, type ToolActivityInfo } from '@threadplane/react/chat';

export function FlightChat({
  session,
  retryLookup,
}: {
  readonly session: AgentSession;
  readonly retryLookup: (callId: string) => void;
}) {
  const renderToolResult = useCallback(
    (activity: ToolActivityInfo) =>
      activity.name === 'lookup_flight' && activity.phase === 'error' ? (
        <button type="button" onClick={() => retryLookup(activity.id)}>
          Retry flight lookup
        </button>
      ) : null,
    [retryLookup]
  );
  return (
    <Chat
      session={session}
      toolOutcome={toolOutcome}
      renderToolResult={renderToolResult}
    />
  );
}
```

`toolOutcome` is the module-level decoder from the previous section, so both callbacks stay stable across renders.

The callback receives the resolved activity, after `toolOutcome` ran, so a declared failure arrives with `phase: 'error'`.
Its content renders outside **Details** and is shown below a collapsed group.
Below a collapsed group, name the call in the control, such as **Retry UA999 lookup**, because a bare **Retry** does not say which call it acts on.
The slot only displays what you return.
It does not run, approve or retry anything, so the handler you pass owns that work.
Return `null` for calls that need nothing extra.

When you render `ToolActivityGroup` yourself, pass the same kind of callback as its `renderResult` prop.
It receives each resolved activity, and a `null` or `undefined` return adds nothing for that call.
For a single `ToolActivity`, pass the content as its `children` instead.

## Replace one call's row

Some calls deserve more than an activity row.
A weather lookup reads better as a small forecast card than as "Used 1 tool".
Pass `renderToolCall` to `MessageList` or `Chat` to draw a call yourself.

```tsx
import { useCallback } from 'react';
import type { AgentSession } from '@threadplane/core';
import { Chat, type ChatProps } from '@threadplane/react/chat';

export function FlightChat({ session }: { readonly session: AgentSession }) {
  const renderToolCall = useCallback<NonNullable<ChatProps['renderToolCall']>>(
    (call, activity) =>
      call.name === 'get_weather' && call.status === 'complete' ? (
        <section aria-label={activity.label ?? 'Weather'}>
          <pre>{JSON.stringify(call.result, null, 2)}</pre>
        </section>
      ) : undefined,
    []
  );
  return <Chat session={session} renderToolCall={renderToolCall} />;
}
```

The callback receives the call as the session observed it, with its arguments and result as values, and the same resolved activity `renderToolResult` gets.
What you return decides what happens to that call:

- `undefined` keeps the built-in row.
- `null` shows nothing for the call.
- Anything else replaces the row.

**Return `undefined`, not `null`, for the calls you do not handle.**
A `null` hides the call, and a hidden call is hard to notice until someone asks where the tool activity went.

A replaced call leaves its group.
The calls before it and after it are summarized separately, so the transcript keeps the order the calls were made in.
The cost is that you own everything about that call's presentation.
`renderToolResult`, outcome previews, **Details** and the retry control do not apply to it, so show the running and failed states yourself.

In the example, a weather call that is still running returns `undefined` and keeps the built-in row until its result arrives.
I think that is the easiest way to start, because the built-in row already handles running, stopped and failed.

## Recover from a partial failure

One read fails, another succeeds, and the user wants the missing piece without losing the rest.
You declare what each tool's result means, and the library does the rest of the display work.
The example tools are `read_reference`, which declares a recoverable `{"error": string, "recoverable": true}` result, and `save_note`, which returns `{"saved": true, "id": string}` only after an approved save.

```typescript
import { toolOutcomes } from '@threadplane/react/chat';

const toolOutcome = toolOutcomes({
  read_reference: ({ args, result }) => {
    const { id } = args as { id: string };
    const read = result as { error?: string; recoverable?: boolean; title?: string; url?: string; summary?: string };
    if (read.recoverable === true && typeof read.error === 'string') {
      return { status: 'failed', text: read.error, retry: { label: `Retry ${id} read` } };
    }
    return typeof read.summary === 'string' && typeof read.title === 'string' && typeof read.url === 'string'
      ? { text: read.summary, sources: [{ title: read.title, url: read.url }] }
      : undefined;
  },
  save_note: ({ result }) => {
    const save = result as { saved?: boolean; id?: string } | null;
    return save?.saved === true && typeof save.id === 'string'
      ? { status: 'receipt', text: `Note ${save.id} in Comparisons.` }
      : undefined;
  },
});
```

`toolOutcomes` takes one decoder per tool name and returns a `toolOutcome` callback.
It parses the arguments and the result once, and runs a decoder only for a completed call of its own tool.
A running, stopped or already failed call never reaches a decoder, and neither does a tool you did not list.
**Decode each tool's declared schema, and nothing else.**
`false`, `0`, `""`, `[]` and `null` arrive unchanged and mean nothing until your decoder says so.

Each call keeps its own outcome.
The successful read keeps its summary and source link beside the failed one, and the group reads **Used 2 tools · 1 failed**.
Sources appear in the message's **Sources** panel, and the literal JSON stays inside **Details**.

### Declare a retry

`retry: { label }` on a failed outcome offers a retry for that one call.
The failure appears in one panel below the group, with the retry after the explanation.

```tsx
<Chat session={session} toolOutcome={toolOutcome} onToolRetry={retryRead} />
```

`onToolRetry` receives the failed activity, and without it no retry control renders.

The library decides only *when* the control is worth showing.
It hides it while anything is running, and removes it once a later call repeats the same tool and arguments.
Your handler decides what a retry does.
Send it as a new request in the same conversation, and have your backend run only the failed read again as a new call.
Name the call in the label, such as **Retry toSorted read**, because the group may be collapsed above it.
While that repeat call is still running, the failure panel leads with **Retrying toSorted read**, built from your label, with the same shimmer as a running step. A label that does not start with "Retry" gives a plain **Retrying**. `ToolActivity` and `ToolActivityGroup` take that line as a `retrying` prop when you render them yourself.
`ToolActivityGroup` takes the same handler as `onRetry`, plus a `context` prop with every observed call so it can apply the same rule across messages.

I would not declare a retry for a write.
A write that failed with an uncertain acknowledgment needs reconciliation before another attempt.

### Show a receipt

`status: 'receipt'` records a write your application confirmed.
It renders as a success panel with the lead **Saved.**, or your own `lead`, followed by your `text`.
Return it only from the decoded save result, never from the approval.
An approval that has not produced `saved: true` shows no receipt, and neither does a denied one.

### The status panel

Failures and receipts use `StatusPanel`, which you can also use for your own approvals and notices.

```tsx
import { StatusPanel } from '@threadplane/react/chat';

<StatusPanel tone="warning" lead="Waiting for your approval." actions={<button type="button" onClick={save}>Save note</button>}>
  <p>Save the comparison note to your workspace?</p>
</StatusPanel>
```

`tone` is `danger`, `warning`, `success` or `neutral`.
The lead sentence carries the meaning and the colour only reinforces it.
Set `role="alert"` for failures only.
The panel displays what you give it and runs nothing.

The cost of all this is one decoder per tool, kept in step with that tool's real schema.
A decoder that drifts shows the wrong state.

## Confirm the saved conversation

After a successful stream, the application reads saved history once. Follow-up messages remain blocked until the exact observed messages, tool identities, arguments and results agree with a terminal root checkpoint for the current conversation. Every completed tool call must have one later matching result. Text-only answers are also supported.

The owner retains an observed conflict even if a later response restores the earlier content. Changed call arguments, replaced results, failed messages, interrupts, subgraphs and uncertain work require a new local conversation. Partial argument chunks stay private in the runtime and do not count as malformed finalized calls.

## Stop and recover locally

While work is active, Send and New conversation stay blocked and Stop remains available. **Stop** immediately detaches the owner; late stream or saved-history responses cannot restore its commands. **New conversation** releases the old local owner and clears the old draft. New text typed during cleanup is preserved. The next server thread is created only when another message is sent.

## Build from source

From a Threadplane checkout with dependencies installed:

```sh
npx nx build cockpit-chat-tool-calls-react
npx nx e2e cockpit-chat-tool-calls-react
```

The isolated build uses installed private candidate packages. Browser tests use the real SDK and a persistent compiled Python graph with deterministic providers and real saved checkpoints. The local worker and verification routes are excluded from public output. Background title generation updates metadata without entering the answer stream. Docs, Code and Run select this same React implementation; Angular remains the default.
