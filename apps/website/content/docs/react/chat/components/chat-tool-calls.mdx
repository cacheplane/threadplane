# React chat tool calls preview

Show the lookups behind an answer without asking readers to infer them from prose. Tool calls have stable identities, so parallel requests to the same function can retain their own arguments and results.

The native React APIs on this page are experimental, private source-build packages. Run the repository example to use them; they are not an npm installation recipe.

## Observe the call the backend already made

`ToolActivity` displays a readable app-authored label and explicit phase with literal technical evidence under collapsed **Details**. `ToolActivityGroup` collects related calls into one borderless, initially collapsed activity row. Rich results and approval actions belong in their `children` slot, outside the disclosure. Neither component executes, approves, resumes, or persists work. Omitted phase is shown as unavailable; output text alone does not imply success.

`ToolObservation` remains the literal inspector for applications that need it. The example associates observations with the requesting assistant and confirms the saved root conversation before another submission. Tool completion and successful business or persistence outcomes remain separate.

```tsx
import { ToolObservation } from '@threadplane/react/chat';

export function RouteLookup({
  argumentsText,
  resultText,
}: {
  argumentsText: string;
  resultText?: string;
}) {
  return (
    <ToolObservation
      name="find_routes"
      argumentsText={argumentsText}
      resultText={resultText}
    />
  );
}
```

For readable activity:

```tsx
import { ToolActivityGroup } from '@threadplane/react/chat';

<ToolActivityGroup
  activities={[
    {
      id: 'call-1',
      name: 'find_routes',
      label: 'Finding flight routes',
      phase: 'running',
      argumentsText: '{"from_code":"LAX"}',
    },
  ]}
/>;
```

`MessageList` and `Chat` group built-in tool activity within each assistant message by default, including a single call. Pass `toolLabel` for app-authored activity wording, or `groupRelatedTools={false}` to render separate activities. A custom `renderMessage` retains presentation ownership.

While a tool is running, its provided label has a subtle text shimmer; the fallback is **Running tools…**. Settled activity reads **Used 4 tools**, with the appropriate count, without an additional completion-count line. When some calls failed it reads **Used 4 tools · 1 failed**. This describes tool activity, not a confirmed business outcome. Opening the row reveals individual calls and their technical Details. Your expansion choice is retained as calls arrive or settle.

An explicit `ToolActivityGroup` `label` overrides the automatic summary wording. Omit it to follow the active call's human label.

Queued, paused, stopped and unavailable states keep static wording. **Tool activity paused** does not imply approval; the application owns approval-specific wording and controls. A failed call can coexist with running work, so the row retains a static failure cue while the active label shimmers. Reduced motion and forced colors use readable static text. A polite status region preserves meaningful state updates without announcing raw payloads or timer ticks.

Pending finalized arguments are distinct from streaming argument fragments. Unresolved calls from an aborted delivery show Stopped; paused deliveries remain paused without claiming approval, and interrupted deliveries show an unavailable status.

## Show confirmed outcomes and sources

Supply `ToolActivityInfo.outcome` to preview a validated result without opening technical Details:

```tsx
<ToolActivityGroup activities={[{
  id: 'reference-1', name: 'read_reference', label: 'Reading reference sources',
  phase: 'complete', resultText: '{"id":"angular-signals"}',
  outcome: {
    text: 'Checked the Angular signals reference.',
    sources: [{ title: 'Angular signals', url: 'https://angular.dev/guide/signals' }],
  },
}]} />
```

Only explicitly complete activities expose outcome previews. Related groups show deduplicated result summaries and sources outside the collapsed technical subtree, with the first three visible and the rest in **More results** or **More sources**. Links accept absolute HTTP(S) URLs without credentials; unsupported links are omitted. Mixed groups retain meaningful activity and failure or pause cues in their status sentence. Raw payload streaming stays out of that region.

Pass a stable `toolOutcome(activity)` callback to `MessageList` or `Chat` to supply the same metadata for default rows. Validate your tool's result schema and author the summary in your application; the library does not infer business success from arbitrary payloads. Custom message renderers retain ownership. Keep approval actions in the persistent rich-content slot, and route explicit retry through the session owner. A failed write with uncertain acknowledgment needs reconciliation before another attempt.

## Declare a failed result

A tool can finish delivery and still report that it failed.
`lookup_flight` returns `{"error": "Flight UA999 not found in dataset"}` for an unknown flight, and the call still completes.
By default the row stays complete, because the library does not guess what a payload means.

Decode the tool's declared schema in `toolOutcome` and return `status: 'failed'` only for its declared error shape.

```tsx
import type { ToolActivityInfo, ToolActivityOutcome } from '@threadplane/react/chat';

function toolOutcome(activity: ToolActivityInfo): ToolActivityOutcome | undefined {
  if (activity.name !== 'lookup_flight' || !activity.resultText) return undefined;
  try {
    const result = JSON.parse(activity.resultText);
    if (typeof result?.error === 'string') {
      return { status: 'failed', text: result.error };
    }
  } catch {
    return undefined;
  }
  return undefined;
}
```

A failed call shows as failed, its `text` becomes the error explanation, and the settled group reads **Used 3 tools · 1 failed**.
Values such as `false`, `0`, `""`, `[]` and `null` are literal results, not failures.
Returning `undefined` keeps the call as it was.
Only a call that completed can be marked failed, so a running or stopped call is never rewritten.

This changes what is shown, not what the model receives.
The model still sees the original tool result.
If a tool should tell the model that it failed, set the error flag your protocol provides on the tool message.
The cost is that you maintain a decoder per tool, and a decoder that drifts from the tool's real schema shows the wrong state.
`resolveToolOutcome(activity, outcome)` is exported if you render activities yourself and want the same resolution.

## Add content to one call

Pass `renderToolResult` to `MessageList` or `Chat` to add content to a single call's row, such as a retry button or a rich result.

```tsx
<Chat
  agent={agent}
  toolOutcome={toolOutcome}
  renderToolResult={(activity) =>
    activity.name === 'lookup_flight' && activity.phase === 'error' ? (
      <button onClick={() => retryLookup(activity.id)}>Try another flight</button>
    ) : null
  }
/>
```

The callback receives the resolved activity, after `toolOutcome` ran, so a declared failure arrives with `phase: 'error'`.
Its content renders outside **Details** and is shown below a collapsed group.
The slot only displays what you return.
It does not run, approve or retry anything, so the handler you pass owns that work.
Return `null` for calls that need nothing extra.

## Confirm the saved conversation

After a successful stream, the application reads saved history once. Follow-up messages remain blocked until the exact observed messages, tool identities, arguments and results agree with a terminal root checkpoint for the current conversation. Every completed tool call must have one later matching result. Text-only answers are also supported.

The owner retains an observed conflict even if a later response restores the earlier content. Changed call arguments, replaced results, failed messages, interrupts, subgraphs and uncertain work require a new local conversation. Partial argument chunks stay private in the runtime and do not count as malformed finalized calls.

## Stop and recover locally

While work is active, Send and New conversation stay blocked and Stop remains available. **Stop** immediately detaches the owner; late stream or saved-history responses cannot restore its commands. **New conversation** releases the old local owner and clears the old draft. New text typed during cleanup is preserved. The next server thread is created only when another message is sent.

## Build from source

From a Threadplane checkout with dependencies installed:

```sh
npx nx build cockpit-chat-tool-calls-react
npx nx e2e cockpit-chat-tool-calls-react
```

The isolated build uses installed private candidate packages. Browser tests use the real SDK and a persistent compiled Python graph with deterministic providers and real saved checkpoints. The local worker and verification routes are excluded from public output. Background title generation updates metadata without entering the answer stream. Docs, Code and Run select this same React implementation; Angular remains the default.
