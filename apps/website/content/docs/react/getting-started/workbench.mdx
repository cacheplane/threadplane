# Messages, responses, and turns

Follow one recorded conversation. No backend or model key needed.

## Follow one recorded turn

The lesson opens with the recorded user message already visible. Choose **Next** to follow the exchange, and read the explanation beside the conversation. Use **Back** to revisit an earlier step or **Restart lesson** to begin again.

Continue from your [React Quickstart](/docs/react/getting-started/quickstart) with a lesson that runs entirely from captured observations.

The trip notebook uses a real SDK/session capture with deterministic **fixture responses**. It is not a live model conversation. Both framework guides share this React-owned recording; framework choice changes the source links and optional live application, not the captured frontend. Replay sends no requests.

1. **User message** shows one conversation entry from the traveler. Its role identifies the speaker; its content holds what they asked.
2. **Turn in progress** shows the application working on that message. Work has started, but a successful outcome has not been observed at this point.
3. **Assistant response** shows the beginning of the answer. Choose **Show next response update** to see more text in the same assistant message. The message count stays the same.
4. **Turn outcome** shows the completed answer alongside the observed outcome. The full text and the operation's settled state can arrive at different times.

Choose **Inspect data** when you want to compare the captured messages and state. The detailed inspector and timeline remain available there. Hiding data or moving backward does not submit the prompt again.

## Three concepts to keep separate

- A **message** is an entry in the conversation. Its role identifies the speaker, and its content holds what they said. This lesson follows one user message and one assistant message.
- A **response** is the agent's answer. In this example, one assistant message carries the response. Streaming extends that message as more text arrives.
- A **turn** is the work started by an action such as sending a message. It has progress and an outcome. A successful turn, a stopped turn, and a failed turn can all leave messages in the conversation.

A conversation can contain many turns. An update to a message is not automatically a new message or a new turn.

## Check what changed

At the end of this recording, there are two conversation messages: the user's input and the assistant's answer. The assistant message grew through several observations during one turn.

The full answer was visible before the application became idle. Even a reported success and a settled busy state are separate observations in this capture. Seeing text, seeing a request return, and seeing the completed turn are different things. Read the operation's outcome alongside its progress.

These `busy` and `outcome` fields belong to the recorded example application. They are not a promise that every Threadplane framework exposes the same public API. This recording demonstrates a successful response; it does not demonstrate stopping, connection failure, itinerary edits, or client tools.

## Connect the lesson to your React app

Choose **View example source**. In `app.tsx`, `useAgent(application)` observes the application snapshot. The view passes `snapshot.rows` to `MessageList`, passes `snapshot.busy` to `ChatInput`, and handles submission and stop through the application. Rendering another snapshot does not send another message.

Your Quickstart used the complete `Chat` composition with an app-owned fake `AgentSession`. Its fields describe this example's application owner; they are not additional requirements for your fake session.

## Explore the details when you need them

Open **Inspect data** to reveal **Messages**, **Events**, **State**, **Requests**, and detailed playback. **Events** lists captured observations, and selecting one moves the whole workbench. Before the initial application snapshot, state is unavailable rather than an empty object. Playback runs at a reading pace; capture offsets are not a model performance benchmark.

In recorded mode, **Requests** shows captured application HTTP requests to the fixture server. A status appears only after response headers were observed. HTTP success does not prove that the turn succeeded. Provider/model requests are not captured.

In live mode, **Requests** shows **Application calls**: the submitted input and whether its invocation is pending, settled, or rejected. Settled means the call returned; read the application's state for the outcome. Live HTTP and provider requests are not captured. Observations stay in this page's memory, with limits reported when older observations or long fields are omitted.
