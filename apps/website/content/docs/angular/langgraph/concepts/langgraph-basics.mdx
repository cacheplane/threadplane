# LangGraph Basics

LangGraph is a framework for building stateful AI agents as directed graphs. For an Angular developer building AI-powered applications, the sections below cover how LangGraph agents work and how `injectAgent()` connects your frontend to your agent backend.

<Callout type="info" title="Why graphs?">
Graphs give you explicit control over agent behavior. Instead of a black-box prompt-and-pray approach, you define exactly how your agent reasons, when it calls tools, and where it pauses for human input. Every step is visible, testable, and debuggable.
</Callout>

## The Core Concepts

A LangGraph agent has three building blocks:

### Nodes — Functions That Do Work

A node is a Python function that receives the current state, does something, and returns updated state. Every node has the same signature:

```python
def my_node(state: State, config: RunnableConfig) -> dict:
    # Read from state
    messages = state["messages"]

    # Do work (call LLM, query DB, invoke tool)
    response = llm.invoke(messages)

    # Return state updates (merged into existing state)
    return {"messages": [response]}
```

<Callout type="tip" title="Node return values">
Nodes do not replace state — they return updates that get **merged** into the existing state. For lists like messages, LangGraph uses reducers (like `operator.add`) to accumulate entries instead of overwriting.
</Callout>

### Edges — Connections Between Nodes

Edges define the execution flow. There are two types:

**Normal edges** — always route to the next node:
```python
builder.add_edge(START, "call_model")   # Start → call_model
builder.add_edge("call_model", END)     # call_model → End
```

**Conditional edges** — route based on state:
```python
def should_continue(state: State) -> str:
    last_msg = state["messages"][-1]
    if last_msg.tool_calls:
        return "tools"      # Agent wants to use a tool
    return END              # Agent is done, return response

builder.add_conditional_edges("call_model", should_continue)
```

### State — The Shared Memory

All nodes read from and write to a shared state object. You define its shape as a Python `TypedDict`:

```python
from typing_extensions import TypedDict, Annotated
from operator import add

class State(TypedDict):
    messages: Annotated[list, add]   # Accumulates messages
    plan: list[str]                   # Agent's current plan
    results: dict                     # Tool results
```

This state is what `injectAgent()` exposes to your Angular app through Signals: the `messages` key becomes `agent.messages()`, and the other keys arrive as `agent.state()`.

## Building Your First Agent

The simplest possible agent — a chat model that takes messages and responds:

<Tabs>
<Tab label="agent.py">

```python
from langgraph.graph import END, START, MessagesState, StateGraph
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-5-mini")

def call_model(state: MessagesState) -> dict:
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

# Build the graph: START → call_model → END
builder = StateGraph(MessagesState)
builder.add_node("call_model", call_model)
builder.add_edge(START, "call_model")
builder.add_edge("call_model", END)

graph = builder.compile()
```

</Tab>
<Tab label="langgraph.json">

```json
{
  "dependencies": ["."],

    "chat": "./src/graph.py:graph"
  },
  "env": ".env",
  "python_version": "3.12"
}
```

</Tab>
<Tab label="Angular component">

```typescript
// app.config.ts
import { provideAgent } from '@threadplane/angular';
import { createSession } from '@threadplane/langgraph';

provideAgent({
  createSession: (context) =>
    createSession({
      apiUrl: 'http://localhost:2024',
      assistantId: 'chat',
      threadId: context.threadId,
      onThreadId: context.onThreadId,
    }),
});

// component.ts: that is the whole Angular side
protected readonly chat = injectAgent();

// chat.messages() updates as the agent streams its response
// chat.status() reports idle, running, or error
```

## Agent Patterns

LangGraph shines in the patterns you can build. Each one maps to specific `injectAgent()` signals.

### Pattern 1: ReAct Agent (Tool Calling)

The agent reasons, decides to call a tool, observes the result, and loops until it has an answer.

```python
from langgraph.prebuilt import ToolNode

@tool
def search_docs(query: str) -> str:
    """Search the knowledge base."""
    return vector_store.similarity_search(query)

tools = [search_docs]

def call_model(state: State) -> dict:
    response = llm.bind_tools(tools).invoke(state["messages"])
    return {"messages": [response]}

def should_continue(state: State) -> str:
    if state["messages"][-1].tool_calls:
        return "tools"
    return END

builder = StateGraph(State)
builder.add_node("model", call_model)
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "model")
builder.add_conditional_edges("model", should_continue)
builder.add_edge("tools", "model")  # Loop back after tool execution

graph = builder.compile()
```

**Angular connection:** Track tool execution in real-time:
```typescript
const agent = injectAgent();

// Watch tools execute. A call is `pending` until its result arrives.
const activeTools = computed(() =>
  agent.toolCalls().filter((tool) => tool.status === 'pending' || tool.status === 'running')
);
const completedTools = computed(() =>
  agent.toolCalls().filter((tool) => tool.status === 'complete')
);
```

### Pattern 2: Human-in-the-Loop (Approval)

The agent proposes an action and pauses. Your Angular UI shows an approval dialog. The user decides, and the agent resumes.

```python
from langgraph.types import interrupt

def propose_action(state: State) -> dict:
    action = llm.invoke(state["messages"])
    # Pause execution — Angular will show approval UI
    approval = interrupt({
        "action": "send_email",
        "to": "client@example.com",
        "body": action.content,
    })
    return {
        "pending_action": action.content,
        "approval": approval,
    }

def execute_action(state: State) -> dict:
    # Only runs after human approves
    if not state.get("approval", {}).get("approved"):
        return {"messages": [{"role": "assistant", "content": "Email cancelled."}]}
    send_email(state["pending_action"])
    return {"messages": [{"role": "assistant", "content": "Email sent."}]}
```

**Angular connection:** The interrupt surfaces automatically:
```typescript
const agent = injectAgent<LangGraphSession>();

// Show approval UI when agent pauses
const pendingAction = computed(() => agent.interrupts()[0]);

// User clicks approve: answer the interrupt by id to resume the agent.
// `value` is what the graph's interrupt() call returns.
approve() {
  const interrupt = agent.interrupts()[0];
  if (!interrupt) return;
  void agent.resume([
    { interruptId: interrupt.id, status: 'resolved', value: { approved: true } },
  ]);
}
```

### Pattern 3: Multi-Agent Orchestration

A supervisor agent delegates work to specialist sub-agents. Each sub-agent is its own graph.

```python
def supervisor(state: State) -> dict:
    routing = llm.invoke([
        {"role": "system", "content": "Route to: researcher, analyst, or writer"},
        *state["messages"]
    ])
    return {"next_agent": routing.tool_calls[0].args["agent"]}

builder = StateGraph(State)
builder.add_node("supervisor", supervisor)
builder.add_node("researcher", researcher_subgraph)
builder.add_node("analyst", analyst_subgraph)
builder.add_conditional_edges("supervisor", lambda s: s["next_agent"])
```

**Angular connection:** Track delegated work through `subagents()`. Subgraph nodes like the ones above need no configuration. When delegation is exposed as tool calls, the session relates each child to the call that started it; the default tool name is `task`, and `subagentToolNames` sets others. Configure once in `app.config.ts`:
```typescript
provideAgent({
  createSession: (context) =>
    createSession({
      apiUrl: '...',
      assistantId: 'orchestrator',
      subagentToolNames: ['task'],
      threadId: context.threadId,
      onThreadId: context.onThreadId,
    }),
});
```

Then consume from any component:
```typescript
const orchestrator = injectAgent<LangGraphSession>();

// A plain list, one entry for each child graph, in start order
const workers = computed(() => orchestrator.subagents());
const workerCount = computed(() => workers().length);
```

### Pattern 4: Persistent Conversations

A conversation survives page refreshes, browser restarts, and server deployments when the backend retains its checkpoints in durable storage and the client restores the same thread ID. The ID identifies the conversation; it does not make an in-memory checkpointer durable. When embedding a graph in your own process, keep every invocation inside the saver's connection scope. The example assumes your application supplies `DATABASE_URL`, `builder`, and `user_message`. LangGraph API deployments use the server's checkpointer; see [Persistence](/docs/angular/langgraph/guides/persistence#choosing-a-checkpointer).

```python
from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string(DATABASE_URL) as checkpointer:
    checkpointer.setup()  # Initialize the checkpoint schema before first use.
    graph = builder.compile(checkpointer=checkpointer)

    # Each thread_id is a persistent conversation.
    result = graph.invoke(
        {"messages": [user_message]},
        config={"configurable": {"thread_id": "user_123_session"}},
    )
```

**Angular connection:** Thread persistence is configured in the provider:
```typescript
// app.config.ts
provideAgent({
  // The thread to start on: a string, null, or a signal the agent follows
  threadId: localStorage.getItem('threadId'),
  // Called with the id of a thread a session created
  onThreadId: (id) => localStorage.setItem('threadId', id),
  createSession: (context) =>
    createSession({
      apiUrl: '...',
      assistantId: 'chat',
      threadId: context.threadId,
      onThreadId: context.onThreadId,
    }),
});

// component.ts
const chat = injectAgent();

// User returns tomorrow: same thread, saved history restored.
// The agent reads the selected thread's history when it starts;
// chat.isThreadLoading() is true meanwhile.
```

## How `injectAgent()` Bridges the Gap

This is the path one message takes between your Angular app and the graph, and the Signal each LangGraph concept maps to.

<Tabs>
<Tab label="The data flow">

<Steps>
<Step title="Your Angular App">
Calls `agent.submit(text)` to send user input
</Step>
<Step title="The LangGraph session">
Creates a thread on the first submit when it has none, then passes the input to its transport
</Step>
<Step title="FetchStreamTransport">
Sends HTTP POST to LangGraph Platform, opens SSE connection
</Step>
<Step title="LangGraph Platform">
Executes graph nodes, calls tools, streams SSE events back
</Step>
<Step title="FetchStreamTransport">
Parses SSE chunks into typed stream events
</Step>
<Step title="The session and `injectAgent()`">
The session projects the events into an immutable snapshot, and the agent exposes each snapshot field as an Angular Signal
</Step>
<Step title="Your Angular App">
Templates that read those Signals re-render, including under OnPush change detection
</Step>
</Steps>

</Tab>
<Tab label="Signal mapping">

```typescript
// Every LangGraph concept maps to a Signal. The surface splits into three
// groups: the runtime-neutral contract every session implements, what the
// injected agent adds, and the fields only the LangGraph session publishes.

// ── On every agent (the core session contract) ──────────────────────────────
agent.messages()       // readonly Message[]: runtime-neutral transcript
agent.status()         // 'idle' | 'running' | 'error'
agent.error()          // AgentError | undefined: classified failure
agent.toolCalls()      // readonly ToolCall[]: finalized calls and their results
agent.state()          // root graph state, without `messages`

// Optional on the contract (a signal of undefined when not published):
agent.interrupts()     // readonly AgentInterrupt[]: what a paused run waits on
agent.subagents()      // readonly AgentSubagent[]: child agents, in start order
agent.plan()           // readonly AgentPlanStep[]: from a `todos` list in state
agent.checkpoints()    // readonly AgentCheckpoint[]: saved history, oldest
                       // first. LangGraph needs `historyState: true`.

// ── Added by the injected agent ─────────────────────────────────────────────
agent.threadId()       // string | null: the thread the agent is on
agent.isThreadLoading() // boolean: the selected thread's history is being read
agent.customEvents()   // the current run's custom events, oldest first

// ── LangGraph-specific fields (`injectAgent<LangGraphSession>()`) ───────────
// These exist because the session is a LangGraphSession. They are NOT part of
// the runtime-neutral contract.
agent.history()        // checkpoint metadata of the loaded page, newest first
agent.subgraphs()      // child graphs by namespace, with messages and state
agent.branchTree()     // loaded checkpoints arranged by parent (`historyState`)
agent.branch()         // the branch selected with setBranch()
agent.toolProgress()   // progress reported through the `tools` stream mode
agent.queue()          // queued runs waiting for the active one
agent.langGraphMessages() // messages as LangGraph sent them (`rawMessages`)
agent.retainedRun()    // the run reconnect() can join after a lost stream
```

`subagents()` is a plain read-only list from the runtime-neutral contract, not a
map. The LangGraph session derives it from `subgraphs()`, one entry for each
child graph and in the same order; filter it by `status` to find the children
that are still `running`.

</Tab>
</Tabs>

<Callout type="tip" title="Zero configuration streaming">
You do not configure SSE or parse events. The session's transport does that. You call `submit()` and read Signals. A stream that drops is not hidden: `error()` reports it with a `recovery` hint, and the application decides whether to check the run's status.
</Callout>

## Graph API vs Functional API

LangGraph offers two ways to define agents:

**Graph API** (recommended for most cases):
```python
builder = StateGraph(State)
builder.add_node("model", call_model)
builder.add_edge(START, "model")
graph = builder.compile()
```

**Functional API** (for simpler workflows):
```python
from langgraph.func import entrypoint

@entrypoint()
async def agent(messages):
    response = await call_model(messages)
    return response
```

Both APIs produce a graph that LangGraph Platform serves, so the Angular side does not change. Choose the Graph API when you need conditional routing, subgraphs, or interrupts. Choose the Functional API for simple, linear workflows.
