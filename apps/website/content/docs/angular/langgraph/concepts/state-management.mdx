# State Management

The trip planner needs a draft in the composer, an itinerary returned by the agent, and a selected day in the UI. Those values have different owners and lifetimes. Model them separately so a local tab change does not become a backend request, and a page reload does not erase the saved itinerary.

<Callout type="info" title="Mental model">
LangGraph owns saved agent state. Your Angular application owns local interface state and decides which input to submit. `injectAgent()` exposes the observed backend state as signals and provides methods for sending new messages, state patches, and decisions.
</Callout>

## Choose an owner for each value

| Value | Owner | When it travels |
|---|---|---|
| Unsent message | Angular component or application store | On Send |
| Itinerary facts and message history | Backend thread | In submitted input and streamed/saved state |
| Selected itinerary day | Application UI | Only if the agent needs that selection |
| Generated layout | Application renderer | When the agent supplies a supported specification |

The useful question is “who is allowed to change this value?” A signal makes an update observable; it does not decide whether the value is durable or whether editing it should run the agent.

<ConversationArchitecture />

## State Lives on the Server

In a traditional Angular app, state lives in a client-side store or a signals-based service. In a LangGraph app, **the agent's state lives on the server**, in LangGraph Platform's checkpoint store. Your Angular app reads a projection of that state through signals while retaining its own local drafts, selections, and presentation settings.

This separation is intentional. Agent state can span multiple LLM calls, tool executions, and human-in-the-loop interrupts. A durable checkpoint store can preserve that state across browser refreshes, reconnections, and server restarts. Configure storage and retention for your deployment; an in-memory development store cannot make that guarantee. Your Angular app submits intentional changes and reads the resulting signals. It still owns the draft and decides when local edits should become backend input.

<Steps>
<Step title="User submits input">
Your Angular component calls `agent.submit(text)`. The component may hold the draft, but the accepted message enters the agent conversation.
</Step>
<Step title="The session sends the request">
The `@threadplane/langgraph` session behind the agent hands the input to its transport. By default that is `FetchStreamTransport`, which opens an HTTP POST and SSE connection to LangGraph Platform.
</Step>
<Step title="LangGraph Platform executes the graph">
The agent runs its nodes (calling the LLM, invoking tools, checking conditions) and streams SSE events back with incremental state updates.
</Step>
<Step title="The session projects the stream">
The transport parses incoming SSE chunks into stream events. The session folds each event into its messages, tool calls, and graph state, and publishes the result as one immutable snapshot.
</Step>
<Step title="`injectAgent()` exposes Signals">
The agent exposes every snapshot field as its own read-only Signal. A field's Signal notifies only when that field's value changes, so a token that extends a message does not notify a view that reads only `state()`.

Notifications are not throttled by default. To pace them, pass `throttle` to `createSession`: the least time in milliseconds between two notifications while a run streams. The last change is always delivered, and a change that ends the run is delivered at once.
</Step>
<Step title="Templates re-render">
Components using `OnPush` re-render only when signal values change. No manual `detectChanges()`, no zone triggers, no subscriptions to manage.
</Step>
</Steps>

## Python State Design

On the Python side, your agent's state is a `TypedDict`. The fields you define here are what the state type you declare with `stateType`, and carry from `provideAgent(ref, …)` to `injectAgent(ref)` with `createAgentRef`, describes in TypeScript. Getting the Python state design right is the most important architectural decision in an agent: everything downstream inherits its shape, so it is worth slowing down for.

### The TypedDict Pattern

The examples here define LangGraph state with a `TypedDict`. Fields can be plain values or annotated with reducers that control how updates are merged.

<Tabs>
<Tab label="Basic state">

```python
from typing_extensions import TypedDict

class ChatState(TypedDict):
    messages: list        # Will be replaced on each update
    session_id: str       # Single value, replaced on update
    turn_count: int       # Single value, replaced on update
```

</Tab>
<Tab label="With reducers">

```python
from typing_extensions import TypedDict, Annotated
from operator import add

class AgentState(TypedDict):
    # Annotated[list, add] means: append new items, do not replace
    messages: Annotated[list, add]
    tool_results: Annotated[list, add]

    # Plain fields: each update replaces the previous value
    status: str
    current_plan: list[str]
```

</Tab>
<Tab label="MessagesState (recommended)">

```python
from langgraph.graph import MessagesState
from typing import Annotated
from operator import add

# MessagesState is a built-in TypedDict that pre-wires
# messages: Annotated[list[AnyMessage], add_messages]
# add_messages handles deduplication, type coercion, and ordering

class ProjectState(MessagesState):
    # Extend with your own fields
    files: Annotated[list[str], add]    # Accumulates file paths
    analysis: dict                       # Latest analysis result
    progress: int                        # 0–100 progress value
```

</Tab>
</Tabs>

### Reducers: How State Merges

When a node returns `{"messages": [new_msg]}`, LangGraph does not replace the messages list. It **calls the reducer** to merge the update. This is what `Annotated[list, add]` means: use Python's `operator.add` to concatenate lists.

```python
from typing_extensions import TypedDict, Annotated
from operator import add

class ResearchState(TypedDict):
    # Each node can append to these — they accumulate across the run
    messages: Annotated[list, add]
    sources: Annotated[list[str], add]
    findings: Annotated[list[str], add]

    # These are replaced (last write wins)
    query: str
    model: str
    confidence: float

def researcher_node(state: ResearchState) -> dict:
    result = llm.invoke(state["messages"])
    new_sources = extract_sources(result.content)

    # Returns partial state — only fields being updated
    # LangGraph merges this into the existing state
    return {
        "messages": [result],           # Appended via reducer
        "sources": new_sources,          # Appended via reducer
        "confidence": 0.87,              # Replaced
    }
```

<Callout type="tip" title="Partial returns are the norm">
Nodes return only the fields they change. LangGraph merges partial updates into the full state object. This is why you can have 10 nodes each updating different fields without conflicts.
</Callout>

## TypeScript Interface Mapping

The TypeScript interface you declare as the session's `stateType` is your contract with the Python state. Every Python state field except `messages` maps to a TypeScript property; the transcript arrives separately as `agent.messages()`. The types do not need to match exactly. They need to be compatible with the JSON that LangGraph streams back.

<Tabs>
<Tab label="Python state">

```python
from typing_extensions import TypedDict, Annotated
from operator import add
from langgraph.graph import MessagesState

class ProjectState(MessagesState):
    # From MessagesState: messages: Annotated[list[AnyMessage], add_messages]
    files: Annotated[list[str], add]
    analysis: dict[str, any] | None
    progress: int
    plan: Annotated[list[str], add]
    error: str | None
```

</Tab>
<Tab label="TypeScript interface">

```typescript
import { createAgentRef, injectAgent } from '@threadplane/angular';
import type { ToolContract } from '@threadplane/core';
import type { LangGraphSession } from '@threadplane/langgraph';

// `messages` is not listed: it arrives as agent.messages(), not in state().
// A run reports partial state before every node has written, so fields the
// graph fills in later are optional.
export interface ProjectState {
  // Maps from Python fields (reducers are transparent: you see the final list)
  files?: string[];
  analysis?: { score: number; issues: string[]; summary: string } | null;
  progress?: number;
  plan?: string[];
  error?: string | null;
}

export type ProjectSession = LangGraphSession<
  Record<string, ToolContract>,
  ProjectState
>;

export const PROJECT_AGENT = createAgentRef<ProjectSession>('project_agent');

// Configure in app.config.ts. `type` comes from @threadplane/core:
// provideAgent(PROJECT_AGENT, {
//   createSession: async (context) =>
//     createSession({
//       ...context,
//       apiUrl: '...',
//       assistantId: 'project_agent',
//       stateType: type<ProjectState>(),
//     }),
// });

const agent = injectAgent(PROJECT_AGENT);
```

</Tab>
<Tab label="Type reference">

| Python type | TypeScript type |
|-------------|-----------------|
| `str` | `string` |
| `int` / `float` | `number` |
| `bool` | `boolean` |
| `list[str]` | `string[]` |
| `dict[str, any]` | `Record<string, unknown>` |
| `TypedDict` | `interface` or `type` |
| `str \| None` | `string \| null` |
| `list[AnyMessage]` | Not in `state()`. Read `agent.messages()`, a `readonly Message[]` |
| `Annotated[list, add]` | Same as the list type — reducer is invisible |

</Tab>
</Tabs>

Once you declare the type, every field is accessible through `agent.state()`. The value is read-only, and `undefined` until the backend reports a state:

```typescript
// Typed state object
const state = agent.state();         // ProjectState (read-only) | undefined

// Computed values from nested fields
const score = computed(() => agent.state()?.analysis?.score ?? 0);
const fileCount = computed(() => agent.state()?.files?.length ?? 0);
const isDone = computed(() => agent.state()?.progress === 100);

// Runtime-neutral message projection for UI
const messages = agent.messages();   // readonly Message[]
```

`type<T>()` declares the type and checks nothing at runtime. Pass a Standard Schema, such as a Zod object, as `stateType` to also check each state the backend reports. A state the schema rejects does not fail the run: `state()` stays at the last one that passed, and the LangGraph field `stateIssues()` lists what was wrong.

## State Updates During Streaming

The agent does not wait until it is finished to send state updates. It streams partial state updates as each node completes. Your Angular signals update incrementally throughout the run.

### How Partial Updates Arrive

The session's own transport always requests the stream modes it needs to fill the agent's Signals: `values`, `messages-tuple`, `updates`, `custom`, and `checkpoints`. The first four feed state snapshots, streamed message tokens, per-node update events, and custom events; the session uses `checkpoints` to follow the position each step saved. A per-run `streamMode` *adds* modes; the ones the session needs are always kept, so you cannot narrow the set and lose a Signal. For example, the `tools` mode fills the LangGraph field `toolProgress()`. Per-run LangGraph settings are grouped under `run`:

```typescript
const agent = injectAgent(PROJECT_AGENT);

void agent.submit('Update the project plan.', {
  run: { streamMode: ['tools'] },
});
```

### Signals Update Mid-Stream

Because every state update is a new signal value, your templates reflect the agent's progress in real time — without polling, without timers, without manual state management.

```typescript
@Component({
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    @if (agent.state(); as state) {
      <!-- Updates as each file is processed -->
      <p>Files processed: {{ state.files?.length ?? 0 }}</p>

      <!-- Progress bar updates as agent emits progress updates -->
      <progress [value]="state.progress ?? 0" max="100"></progress>

      <!-- Plan items appear as the agent builds the plan -->
      @for (step of state.plan ?? []; track step) {
        <li>{{ step }}</li>
      }
    }

    <!-- Messages stream token by token -->
    @for (msg of agent.messages(); track msg.id) {
      <app-message [message]="msg" />
    }
  `
})
export class ProjectComponent {
  protected readonly agent = injectAgent(PROJECT_AGENT);
}
```

### Immutability and OnPush

Every change produces a new frozen value, and a part that did not change keeps its reference. Angular's `OnPush` change detection follows the Signals a template reads, so the component re-renders when one of them changes. You never need to clone objects or call `markForCheck()` manually.

```typescript
// Safe: computed() re-evaluates when agent.state() changes
const hasErrors = computed(() =>
  (agent.state()?.analysis?.issues ?? []).length > 0
);

// Safe: every message has a stable id, so track by it for stable DOM
@for (msg of agent.messages(); track msg.id) {
  <app-message [message]="msg" />
}

// Safe: optional chaining handles a state, or a field, not yet reported
const score = computed(() => agent.state()?.analysis?.score ?? 0);
```

<Callout type="tip" title="No manual subscriptions">
Every Signal has a value before the first stream update: `messages()` starts as an empty list and `status()` as `'idle'`. `state()` is `undefined` until the backend reports a state, and individual state fields may be missing or `null` until the agent populates them.
</Callout>

## Thread State vs Application State

There are two kinds of state in a LangGraph Angular app, and keeping them separate makes your code far easier to reason about.

**Thread state** is owned by LangGraph Platform. You read it through `injectAgent()` signals. You never write to it directly. You send new input with `submit()`, which can carry a partial `state` for the backend to merge: `submit({ message, state })`.

**Application state** is owned by your Angular component or service. It is UI-only: sidebar visibility, active tab, selected message, form input values. It has nothing to do with the agent.

```typescript
// Defined once (e.g. in agent.ts):
// export const CHAT_AGENT = createAgentRef<ChatSession>('chat');

@Component({
  changeDetection: ChangeDetectionStrategy.OnPush,
})
export class ChatComponent {
  // --- Thread state (from injectAgent(), read-only) ---
  protected readonly agent = injectAgent(CHAT_AGENT);

  // Convenience values from thread state
  readonly messages = this.agent.messages;           // Signal<readonly Message[]>
  readonly running = computed(() => this.agent.status() === 'running');
  readonly interrupts = this.agent.interrupts;       // Signal<readonly LangGraphInterrupt[]>

  // --- Application state (your Angular signals) ---
  readonly sidebarOpen = signal(true);
  readonly activeTab = signal<'chat' | 'history' | 'settings'>('chat');
  readonly inputText = signal('');
  readonly selectedMessageId = signal<string | null>(null);

  // --- Actions ---
  send() {
    const text = this.inputText();
    if (!text.trim()) return;
    void this.agent.submit(text);
    this.inputText.set('');                          // UI state: clear the input
  }

  approve() {
    const interrupt = this.agent.interrupts()[0];
    if (!interrupt) return;
    void this.agent.resume([
      { interruptId: interrupt.id, status: 'resolved', value: { approved: true } },
    ]);
  }
}
```

<Callout type="warning" title="Do not mirror thread state into Angular signals">
A common mistake is copying `agent.messages()` into a local signal to "control" it. This creates stale state bugs and defeats the purpose of the reactive signal model. Read thread state directly from `agent.*` signals and derive what you need with `computed()`.
</Callout>

## The Checkpoint Model

LangGraph Platform persists state at every node boundary using a checkpoint store. Each checkpoint is an immutable snapshot of the full state at a point in time.

<CheckpointHistory />

### What This Means for Your Angular App

**Resumable threads**: If the user refreshes the page or closes the browser, the thread is still there. Pass the same `threadId` to `provideAgent()` and the agent reads that thread's saved history when it starts; `isThreadLoading()` is true meanwhile.

**Time travel**: You can fork a thread at any checkpoint and replay it with different input. This powers the time-travel debugging guides.

**Interrupt persistence**: When the agent raises an `Interrupt`, the checkpoint captures everything. The agent can be resumed hours or days later.

```typescript
import { inject } from '@angular/core';
import { ActivatedRoute, Router } from '@angular/router';
import { injectAgent, provideAgent } from '@threadplane/angular';
import { createSession } from '@threadplane/langgraph';

// chat-page.component.ts: `providers` of the routed component, so the
// injected ActivatedRoute is that route.
// (CHAT_AGENT = createAgentRef<ChatSession>('chat'), declared in agent.ts)
// The factory form runs inside an injection context, so it can inject router
// services. A plain object literal cannot.
provideAgent(CHAT_AGENT, () => {
  const route = inject(ActivatedRoute);
  const router = inject(Router);
  return {
    // Same threadId = restored conversation history
    threadId: route.snapshot.paramMap.get('threadId'),

    // Called with the id of a thread a session created for a new conversation
    onThreadId: (id: string) => void router.navigate(['/chat', id]),

    createSession: async (context) =>
      createSession({
        ...context,
        apiUrl: '...',
        assistantId: 'chat',
        // Keep each checkpoint's state for a time-travel UI
        historyState: true,
      }),
  };
});

// component.ts
const agent = injectAgent(CHAT_AGENT);

// Read checkpoint history for time-travel UI (with `historyState: true`)
const checkpoints = agent.checkpoints();   // saved states, oldest first
const history = agent.history();           // checkpoint metadata, newest first
const branch = agent.branch();             // the branch setBranch() selected
const branchTree = agent.branchTree();     // checkpoints arranged by parent
```

For full checkpoint and time-travel patterns, see the [Persistence guide](/docs/angular/langgraph/guides/persistence) and [Time Travel guide](/docs/angular/langgraph/guides/time-travel).

## Custom State Fields

`messages` is just one field. Real agents carry rich state: structured plans, tool results, progress indicators, metadata, and more. Every custom field you define in Python can be declared in your TypeScript state type and read from `agent.state()`.

<Tabs>
<Tab label="Python state">

```python
from typing_extensions import TypedDict, Annotated
from operator import add
from langgraph.graph import MessagesState
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-5-mini")

class ResearchState(MessagesState):
    # Accumulating lists — each node can append
    plan: Annotated[list[str], add]
    sources: Annotated[list[str], add]
    findings: Annotated[list[str], add]

    # Scalar progress
    progress: int          # 0–100

    # Structured results
    report: dict | None    # Final report when complete

    # Agent metadata
    query: str
    model_used: str

def planner_node(state: ResearchState) -> dict:
    steps = llm.invoke([
        {"role": "system", "content": "Break this query into research steps."},
        *state["messages"]
    ])
    plan_items = steps.content.split("\n")
    return {
        "plan": plan_items,       # Appended via reducer
        "progress": 10,
        "model_used": "gpt-5-mini",
    }

def researcher_node(state: ResearchState) -> dict:
    # A node returns ONE dict, so accumulate across the loop and return once
    findings = []
    for step in state["plan"]:
        findings.append(search(step))
    return {
        "findings": findings,  # Appended via reducer
        "progress": state["progress"] + 80,
    }
```

</Tab>

### Derived State with computed()

You rarely need to consume `agent.state()` raw in your template. Use `computed()` to derive clean, focused values:

```typescript
protected readonly agent = injectAgent(RESEARCH_AGENT);

// Derived signals: recalculate only when their dependencies change
readonly progress = computed(() => this.agent.state()?.progress ?? 0);
readonly isPlanning = computed(
  () => !this.agent.state()?.plan?.length && this.agent.status() === 'running'
);
readonly sourceCount = computed(() => this.agent.state()?.sources?.length ?? 0);
readonly hasReport = computed(() => this.agent.state()?.report != null);
readonly reportTitle = computed(() => this.agent.state()?.report?.title ?? '');
```
