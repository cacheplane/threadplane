# Deployment

A deployed agent is two independent artifacts: a graph running on LangGraph Platform, and an Angular application that connects to it. The running example is the smallest pair that works (one graph, one provider, one component), and the rest of this guide covers the operational parts the example cannot show: authentication, CORS, error handling, continuous delivery, and monitoring.

<Callout type="tip" title="Prerequisites">
Make sure you have completed the Installation guide first.
</Callout>

## What the demo does

The Run tab shows the prebuilt `<chat>` composition and nothing else. Send a message and the answer streams back from the graph, exactly as it would from a local server.

That is the point of this example. Nothing about the deployment is visible in the component: the graph name lives in `langgraph.json`, and the API URL and assistant ID live in the provider. Change those values and the same component talks to a local server, a staging deployment, or production.

## How it is built

Three files carry the deployable unit: the graph packaged for the platform, the provider that holds the connection, and a component that knows neither. Open the Code tab to read them in place.

### The graph you deploy

The backend is a single node. Its state extends `MessagesState`, which gives the LangGraph SDK a message list it already understands, the model is constructed with `streaming=True`, and the node prepends a system prompt read from the capability's prompt file before it awaits the model. After the reply it also records the IDs of the completed turn in three optional state fields.

<ExampleCode file="graph.py" />

The last line matters more than the graph does: `graph = build_deployment_runtime_graph()` is the module-level symbol `langgraph.json` points at, and `compile()` is called with no checkpointer because the platform provides persistence itself.

### Pointing the app at a deployment

`provideAgent()`, from `@threadplane/angular`, registers the agent once for the whole application. It knows nothing about LangGraph: its `createSession` function builds the session, with `createSession()` from `@threadplane/langgraph`, and that call is where every deployment-specific value belongs. The agent calls the function at the start and again for each thread switch. The example resolves its connection details at runtime from the host that serves the demo, which is why its factory reads them rather than hard-coding them.

<ExampleCode file="app.config.ts" />

Your own application does not need the factory. Pass the config object with the values:

```typescript
import { provideAgent } from '@threadplane/angular';
import { createSession } from '@threadplane/langgraph';

provideAgent({
  createSession: (context) =>
    createSession({
      apiUrl: 'https://your-deployment.langgraph.app',
      assistantId: 'deployment-runtime',
      threadId: context.threadId,
      onThreadId: context.onThreadId,
    }),
}),
```

`clientOptions` is the third value the example forwards. It tunes the LangGraph SDK client behind the default transport, and it accepts two keys: `defaultHeaders`, sent with every request so a per-user session token can reach your deployment's custom auth handler, and `maxRetries` for how many times the SDK retries a failed request with exponential backoff before the error reaches your UI. A session defaults `maxRetries` to 0, because a retried run-creation request could start a second run. There is no `apiKey` option, on purpose: a deployment credential passed from Angular would ship in the bundle. The example's `onOperationFailure` line is a hook for the host that serves the demo; your application can leave it out.

<Callout type="warning" title="assistantId must match the graph key">
The `assistantId` you pass to `createSession()` must exactly match a key in the `graphs` map of `langgraph.json`. A mismatch is not a build error: the application starts normally and the first message fails against the deployment.
</Callout>

### The component

`injectAgent()` returns the agent registered above and hands it to `<chat>`. The class is one field and one handler: the "New conversation" button calls `agent.switchThread(null)`, which moves to a new, empty thread.

<ExampleCode file="deployment-runtime.component.ts" />

No URL, no assistant ID, no environment check: the same component ships to every environment.

## Deploying the graph

Your agent needs a `langgraph.json` manifest at the project root. This is the example's, and it is the whole file:

```json
{
  "graphs": {
    "deployment-runtime": "./src/graph.py:graph"
  },
  "dependencies": ["."],
  "python_version": "3.12",
  "env": ".env"
}
```

The `graphs` key maps an assistant ID to a module path and the graph variable inside it. `dependencies` names the packages to install into the image, and `env` points at a file with secrets like `OPENAI_API_KEY` that are injected at runtime.

<Callout type="tip" title="Run it locally first">
`langgraph dev` serves the same manifest on your machine and speaks the same API a deployment does, so you can point a development build at it before you deploy anything. It refuses a graph that compiles its own checkpointer; a deployment ignores one. Compile with no checkpointer, as the example does.
</Callout>

### Push and deploy

```bash
# Initialize and push to GitHub
git init && git add . && git commit -m "initial agent"
gh repo create my-agent --public --source=. --push

# Deploy via CLI (alternative to the LangSmith UI)
pip install langgraph-cli
langgraph deploy --project my-agent
```

The CLI watches your repository and builds a container image on LangGraph Cloud. First deployments take roughly 10-15 minutes. Subsequent pushes to the default branch trigger automatic redeployments.

## Environment configuration

Angular uses file-based environment replacement at build time rather than `process.env`. Create separate environment files for development and production.

<Tabs>
<Tab label="Development">

```typescript
export const environment = {
  production: false,
  langgraphUrl: 'http://localhost:2024',
};
```

</Tab>
<Tab label="Production">

```typescript
export const environment = {
  production: true,
  langgraphUrl: '/api/langgraph',
};
```

</Tab>
</Tabs>

Wire the environment into the session factory:

```typescript
import type { ApplicationConfig } from '@angular/core';
import { provideAgent } from '@threadplane/angular';
import { createSession } from '@threadplane/langgraph';
import { environment } from '../environments/environment';

export const appConfig: ApplicationConfig = {
  providers: [
    provideAgent({
      createSession: (context) =>
        createSession({
          apiUrl: environment.langgraphUrl,
          assistantId: 'deployment-runtime',
          threadId: context.threadId,
          onThreadId: context.onThreadId,
        }),
    }),
  ],
};
```

Angular CLI replaces `environment.ts` with `environment.prod.ts` during `ng build --configuration production` automatically via the `fileReplacements` array in `angular.json`.

## Authentication

### Keep LangGraph credentials server-side

Do not ship LangSmith or LangGraph API keys in an Angular bundle. The session gives you no field to put one in: `LangGraphClientOptions` has no `apiKey` member, and the SDK client is constructed with an explicit null key so it never picks one up from the environment either. The default `FetchStreamTransport` uses the LangGraph SDK client directly, not Angular `HttpClient`, so Angular HTTP interceptors do not attach headers to the agent's requests. To send a header the deployment should see, such as a per-user session token for LangGraph custom auth, use `clientOptions.defaultHeaders`.

For production, put a same-origin backend route, edge function, or API gateway in front of LangGraph. The browser calls your relative URL, and that server-side layer adds the deployment credentials. Set `apiUrl` to that relative path, as the production environment file above does.

For me, the same-origin proxy is worth the extra hop. You give up the simplicity of pointing Angular straight at the deployment, but your keys never leave the server, and HTTP-only cookies just work.

<Callout type="warning" title="Never expose API keys">
Environment files that are bundled into Angular are public. Store LangGraph deployment credentials in your server-side proxy, hosting provider secret store, or CI/CD environment, not in `environment.prod.ts`.
</Callout>

### User-level authentication

If your app has its own user authentication, authenticate the same-origin proxy with cookies or your usual app session. The proxy can forward user identity to LangGraph through safe, server-controlled metadata or headers.

If your deployment runs a custom `authenticate` handler instead, the browser can send the user's own short-lived token directly. That token is per user and expires, which is what makes it safe to hold in the page where a deployment key is not:

```typescript
provideAgent(() => {
  // The config factory runs once, in an injection context.
  const auth = inject(AuthService);
  return {
    createSession: (context) =>
      createSession({
        apiUrl: environment.langgraphUrl,
        assistantId: 'deployment-runtime',
        threadId: context.threadId,
        onThreadId: context.onThreadId,
        clientOptions: {
          defaultHeaders: { Authorization: `Bearer ${auth.accessToken()}` },
        },
      }),
  };
}),
```

`AuthService` stands for your own service. The handler on the LangGraph side validates the token and scopes threads and runs to that user. A session reads its client options once, when it is created, so a refreshed token reaches the deployment with the next session the agent creates, which is the next thread switch.

### Client option precedence

`provideAgentClientOptions(options)`, from `@threadplane/angular`, sets app-wide client options once at the application root. Nothing applies them for you: each agent passes them to its session factory as `context.clientOptions`, and the factory decides what the session gets. The usual choice is `clientOptions: mine ?? context.clientOptions`, where `mine` is whatever that agent sets for itself. Fields are not merged. A per-agent `{ maxRetries: 0 }` chosen that way replaces the entire app-wide object, including any `defaultHeaders`. Include the headers explicitly in that object if the agent still needs them. `context.clientOptions` is typed as `object`, because the Angular package knows no backend, so cast it to `LangGraphClientOptions` when you forward it. See [`LangGraphClientOptions`](/docs/api/langgraph/LangGraphClientOptions) for the supported fields.

## CORS configuration

When your Angular frontend and LangGraph backend are on different origins, you must configure CORS on the LangGraph side.

In `langgraph.json`, add an `http` section:

```json
{
  "dependencies": ["."],
  "graphs": {
    "deployment-runtime": "./src/graph.py:graph"
  },
  "http": {
    "cors": {
      "allow_origins": ["https://your-angular-app.com"],
      "allow_methods": ["GET", "POST", "PUT", "DELETE", "OPTIONS"],
      "allow_headers": ["Content-Type", "Authorization"],
      "allow_credentials": true
    }
  }
}
```

<Callout type="tip" title="Local development">
During local development with `langgraph dev`, CORS is permissive by default. You only need explicit CORS configuration for production deployments.
</Callout>

## Error handling

The demo leans on `<chat>`, which renders failures for you. A hand-built UI reads the same two signals the composition does: `status()` flips to `'error'`, and `error()` holds an `AgentError`, a plain object with a classified `kind`, a `message`, a `retryable` flag, and an optional HTTP `status`. `recovery` and `detail` name the one action the session can prove is safe. It is not an `Error` instance; what the failure was classified from is described separately in `errorDiagnostic()`.

```typescript
import { ChangeDetectionStrategy, Component, computed } from '@angular/core';
import { injectAgent } from '@threadplane/angular';

@Component({
  selector: 'app-chat',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    @if (hasError()) {
      <div class="error-banner">
        <p>{{ errorMessage() }}</p>
        @if (agent.error()?.detail; as detail) {
          <p>{{ detail }}</p>
        }
        @if (canCheck()) {
          <button (click)="checkStatus()">Check status</button>
        } @else if (canRetry()) {
          <button (click)="retry()">Try again</button>
        }
      </div>
    }
  `,
})
export class ChatComponent {
  protected readonly agent = injectAgent();

  protected readonly hasError = computed(() => this.agent.status() === 'error');
  protected readonly canCheck = computed(
    () => this.agent.error()?.recovery === 'check' && this.agent.checkStatus !== undefined,
  );
  protected readonly canRetry = computed(
    () => this.agent.error()?.recovery === 'retry' && this.agent.retry !== undefined,
  );

  protected readonly errorMessage = computed(() => {
    const failure = this.agent.error();
    if (!failure) return '';
    switch (failure.kind) {
      case 'auth':
        return 'The deployment rejected the request. Check the credentials on your proxy.';
      default:
        // 'interrupted' included: the session already set the message that
        // matches the recovery it chose, and `detail` continues that sentence.
        return failure.message;
    }
  });

  protected retry(): void {
    void this.agent.retry?.();
  }

  protected checkStatus(): void {
    void this.agent.checkStatus?.();
  }
}
```

`retry` and `checkStatus` are optional commands: each is `undefined` on the agent when the session cannot offer it, which is why the component asks before it shows a button. Branching on `kind` covers the cases that need different copy without reading HTTP status codes; `failure.status` is there when you want the exact code. A LangGraph session reports three kinds: `auth` for a 401 or 403, `server` for a run or a request that failed, and `interrupted` for a stream that ended without a final state. Do not hard-code copy for `interrupted`: several different outcomes share that kind, and the session's own message is the one that matches the recovery it settled on.

### Retry with exponential backoff

`submit()` resolves with the outcome whether the run succeeded or failed. A failure lands on `error()` rather than rejecting the promise, so an automated retry reads the signal between attempts and uses `retry()`, which clears the error and sends the same input again under the same user message ID.

```typescript
import type { Agent } from '@threadplane/angular';

export async function submitWithBackoff(
  agent: Agent,
  text: string,
  maxAttempts = 3,
): Promise<void> {
  let outcome = await agent.submit(text);

  for (let attempt = 1; attempt < maxAttempts && outcome === 'error'; attempt++) {
    if (agent.error()?.recovery !== 'retry' || !agent.retry) break;
    await new Promise((resolve) => setTimeout(resolve, 1000 * 2 ** (attempt - 1)));
    outcome = await agent.retry();
  }

  const failure = agent.error();
  if (failure) throw new Error(failure.message);
}
```

The `recovery` check is what keeps a rejected credential from being retried three times. It matters more than that in an automated loop. The session offers `retry` only for a run the backend itself reported as failed, and for a first message whose thread could not be created. An `interrupted` error never offers it, because the server may already have begun answering, so the guard is also what stops a backoff loop from sending the same tool call or booking three times. A failed run can still have done work before it failed, and a retry runs the graph again from the same input.

## Stream recovery

A stream that closes without a final state is reported as an `interrupted` error rather than as a completed turn, and the partial content and any approval state stay on the signals. Because the server may already have begun answering, that error does not offer a retry. Where the transport can read thread history the session reports `recovery: 'check'` and exposes `checkStatus()`, a read-only reconciliation that reads the thread again and settles the turn: it clears the error when the run completed server-side after the stream died, and leaves it in place when the outcome stays unknown. Where it cannot, the recovery is `none` and the error says the outcome could not be confirmed.

`reconnect()` rejoins the run the session still holds, which `retainedRun()` names. Use `joinStream()` to join a run by ID after a page refresh or a navigation, when that session is gone. Both are LangGraph commands, so type the agent with `LangGraphSession`.

```typescript
import { injectAgent } from '@threadplane/angular';
import type { LangGraphSession } from '@threadplane/langgraph';

const agent = injectAgent<LangGraphSession>();

// Store the run ID when LangGraph creates the run
await agent.submit(
  { message: input },
  {
    run: {
      onRunCreated: ({ run_id }) => {
        localStorage.setItem('activeRunId', run_id);
      },
    },
  },
);

// After a reload, on the same thread, join the run again
const savedRunId = localStorage.getItem('activeRunId');
if (savedRunId) {
  // The second arg is an optional last-event id. Omit it (or pass
  // undefined) to join the run from its first event; pass a stored id to
  // continue with only the events after it.
  await agent.joinStream(savedRunId);
}
```

Run settings such as `onRunCreated` go under `run` in the submit options. `joinStream(runId, lastEventId?)` joins a run of the agent's current thread, so restore the thread ID first. It adds no user message and creates no run, and it resolves with the joined run's outcome. Joining from the first event is the safe default: the session asks for each run it starts as a resumable stream, and the run's full state is on the Platform, so the client renders it again from the start.

<Callout type="tip" title="Stateless client pattern">
The agent keeps nothing that has to survive a reload except the thread ID your application stores. All conversation state lives on the LangGraph Platform. This means your Angular app can be deployed anywhere (CDN, edge, SSR) without state management concerns. Scale your frontend independently of your agent infrastructure.
</Callout>

## Hosting the Angular app

A built Angular app is static files, so any static host will serve it. Two rules apply: rewrite unknown paths to `index.html` so client-side routing works, and proxy the LangGraph calls through the same origin so the deployment credentials stay on the server. On Vercel both are one file:

```json
{
  "rewrites": [
    { "source": "/api/langgraph/(.*)", "destination": "https://your-deployment.langgraph.app/$1" },
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}
```

That is the server-side layer the Authentication section describes, and it is why the production environment file sets `langgraphUrl` to `/api/langgraph`.

## CI/CD pipeline

The Python agent and the Angular frontend are independent artifacts, so a pipeline can build them in parallel.

```yaml
name: Deploy
on:
  push:
    branches: [main]

jobs:
  deploy-agent:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install langgraph-cli
      - run: langgraph deploy --project my-agent
        env:
          LANGSMITH_API_KEY: ${{ secrets.LANGSMITH_API_KEY }}

  deploy-angular:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
      - run: npm ci
      - name: Generate production environment
        run: |
          cat > src/environments/environment.prod.ts << 'EOF'
          export const environment = {
            production: true,
            langgraphUrl: '${{ secrets.LANGGRAPH_URL }}',
          };
          EOF
      - run: npx ng build --configuration production
      - name: Deploy to hosting
        run: |
          # Replace with your hosting provider's CLI
          # e.g., npx vercel deploy --prod dist/my-app/browser
          echo "Deploy dist/ to your hosting platform"
```

<Callout type="tip" title="Order the jobs when a release spans both">
Parallel is right when the two artifacts do not depend on each other. When a release changes the graph and the UI together, add `needs: deploy-agent` to the frontend job so the new API is live before any traffic reaches it.
</Callout>

## Monitoring

### LangSmith observability

When `LANGCHAIN_TRACING_V2=true` is set in your agent environment, every run is automatically traced in LangSmith. No code changes are needed.

Key metrics to track in production:

| Metric | Where to find it | Why it matters |
|--------|-------------------|----------------|
| End-to-end latency | LangSmith Runs tab | Directly affects user-perceived responsiveness |
| Error rate | LangSmith Runs tab, filter by error | Spike detection for broken tools or provider outages |
| Token usage | LangSmith per-run detail | Cost control and budget alerting |
| Time to first token | Angular performance monitoring | Stream startup latency visible to users |
| Thread count | LangGraph Platform dashboard | Capacity planning |

### Client-side monitoring

Track stream health from your Angular app:

```typescript
const status = this.agent.status(); // 'idle' | 'running' | 'error'
const isStreaming = status === 'running';

// Log stream lifecycle for your APM tool
effect(() => {
  const failure = this.agent.error();
  if (failure) {
    this.analytics.trackError('stream_error', failure.kind);
  }
});
```

## Deployment checklist

<Steps>
<Step title="Set production apiUrl">
Point the `apiUrl` you pass to `createSession()` to your same-origin LangGraph proxy, or to a direct LangGraph URL only when that deployment is intentionally public.
</Step>
<Step title="Match assistantId to the manifest">
Pass the `graphs` key from `langgraph.json` as `assistantId`. A mismatch fails on the first message, not at build time.
</Step>
<Step title="Configure authentication">
Route browser traffic through a server-side proxy or gateway that adds LangGraph credentials outside the Angular bundle.
</Step>
<Step title="Set up CORS">
Add your Angular app's origin to the `allow_origins` list in `langgraph.json`.
</Step>
<Step title="Handle errors gracefully">
Branch on `error().kind` for legible copy, show a retry button only when `error().recovery` is `retry` and the agent has `retry`, and offer a status check when `error().recovery` is `check` and the agent has `checkStatus`.
</Step>
<Step title="Implement stream recovery">
Offer `checkStatus()` after a dropped stream, and store the run ID to rejoin with `joinStream()` after a reload.
</Step>
<Step title="Persist thread IDs">
Store the thread ID that `onThreadId` reports in `localStorage` or a backend so users can resume conversations across sessions.
</Step>
<Step title="Configure throttle">
A session does not throttle its updates by default. Pass `throttle` to `createSession()` if token-by-token updates are too frequent for your UI rendering.
</Step>
<Step title="Enable LangSmith tracing">
Set `LANGCHAIN_TRACING_V2=true` in your agent environment for production observability.
</Step>
<Step title="Secure environment files">
Add `environment.prod.ts` to `.gitignore`. Generate it from CI secrets at build time.
</Step>
<Step title="Set up CI/CD">
Automate agent and Angular deployments on push to your main branch.
</Step>
<Step title="Verify monitoring">
Confirm LangSmith traces are arriving and set up alerts for error rate spikes and latency regressions.
</Step>
</Steps>
