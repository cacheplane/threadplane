# Durable Execution

Persistence keeps a thread's history; durable execution keeps a _run_ alive through failure. When a step crashes, the process restarts, or a deployment rolls, the checkpointer lets the run resume from its last completed super-step instead of starting over, and the UI can offer a status check, a retry, or a reconnect rather than a blank transcript.

This page is the live example for durable execution over LangGraph. Use **Run** to watch one request move through a three-node graph that commits its state after every node, **Code** to read the Angular and Python sources, and **API** for the extracted reference. The checkpointer configuration it relies on is written up in the [Persistence guide](/docs/angular/langgraph/guides/persistence).

## What the demo does

The Run tab shows the prebuilt `<chat>` composition beside a sidebar titled Pipeline, listing three steps: Analyze, Plan, and Generate. Send any question and the sidebar tracks the run. Each step shows the spinner once its own node has committed and the next one is running, and turns green when a later node commits. The graph writes the name of the node it just finished, so the indicator trails execution by one step, and nothing spins while the first node runs. The component reads that field back out of state.

Two things are worth watching. The first is how long each step holds: the graph makes a separate model call per node, so the answer you eventually read is the third of three passes rather than one long generation. The second is where the sidebar stops. The final step stays marked active rather than complete when the run ends, because `generate` is the last name the graph ever writes and there is no fourth step for the indicator to advance to.

Nothing in the demo fails on purpose. What durability buys you here is visible in the shape of the run rather than in a staged crash: three separately committed steps instead of one all-or-nothing call.

## How it is built

Three files carry the feature: a graph that splits one answer into three checkpointed nodes, an application config that registers the agent, and a component that derives the sidebar from graph state. Open the Code tab to read them in place.

### The state the run carries

The state schema is short on purpose. Alongside the message list it keeps a single `step` string, which is the entire progress protocol between the graph and the browser, and two optional identifiers that only the final node writes.

No field declares a reducer, so whatever a node returns for a key replaces that key outright.

### One node of the pipeline

Each node loads the shared system prompt, appends a line telling the model which phase it is in, calls the model, and returns the conversation with its own response appended plus the name of the step it just completed. `analyze` is the first of the three and `plan` is the same code with a different instruction.

<ExampleCode file="graph.py" region="analyze" title="graph.py — the analyze node" />

The return value is the commit: LangGraph saves the state a node returns before the next node starts, which is what makes the run recoverable partway through.

### The node that ends the run

`generate` is where the shape changes. The first two nodes append to the message list they received, so the intermediate analysis and outline accumulate in state. The last node returns two messages, and because `messages` has no reducer that return replaces the list. It scans backwards for the newest human message rather than reading `state["messages"][-1]`, which by that point is the plan node's outline, so the pair it commits is the user's original question and the final answer. It also records the identifiers of that pair, which the React version of this example uses to confirm the turn.

<ExampleCode file="graph.py" region="generate" title="graph.py — the generate node" />

The scratch work exists for exactly as long as the run needs it: once `generate` commits, the thread holds the question and the answer, and the analysis and outline are gone.

### The agent provider

`provideAgent()` from `@threadplane/angular` registers the agent once for the whole application, and it is the only provider this example needs. Its config supplies `createSession`, a function that builds a LangGraph session with `createSession()` from `@threadplane/langgraph`. The agent calls it once at start and again for each thread switch. The example wraps the config in a factory because it resolves its connection details at runtime from the host that serves the demo.

<ExampleCode file="app.config.ts" />

Your own application does not need the outer factory. Pass the two connection values directly, and forward the thread the agent hands you:

```typescript
import { provideAgent } from '@threadplane/angular';
import { createSession } from '@threadplane/langgraph';

provideAgent({
  createSession: async (context) =>
    createSession({
      ...context,
      apiUrl: 'https://your-deployment.langgraph.app',
      assistantId: 'durable-execution',
    }),
});
```

`assistantId` must match the graph name in `langgraph.json`.

<Callout type="warning" title="Keep the API key on the server">
Never expose a LangSmith API key in client-side code. Point `apiUrl` at a deployment that authenticates the browser another way, or proxy the requests through your own server and attach the key there.
</Callout>

The component holds the node order and the labels it renders for them. This list is the contract with the graph: the strings are the node names the Python side writes into `state.step`.

## What durability covers

Splitting one answer across three nodes is what makes the run durable. Each node's return is committed before the next one starts, so a failure in `generate` does not throw away the analysis and the outline, and the thread you retry against is not empty.

What it does not cover is the request in the browser. A dropped connection, a restarted server, or an error from the model ends the run in the client with an error, and something has to start a new one. That is the UI's job, and it is one call — but only when starting a new one is safe.

### Retrying a failed run

The `<chat>` composition already renders the retry. Its error banner shows a Retry response button whenever the error it received is marked retryable and the agent has a `retry` command, and the button calls `agent.retry()`. The session marks an error retryable in two cases only: the backend itself reported the run as failed (`error` or `timeout`), or the thread for a first submission could not be created.

A dropped stream is the case that does not qualify. When the stream closes without a terminal event the session reports an `interrupted` error, and the run may well have carried on and committed its next node on the server. Retrying it would run that work twice, so the banner does not offer a retry. Instead it offers Check status where the transport can read thread history, a read-only re-read that resubmits nothing and settles the turn if the run turns out to have finished, and otherwise says plainly that the outcome could not be confirmed. A failure before any response is reported the same way, because the client cannot prove the request never left.

`retry()` puts the transcript and state back to what they were before the command and sends the captured input again, against the same thread. A submission keeps its user message id, so the transcript gains no second copy. It is an optional command, so call it as `agent.retry?.()`. Three guards matter when you call it yourself:

- It resolves `'aborted'` without sending while a request is active, so a double click cannot start a second run.
- It resolves `'aborted'` when nothing failed: before the first submission, and after `switchThread()`, which replaces the session. A Retry button on a thread the user just switched to is a button that does nothing.
- It rejects while the error shown is not a retryable one, such as a dropped stream. After `checkStatus()` settles that error as a failed run, `retry()` is allowed.

When the session loses its stream to a run that may still be going, it names that run in `retainedRun()`. `reconnect()` joins it from its last cursor and never submits another run, and `joinStream(runId, lastEventId?)` projects a run of this thread that the session did not start, such as one created by another client or before a reload. Both are LangGraph extensions, typed on `injectAgent<LangGraphSession>()`. `checkStatus()` is the portable form, and a resolved check clears the retained run.

<Callout type="info" title="A retry is a new run, not a rewind">
A retry runs the graph again from the same input, against the same thread. The view returns to what it showed before the command, but a failed run can still have done work in the steps before it failed, and those steps can run again. The thread gains no second user message when its `messages` key uses the standard `add_messages` reducer, which replaces a message by id. To answer a prompt again from an earlier point, `regenerate(messageId)` is the call: it takes the `id` of an assistant message and forks from the newest saved checkpoint that does not hold the prompt before it yet. It rejects rather than no-ops while a response is running or when the id is not an assistant message.
</Callout>

### Continue pending work or answer an interrupt

`submit(null)` starts a run with no input: the graph continues from the thread's saved state and no user message is added. Use it with `run.command` to route or update the graph, or after an external state update. `runWithoutMessage({ state })` is the core contract's command for the same run, and it merges a partial state first. A dynamic `interrupt()` needs an answer: call `resume()` with a response that names the pending interrupt, so the session sends LangGraph a resume command. Submitting null alone does not answer that interrupt. See the [Interrupts guide](/docs/angular/langgraph/guides/interrupts).

It is not the retry. A run with no input sends nothing the failed command carried; it only asks the graph to continue from what the thread saved. Every one of these commands takes the LangGraph settings of the run it creates under `options.run`, beside `config`, `context`, `metadata`, and `signal`: `durability`, `onDisconnect`, `multitaskStrategy`, `checkpointId`, and the rest. A setting at the root of the options is never read, and nothing carries over to the next command.

<Callout type="warning" title="Guard the retry affordance">
`retry()` sends nothing when the agent has nothing to send again, and `checkStatus()` and `retry()` are both optional commands. Render each button from `error()?.recovery` and from whether the command exists, as `<chat>` does, so the user is never offered a control that cannot do anything.
</Callout>

### Where checkpointing comes from

Nothing in this example configures durability. The graph compiles without a checkpointer and the component asks for no recovery options, because the LangGraph API server checkpoints every thread it runs. Move the same graph into a process you host and the checkpointer becomes yours to choose — an in-memory saver for tests, Postgres for anything that has to survive a restart. The [Persistence guide](/docs/angular/langgraph/guides/persistence) covers the choice and the warning that comes with it: a graph served by `langgraph dev` or LangGraph Platform must not compile a checkpointer of its own.
