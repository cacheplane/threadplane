# Interrupts

Interrupts let a LangGraph agent pause mid-execution and hand control to a human. The agent proposes an action, the graph freezes, your Angular UI shows an approval card, the person decides, and the agent resumes with that decision. The injected agent lists the pending interrupts in its `interrupts()` signal and answers them with `resume()`, so an approval flow needs no manual event wiring. The running example is a refund authorization, and this guide walks the three files that make it work.

<Callout type="info" title="When to use interrupts">
Use interrupts when an agent action is irreversible (sending an email, placing an order, issuing a refund), when the agent needs a human decision it cannot make on its own, or when compliance requires explicit approval before execution.
</Callout>

## A pause is a decision point

In a trip planner, proposing a booking and making the booking are different actions. An interrupt lets the backend save a pending decision, return control to the person, and continue when the application submits that decision. The approval UI should describe the actual pending payload and remain associated with that pause.

<RunState />

The interrupt belongs to agent state; it is not another chat message. Keep the composer, progress display, and decision controls consistent with that state. The example below uses a simulated refund so you can follow the pause and resume without issuing a real charge.

## What the demo does

The Run tab shows the prebuilt `<chat>` composition in front of a refund graph. Ask for a refund and the agent acknowledges the draft in the transcript, and then the run stops: an approval panel appears at the end of the conversation with the amount, the customer identifier, and the reason the agent extracted from your request, above three buttons: Issue refund, Edit, and one that declines the refund.

Two welcome suggestions set it up. "Refund a duplicate charge" asks for $47.50 back to customer `cus_a8x2k`, and "Refund a chargeback" asks for $129.00 with a different justification, so you can watch the same pause fire on two different payloads.

Approve resumes the graph, which issues a stand-in refund and posts the refund ID into the transcript. Cancel resumes it with a rejection, and the graph says so and issues nothing. Edit is the interesting one: the card stays open, an amount field appears, and saving resumes with an amount the operator chose rather than the one the agent proposed.

## How it is built

Three files carry the whole feature: a graph that stops in the middle of a run, an application config that registers the agent, and a component that maps the card's three buttons onto resume values. Open the Code tab to read them in place.

Splitting extraction from narration is deliberate: the card needs typed fields, and the transcript needs prose, and one call cannot do both well.

### Pausing at interrupt()

`interrupt()` freezes the graph and streams its argument to the client. The argument is any JSON-serializable value, and it becomes the payload your component renders. When the client resumes, that same call returns the resume value, so the node reads like a straight-line function even though a human answered in the middle of it.

<ExampleCode file="graph.py" region="request-approval" title="graph.py — the interrupt" />

Notice the `kind` field on the payload. It is not required by LangGraph; it is how the frontend tells this interrupt apart from any other one the graph might raise. Notice too that the node validates what came back: a resume value that is not a dictionary, or one whose `approved` is missing or false, is treated as a rejection.

<Callout type="tip" title="A resumed node re-executes from the top">
LangGraph resumes by running the interrupting node again, and `interrupt()` returns the resume value instead of pausing a second time. Every line above the `interrupt()` call runs again, including on later retries, so keep that stretch free of side effects. Reading state, as the example does, is safe; charging a card there is not.
</Callout>

### Routing on the decision

After the pause the graph branches. A conditional edge sends an approved refund to the node that issues it and sends everything else to the end, which is why the rejection message is written by the interrupting node itself.

<ExampleCode file="graph.py" region="graph" title="graph.py — issuing and routing" />

`compile()` is called with no checkpointer, because the LangGraph API server provides persistence and either rejects or ignores a graph that brings its own. The [Persistence guide](/docs/angular/langgraph/guides/persistence) covers the checkpointer choices for a graph you embed in your own process.

<Callout type="warning" title="Interrupts require a checkpointer somewhere">
A paused graph is a stored checkpoint. Serving through `langgraph dev` or LangGraph Platform gives you that for free. `langgraph dev` refuses to load a graph that compiles its own saver, and a deployment ignores it, so leave it off in both cases.
</Callout>

### The agent provider

`provideAgent()` from `@threadplane/angular` registers the agent once for the whole application, and it is the only provider this example needs. Its config supplies `createSession`, a function that builds a LangGraph session with `createSession()` from `@threadplane/langgraph`. The agent calls it once at start and again for each thread switch. The example wraps the config in a factory because it resolves its connection details at runtime from the host that serves the demo.

<ExampleCode file="app.config.ts" />

Your own application does not need the outer factory. Pass the two connection values directly, and forward the thread the agent hands you:

```typescript
import { provideAgent } from '@threadplane/angular';
import { createSession } from '@threadplane/langgraph';

provideAgent({
  createSession: (context) =>
    createSession({
      ...context,
      apiUrl: 'https://your-deployment.langgraph.app',
      assistantId: 'interrupts',
    }),
});
```

`assistantId` must match the graph name in `langgraph.json`.

<Callout type="warning" title="Keep the API key on the server">
Never expose a LangSmith API key in client-side code. Point `apiUrl` at a deployment that authenticates the browser another way, or proxy the requests through your own server and attach the key there.
</Callout>

### The approval card

`<chat-approval-card>` is a prebuilt composition. Give it the agent and it watches `interrupts()` for you: when a pending interrupt arrives it shows an approval panel with that interrupt's `value` as the payload, and when the interrupt resolves the panel goes away. Put it in a `chatInterruptTemplate` inside `<chat>` so the panel sits at the end of the transcript. `approveLabel` and `cancelLabel` name the two actions, and `presentation="dialog"` opens a modal instead. `matchKind` compares the payload's `kind` field, so the card picks the first pending interrupt that is a refund approval and ignores any other, and `showEdit` adds the third button.

<ExampleCode file="interrupts.component.ts" region="approval-card" title="interrupts.component.ts — the card" />

The card owns the chrome and the buttons; the `#body` template owns the content. The payload arrives as the template's implicit value, so the demo renders the amount through the currency pipe and reveals the edit form inline rather than in a second dialog.

### Resuming with the decision

The card emits an action rather than resuming by itself, which leaves the resume value entirely up to the component. Approve and Cancel are terminal, so the handler answers with the matching decision. Edit is not: it flips a signal, the body template grows an amount field, and the Save button answers with the edited value. All three paths end in the private `answer()` method, which reads the first pending interrupt and calls `resume()`.

<ExampleCode file="interrupts.component.ts" region="resume" title="interrupts.component.ts — resuming the graph" />

`resume(responses)` continues the paused run instead of starting a new one. Each response names one pending interrupt by its `id` and carries the status `resolved`. With one interrupt pending, the response's `value` is exactly what `interrupt()` returns on the server. LangGraph has no cancelled response, so a refusal is a value the graph reads, which is why Cancel sends `{ approved: false }`.

The component injects the agent as `injectAgent<LangGraphSession>()`. Naming the session type makes `interrupts()` a list that is always present and `resume` a command that always exists. The ref-less `injectAgent()` is typed by the core contract, where both are optional: read `interrupts()?.[0]` and call `agent.resume?.(...)` there.

<Callout type="info" title="Injection context">
`injectAgent()` must run inside an Angular injection context: a field initializer, as it is here, or a constructor body.
</Callout>

## The interrupt lifecycle

Five stages, and the example passes through all of them on every refund:

<Steps>
<Step title="The agent plans">
A node reasons about the request and produces the structured payload that describes what it wants to do. In the example that is the draft node and its extraction call.
</Step>
<Step title="The interrupt fires">
A node calls `interrupt({...})`, which freezes the graph. The payload is persisted in the checkpoint and streamed to the client.
</Step>
<Step title="The UI shows the decision">
The agent's `interrupts()` signal lists the pending interrupt. The approval card reads it, matches on `kind`, and shows its panel.
</Step>
<Step title="The person decides">
Approve, Edit, or Cancel. The component calls `agent.resume()` with one response whose `value` carries the decision.
</Step>
<Step title="The agent resumes">
LangGraph re-runs the interrupting node, `interrupt()` returns the resume value, and the graph routes on it — issuing the refund or ending the run.
</Step>
</Steps>

## Retrying a resume and restoring a thread

`retry()` is an optional command, present when the transport can read the status of an exact run. It sends a command again only when the backend reported that command's run as failed (`error` or `timeout`), or when the thread for a first submission could not be created. The error then carries `retryable: true` and `recovery: 'retry'`. A retried resume sends the same response and no message. The response was captured when it was sent, so later edits to the caller's object cannot change the retry.

A dropped stream is a different case. A transport failure does not prove the server rejected the decision, so the session reports an `interrupted` error, and `retry()` rejects while that error is shown. Where the transport can read thread history the error's `recovery` is `'check'`, and `checkStatus()` reads the saved thread without sending anything. New activity, or a different pause, settles the turn. The same pause with nothing new is inconclusive: the decision may never have landed, or may still be running before its first checkpoint, so the session neither restores the pause nor replays the decision.

An uncertain resume does not strand the operator. The pending interrupt lives in the server checkpoint, and the agent reads a thread's history when it selects that thread, so reloading the thread (`switchThread()` with the current id does that) restores a pause that is still pending, and the decision can be sent again. Retaining the thread ID and the server checkpoint is required. A retry, by contrast, lives in the current session: loading the thread or sending another command withdraws it, and reopening the browser restores the server checkpoint, not the captured command. Neither a stopped stream nor a dismissed approval card proves that the backend completed or cancelled the work.

`interrupts()` for display and `resume(responses)` for the decision are the core contract, so a component written against them works with any session that can pause. What a response may express is the backend's rule: this session rejects, without sending, a response that names an interrupt that is not pending, names one twice, or uses the status `cancelled`. Server checkpoint retention and safe handling of repeated side effects remain backend responsibilities.

### Migration note

The Angular-only adapter exposed one `interrupt()` signal and resumed through `submit({ resume })`. Both are gone. Read `interrupts()[0]` (or `interrupts()?.[0]` on a core-typed agent) and answer with `resume([{ interruptId, status: 'resolved', value }])`. A `command.resume` under the run settings is rejected, because the answer is the argument of `resume()`. Restore an existing thread through its checkpoint before offering an approval again, and keep side effects above `interrupt()` safe to re-execute.

## Approving more than once

The example pauses once per run. A workflow that needs a sign-off at each stage of a plan uses the same primitive in a loop: the approving node interrupts on the current step, the executing node advances the counter, and a conditional edge sends the run back for the next approval until the plan is exhausted.

```python
def approve_step(state: DeployState) -> dict:
    step = state["plan"][state["current_step"]]
    decision = interrupt({
        "kind": "deploy_step",
        "step_number": state["current_step"] + 1,
        "total_steps": len(state["plan"]),
        "description": step["description"],
    })
    return {"approval_result": decision}


def should_continue(state: DeployState) -> str:
    return "approve_step" if state["current_step"] < len(state["plan"]) else END


builder.add_edge("approve_step", "execute_step")
builder.add_conditional_edges("execute_step", should_continue)
```

Nothing changes on the client. Each pause raises one interrupt, the card matches on `kind` exactly as before, and the same `resume()` call answers it. A card that should show progress reads the counters straight out of the payload, which is the reason to put `step_number` and `total_steps` in there rather than deriving them.

<Callout type="info" title="Reading every pending interrupt">
`interrupts()` is already the whole list. When a run pauses in several branches at once, one `resume()` call can answer any of them: the answered ones are sent together, keyed by the id the backend gave each interrupt, so each response needs a value, and the others stay pending. `subgraphs()` carries the interrupts a child graph reported, for display only.
</Callout>

## Typed interrupt payloads

An interrupt's `value` is plain data whose shape belongs to the graph that paused, so the agent types it as `PlainValue`. The example lets it reach the template untyped, giving the payload a shape only where `submitEdit()` declares its parameter. Narrow it once, with a type guard, and every read after that is typed.

Graph state is typed a different way: declare it on the session with `stateType`, and carry the session type through a ref from `createAgentRef()`. This variation passes that ref to both `provideAgent()` and `injectAgent()`, where the example uses the unnamed form.

```typescript
import { computed } from '@angular/core';
import { createAgentRef, injectAgent, provideAgent } from '@threadplane/angular';
import { type, type ToolContract } from '@threadplane/core';
import { createSession, type LangGraphSession } from '@threadplane/langgraph';

// The exact shape the graph passes to interrupt()
interface RefundApproval {
  kind: 'refund_approval';
  amount: number;
  customer_id: string;
  reason: string;
}

// The graph state without `messages`, as `agent.state()` reports it
interface RefundState {
  amount?: number | null;
  customer_id?: string | null;
  decision_approved?: boolean | null;
}

type RefundSession = LangGraphSession<Record<string, ToolContract>, RefundState>;

// The ref carries the session type from the provider to every inject site.
export const REFUND_AGENT = createAgentRef<RefundSession>('interrupts');

// app.config.ts
provideAgent(REFUND_AGENT, {
  createSession: (context) =>
    createSession({
      ...context,
      apiUrl: 'https://your-deployment.langgraph.app',
      assistantId: 'interrupts',
      stateType: type<RefundState>(),
    }),
});

function isRefundApproval(value: unknown): value is RefundApproval {
  return (
    typeof value === 'object' &&
    value !== null &&
    (value as { kind?: unknown }).kind === 'refund_approval'
  );
}

export class TypedApprovalComponent {
  private readonly agent = injectAgent(REFUND_AGENT);

  readonly pending = computed(() => {
    const interrupt = this.agent.interrupts()[0];
    return interrupt && isRefundApproval(interrupt.value)
      ? { id: interrupt.id, payload: interrupt.value }
      : undefined;
  });

  readonly amount = computed(() => this.pending()?.payload.amount); // number | undefined
  readonly approved = computed(() => this.agent.state()?.decision_approved); // typed by RefundState
}
```

`type<T>()` checks nothing at runtime. Pass a Standard Schema, such as a Zod object, as `stateType` to have each reported state checked as well.

<Callout type="tip" title="Type your interrupts early">
Define the payload interface next to your Python state schema. It is the contract between graph and UI, and when the Python payload changes the TypeScript interface has to change with it. Generating both from one schema is worth it once the payloads stop being trivial.
</Callout>

## Timeout handling

An interrupt pauses execution indefinitely by default: the agent waits until a human responds. In production you usually need a fallback for the case where nobody does.

For me, the server-side timeout is the safer default. It costs you a background job to run and maintain, but it fires even if the user closed the tab — which is exactly when you most need it to.

**Server-side timeout with a background task:** schedule a job that looks for stale interrupts and resumes them with a default decision.

```python
async def check_stale_interrupts():
    """Periodic task to auto-reject stale interrupts."""
    threads = await client.threads.search(
        status="interrupted",
        metadata={"interrupt_type": "approval"},
    )
    for thread in threads:
        created = thread["updated_at"]
        if (now() - created).total_seconds() > 3600:  # 1 hour timeout
            await client.runs.create(
                thread["thread_id"],
                assistant_id="interrupts",
                input=None,
                command={"resume": {
                    "approved": False,
                    "reason": "Auto-rejected: approval timeout",
                }},
            )
```

**Client-side timeout in Angular:** run a timer in the component and reject if the operator does not act.

```typescript
import { effect } from '@angular/core';

// Watch for a pending interrupt and start a timeout
effect((onCleanup) => {
  const pending = this.agent.interrupts()[0];
  if (!pending) return;
  const timeout = setTimeout(() => {
    // Auto-reject after 5 minutes of inaction
    void this.agent.resume([
      { interruptId: pending.id, status: 'resolved', value: { approved: false } },
    ]);
  }, 5 * 60 * 1000);
  // Clean up if the operator responds before the timeout
  onCleanup(() => clearTimeout(timeout));
});
```

<Callout type="warning" title="Pick one timeout strategy">
Avoid running server-side and client-side timeouts together. If both fire, the second answer arrives for a pause the graph has already moved past, and two responders to one pause are something the application has to coordinate. Choose the server side for reliability, since it works even when the browser is closed, or the client side for immediacy.
</Callout>

<Callout type="info" title="Checkpoint persistence saves you">
With a durable server checkpointer and the same thread ID, the operator can close the browser and later restore an action that is still pending: the agent reads the thread when it selects it, and the pause returns in `interrupts()`. A lost or expired checkpoint cannot be recreated from browser state; another operator or a server timeout may also have already answered it.
</Callout>
