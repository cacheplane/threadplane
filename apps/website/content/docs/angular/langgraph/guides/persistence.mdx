# Persistence

<DocsDemoVideo demo="persistence" frontend="angular" />

Thread persistence keeps conversations alive across page refreshes, browser restarts, and server deployments. LangGraph checkpoints agent state at every super-step, keyed by a thread ID, and the agent you get from `injectAgent()` reads them back whenever a thread is selected. The running example is a chat with a thread sidebar, and this guide walks the four files that make it work.

<Callout type="tip" title="Prerequisites">
Make sure you have completed the Installation guide first.
</Callout>

## Save the conversation and remember its address

A traveler should be able to close the Portland itinerary and return to the same plan. The server must retain the messages and agent state; the application must remember which thread to load. These are separate responsibilities.

<PersistenceModel />

The thread ID is an address. A checkpoint is a saved version of the agent state at a step in that thread. The sidebar is an application view of available threads. Keeping one of these does not automatically keep the others: this demo's page-local list disappears on reload even though the server still holds its threads. The reload example later in this guide adds the missing address retention.

## What the demo does

The Run tab shows the prebuilt `<chat>` composition next to a thread sidebar. Send a message and the backend assigns a thread ID, which appears in the sidebar as "Thread 1". Click "+ New Thread" and send another message, and you have two conversations you can move between.

Switching back to an earlier thread replays its stored history: the messages come back from the server checkpoint, not from anything the browser kept. Give each thread a different fictional fact, and you can tell them apart when you return.

## How it is built

Four pieces carry the whole feature: a graph that leaves checkpointing to the platform, an application config that deliberately does not register the agent, a component-scoped provider that captures thread IDs, and a sidebar that switches between them. Open the Code tab to read them in place.

### The graph and its checkpointer

The backend is a single node. `MessagesState` gives the LangGraph SDK a message list it already understands, the node prepends a system prompt read from the capability's prompt file, and the compiled graph is exported as `graph`, which is the symbol `langgraph.json` points at.

<ExampleCode file="graph.py" />

Look at the last line of `build_persistence_graph`: it calls `compile()` on the `StateGraph` with no checkpointer at all. Persistence here comes entirely from the LangGraph API server, which is the case whenever you serve a graph with `langgraph dev` or on LangGraph Platform.

<Callout type="warning" title="Serving through langgraph dev or LangGraph Platform? Do not compile a checkpointer.">
The platform provides persistence itself. `langgraph dev` refuses to load a graph that compiles its own saver, and a deployment ignores one, so leave it off in both cases. Call `compile()` on the `StateGraph` with no argument, as the example does.

Passing one is not a soft warning — `langgraph dev` fails to load the graph and exits:

```text
ValueError: Heads up! Your graph 'graph' from './graph.py' includes a custom
checkpointer (type <class 'langgraph.checkpoint.memory.InMemorySaver'>). With
LangGraph API, persistence is handled automatically by the platform…
Application startup failed. Exiting.
```

To point the platform at your own database, set the `POSTGRES_URI` environment variable rather than constructing a saver in code.
</Callout>

### Capturing thread IDs with onThreadId

`provideAgent()`, from `@threadplane/angular`, sits in the component's `providers` array, so the agent and its callback are created with the component. The config has two members. `createSession` builds a LangGraph session for one thread with `createSession()` from `@threadplane/langgraph`; the agent calls it once at the start and again for each thread switch, passing the thread to open as `context.threadId`. `onThreadId` is the application's callback.

<ExampleCode file="persistence.component.ts" region="agent-provider" title="persistence.component.ts — the agent provider" />

The example passes a factory because it resolves its connection details at runtime from the host that serves the demo. Your own application passes the config object with its `apiUrl` and `assistantId`:

```typescript
import { provideAgent } from '@threadplane/angular';
import { createSession } from '@threadplane/langgraph';

provideAgent({
  createSession: (context) =>
    createSession({
      ...context,
      apiUrl: 'https://your-deployment.langgraph.app',
      assistantId: 'persistence',
    }),
  onThreadId: (id) => console.log('New thread', id),
});
```

A session that starts without a thread creates one on its first submit and reports the ID. The agent adopts it and calls `onThreadId` once for that thread. The example's callback records it as the active thread and appends it to the list if it is new, which is the only bookkeeping the sidebar needs.

<Callout type="warning" title="Thread IDs come from the server">
Use a thread that the backend has confirmed exists. The agent supplies the ID of each thread a session creates through `onThreadId`. An application using the Threads API may request its own UUID, but must create that thread and confirm the returned identity before submitting a run; generating a string alone creates no saved conversation.
</Callout>

<Callout type="warning" title="Keep the API key on the server">
Never expose a LangSmith API key in client-side code. Point `apiUrl` at a deployment that authenticates the browser another way, or proxy the requests through your own server and attach the key there.
</Callout>

### Switching and starting threads

The class itself is small. It injects the agent registered above, forwards a suggestion into `submit()`, and exposes the two thread actions the sidebar calls. `injectAgent<LangGraphSession>()` names the session type, which adds the LangGraph fields and commands to the core ones.

<ExampleCode file="persistence.component.ts" region="thread-actions" title="persistence.component.ts — agent and thread actions" />

A session belongs to one thread. `switchThread(id)` replaces the session with one for that thread and reads its saved history; every signal the composition reads stays the same reference and follows the new session. `switchThread(null)` moves to a new, empty conversation and sends no request; the thread is created on the next submit, and `onThreadId` adds it to the sidebar. `agent.threadId()` is the thread the agent is on, or `null` before one exists.

<Callout type="info" title="Injection context">
`injectAgent()` must run inside an Angular injection context: a field initializer, as it is here, or a constructor body.
</Callout>

<Callout type="info" title="Backend-defined behavior">
The agent reads a selected thread's history through the session's optional `load()` command. A LangGraph session has it because the LangGraph API exposes per-thread checkpoint history. The core session contract does not require it, so an agent over a backend without `load()` switches to an empty transcript. If you are writing your own backend, the [Writing an Adapter guide](/docs/angular/chat/guides/writing-an-adapter) covers the design choice.
</Callout>

## Choosing a checkpointer

The example leaves checkpointing to the platform, and that is the right default. The checkpointers below apply when you **embed** the graph in your own process — a FastAPI app calling `graph.ainvoke()`, a worker, a script, or an AG-UI server built with `ag-ui-langgraph` (which needs a checkpointer to read state via `aget_state`).

`@threadplane/langgraph` connects to a LangGraph *server*, so if you are following the [Quick Start](/docs/angular/langgraph/getting-started/quickstart) and running `langgraph dev`, you are in the first case and can skip this section.

<Tabs>
<Tab label="MemorySaver (dev)">

```python
from langgraph.checkpoint.memory import MemorySaver

# MemorySaver stores checkpoints in-process memory
# Fast for development — lost when the process restarts
graph = builder.compile(checkpointer=MemorySaver())
```

</Tab>
<Tab label="SqliteSaver (prototype)">

```python
from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver

# Persists to a local file — survives restarts, zero infrastructure
async with AsyncSqliteSaver.from_conn_string("checkpoints.db") as checkpointer:
    graph = builder.compile(checkpointer=checkpointer)
```

</Tab>
<Tab label="PostgresSaver (production)">

```python
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

DATABASE_URL = "postgresql://user:pass@localhost:5432/myapp"

async with AsyncPostgresSaver.from_conn_string(DATABASE_URL) as checkpointer:
    # Run migrations once on startup
    await checkpointer.setup()

    graph = builder.compile(checkpointer=checkpointer)
```

</Tab>
</Tabs>

<Callout type="warning" title="Production checkpointers">
MemorySaver is for development only — all state vanishes when the process exits. For anything users depend on, use PostgresSaver. SqliteSaver is a middle ground for prototypes and single-server deployments where you need persistence without a database.
</Callout>

## Thread IDs in graph invocation

When you invoke an embedded graph yourself, the thread ID is how LangGraph associates a conversation with its checkpoint history. Pass it in the `configurable` dict on every call:

```python
# First message creates the thread
result = graph.invoke(
    {"messages": [{"role": "user", "content": "What is LangGraph?"}]},
    config={"configurable": {"thread_id": "user_123"}}
)

# Second message continues the same conversation
result = graph.invoke(
    {"messages": [{"role": "user", "content": "How does it handle state?"}]},
    config={"configurable": {"thread_id": "user_123"}}
)
# The agent sees both messages — the full history is restored from the checkpoint
```

<Callout type="tip" title="Thread ID strategy">
Use stable, user-scoped identifiers for thread IDs. A common pattern is `f"{user_id}_{session_id}"` — this prevents cross-user data leaks and lets one user have multiple conversations.
</Callout>

## Surviving a full page reload

The example keeps its thread list in memory, so a browser refresh starts it over. An application that should survive a reload writes the IDs somewhere durable and reads them back at startup:

```typescript
import { signal } from '@angular/core';
import { provideAgent } from '@threadplane/angular';
import { createSession } from '@threadplane/langgraph';

const threadId = signal<string | null>(localStorage.getItem('threadId'));

provideAgent({
  // Restore the last thread on app start
  threadId,
  // Persist the ID whenever a session creates a thread
  onThreadId: (id) => {
    threadId.set(id);
    localStorage.setItem('threadId', id);
  },
  createSession: (context) =>
    createSession({
      ...context,
      apiUrl: 'https://your-deployment.langgraph.app',
      assistantId: 'persistence',
    }),
});
```

`threadId` accepts a string, `null`, or a signal. A signal is the other way to change threads: set it to a different ID and the agent switches to that thread and reads its checkpoint history, as `switchThread()` does. The change is picked up when Angular next runs effects. The example calls `switchThread()` instead because it wants the switch to happen exactly when the button is clicked.

The agent reads history itself, so an Angular app does not set the session's `autoLoad` option. That option is for a session used without the agent: with `autoLoad: true`, a session created with a `threadId` calls its own `load()`.

### What a reloaded thread shows

A reloaded thread is rebuilt from checkpoint history, not from the stream events the live view saw, so it shows what history carries and no more:

- **Messages, state, tool calls and pending interrupts** come from the latest checkpoint.
- **Reasoning** is restored from the `reasoning` and `thinking` content blocks the checkpoint saved with each assistant message. Its duration is not: the session measures reasoning time as text arrives and history was never observed arriving, so a reloaded message has no `reasoningDurationMs` and shows its reasoning without the "Thought for" duration label.
- **Subagent cards** are not rebuilt by default, because no child event replays when a thread is loaded. Pass `restoreSubagents: true` to `createSession()` and a load rebuilds the children started by delegation tool calls (the `subagentToolNames` option, `task` by default) from the parent's tool calls and their results, so each card sits under its tool call with its final status. The parent checkpoints also link each call to the child's checkpoint namespace; the default transport reads the child's latest checkpoint there to restore the card's transcript, and a run that resumes after the reload updates the same child instead of opening a second one.
- **Not rebuilt:** compiled subgraphs added as plain graph nodes, nested delegations (a subagent that delegates again), and tool progress events. History does not tie these to a parent tool call, so they appear only while a run is streaming.

A custom transport restores child transcripts only if it implements the optional `getChildState()` method; without it, restored subagent cards come back with their status and no messages.

<Callout type="tip" title="Thread loading state">
Use the `isThreadLoading()` signal to show a skeleton UI while the agent reads checkpoint state from the server. This avoids a flash of empty content when switching threads.
</Callout>

<Callout type="info" title="Reloading the current thread">
`switchThread()` with the ID the agent is already on reads that thread again. It replaces the session, as any switch does, so a run in progress on the old session is stopped first.
</Callout>

## Forking a conversation

A fork branches the same thread from an earlier checkpoint: `agent.fork(checkpoint, input)`, on an agent typed with `LangGraphSession`, starts a run from that checkpoint, and the thread gains a branch there. The [Time Travel guide](/docs/angular/langgraph/guides/time-travel) covers checkpoints and branches. There is no command that copies a transcript into a new thread: a `state` patch on `submit()` cannot carry `messages`.

## Checkpoint recovery

When a connection drops mid-stream, the run may still be going on the server. The session reports an `interrupted` error and never sends the input again on its own. `joinStream()` joins a run of the current thread by ID without starting a new one, which prevents duplicate work.

```typescript
// Join a run of this thread after a network interruption or a reload
await this.agent.joinStream(runId, lastEventId);
// Continues after lastEventId; no second agent execution
```

`joinStream()` is a LangGraph command, so the agent has to be typed with `LangGraphSession`. Without `lastEventId` the run is joined from its first event, which the backend serves only for a resumable stream.

<Callout type="info" title="Recovery without a run ID">
In most cases you do not need a run ID. When a stream closes without a final state, the session reads the thread once to settle the turn. If the outcome is still unknown, `error()` carries `recovery: 'check'` and `agent.checkStatus()` reads the thread again without sending anything. `agent.reconnect()` rejoins the run the session itself still holds, named by `retainedRun()`. Use `joinStream()` when the ID comes from somewhere else, for example a URL parameter after a full page reload.
</Callout>

## Thread lifecycle

<Steps>
<Step title="Agent is created">
The agent reads the configured `threadId` and asks `createSession` for a session. If there is a thread, its checkpoint history is read from the server and `isThreadLoading()` is true meanwhile.
</Step>
<Step title="User sends first message">
If there is no thread yet, the session creates one through the LangGraph API before the run starts, and `onThreadId` is called with the new ID.
</Step>
<Step title="Agent streams response">
Each super-step is checkpointed server-side. The `messages()` signal updates in real time as events arrive.
</Step>
<Step title="User switches threads">
Setting the `threadId` signal (or calling `switchThread()`, as the example does) stops and disposes the old session, creates one for the target thread, and loads its latest checkpoint. All signals update to reflect the restored state.
</Step>
<Step title="Connection drops">
The run settles as `interrupted`. `checkStatus()` reads what the server saved, and `reconnect()` or `joinStream()` joins a run that is still in progress. The graph does not run a second time.
</Step>
</Steps>

## Where threads and checkpoints live

In your backend's persistence layer. Threadplane exposes thread, history, and resume behavior in the UI; durability comes from the runtime you operate.


## Wiring a thread list

The example keeps its own list of the threads it created. A real application lists the conversations the deployment has saved. `provideThreadDirectory()` and `injectThreadDirectory()`, from `@threadplane/angular`, give a component tree one view of a thread directory, and `createLangGraphThreadDirectory()`, from `@threadplane/langgraph`, builds the directory over the LangGraph Threads API.

`<chat-thread-list>` renders the rows; the application owns the active-thread signal. That signal is the same one handed to `provideAgent({ threadId })`, which is what makes selecting a row switch the conversation: the agent follows the signal, replaces its session, and reads that thread's server-side history.

```ts
import { Component, signal } from '@angular/core';
import {
  injectAgent,
  injectThreadDirectory,
  provideAgent,
  provideThreadDirectory,
  refreshOnRunEnd,
} from '@threadplane/angular';
import { ChatThreadListComponent, type ThreadActionAdapter } from '@threadplane/angular/chat/threads';
import {
  createLangGraphThreadDirectory,
  createSession,
  type LangGraphThreadDirectory,
} from '@threadplane/langgraph';

const apiUrl = 'http://localhost:2024';

/** Source of truth for the active thread. Module scope, because the
 *  `provideAgent()` config below has to close over it. */
const activeThreadIdState = signal<string | null>(null);

@Component({
  selector: 'app-threads-panel',
  imports: [ChatThreadListComponent],
  providers: [
    provideThreadDirectory({
      createDirectory: (context) =>
        createLangGraphThreadDirectory({ ...context, apiUrl }),
    }),
    provideAgent({
      threadId: activeThreadIdState,
      onThreadId: (id) => activeThreadIdState.set(id),
      createSession: (context) =>
        createSession({
          ...context,
          apiUrl,
          assistantId: 'agent',
        }),
    }),
  ],
  template: `
    <chat-thread-list
      [threads]="threads.threads()"
      [activeThreadId]="activeThreadId() ?? ''"
      [actions]="actions"
      [showNewThreadButton]="true"
      (threadSelected)="onThreadSelected($event)"
      (newThreadRequested)="onNewThread()"
    />
  `,
})
export class ThreadsPanel {
  protected readonly agent = injectAgent();
  protected readonly threads = injectThreadDirectory<LangGraphThreadDirectory>();
  protected readonly activeThreadId = activeThreadIdState;

  protected readonly actions: ThreadActionAdapter = {
    rename: this.threads.rename,
    pin: this.threads.pin,
    unpin: this.threads.unpin,
    archive: async (id) => {
      await this.threads.archive(id);
      if (activeThreadIdState() === id) activeThreadIdState.set(null);
    },
    delete: async (id) => {
      await this.threads.delete(id);
      if (activeThreadIdState() === id) activeThreadIdState.set(null);
    },
  };

  constructor() {
    void this.threads.refresh();
    refreshOnRunEnd(this.agent, this.threads);
  }

  protected onThreadSelected(id: string): void {
    activeThreadIdState.set(id);
  }

  protected async onNewThread(): Promise<void> {
    const id = await this.threads.create();
    if (id) activeThreadIdState.set(id);
  }
}
```

The example scopes both the directory and the agent to the panel. To share one thread list across the app, call `provideThreadDirectory()` at the application root instead.

Four details in that component are easy to get wrong:

- `activeThreadId` is `input<string>('')`, not a nullable input, so a `null` active thread has to become `''`. Passing `null` is a template type error.
- The selection output is `threadSelected`, and `<chat>` re-emits an output of the same name, so either surface can drive the switch.
- `injectThreadDirectory<LangGraphThreadDirectory>()` names the directory's type, so `create`, `archive` and the rest are typed as present and are called directly. Without the type argument the view is typed by the core directory contract, where every command is optional and a command the directory does not offer is `undefined`; the list then offers no menu entry for it.
- Nothing is loaded until `refresh()` is called. A failed load is published through `threads.status()` and `threads.error()`; the promise does not reject.

An application that does not bind a `threadId` signal can call `agent.switchThread(id)` from the same handler instead, and read the current thread back from `agent.threadId()`. Binding the signal is the better default, because it also suits a config factory that reads the ID from the router.

<Callout type="info" title="Which menu entries appear">
`<chat-thread-list>` builds its row menu from the keys the adapter actually defines, and from `[mode]`. A list in the default `active` mode offers Rename, Pin or Unpin, Move up and Move down for a pinned row with `reorderPinned`, Move to project when `[projects]` is bound, Archive, and Delete. A list rendered with `[mode]="'archived'"`, the natural home for `archivedThreads()`, offers only Unarchive and Delete.
</Callout>

## Keeping the list fresh

The directory does not watch the server, so something has to read the list again. `refreshOnRunEnd()` fires on every transition out of the `'running'` status, which is precisely when a title-writing node has finished, and it keeps following the agent across thread switches. Pass it the directory view, or a function:

```ts
refreshOnRunEnd(this.agent, this.threads);
```

`refreshOnTransition(watch, isActive, fn)` is the generic form for any other signal that has an active state: it calls `fn` whenever `isActive(watch())` goes from `true` to `false`.

Both helpers use an Angular `effect()` under the hood, so both must be called from an injection context: a constructor body or a field initializer. `refresh()` itself is a plain asynchronous call with no such requirement. A rename, pin, archive or delete shows in the list at once and rolls back if the request fails, so those need no refresh of their own.

## Shared SDK client

Pass `client` to `createLangGraphThreadDirectory()` to hand the directory an SDK `Client` you already own, or a test double; without it the directory builds its own client from `apiUrl`. Call `provideAgentClientOptions()` once at the application root to set the auth headers and SDK retry budget for every agent below it. The options arrive in both factories as `context.clientOptions`, together with the operation-failure reporter, and spreading the context forwards both:

```ts
import { provideAgentClientOptions } from '@threadplane/angular';
import { createLangGraphThreadDirectory } from '@threadplane/langgraph';

providers: [
  provideAgentClientOptions({ defaultHeaders: { 'x-tenant': 'acme' } }),
  provideThreadDirectory({
    createDirectory: (context) =>
      createLangGraphThreadDirectory({ ...context, apiUrl }),
  }),
];
```

<Callout type="warning" title="Thread ids come from the server">
Use a confirmed backend thread ID: the value `create()` resolves, the one handed to `onThreadId`, or one returned by the Threads API. A caller can request a UUID during thread creation, but must confirm the returned identity before using it for a run. Generating an ID alone creates no backend thread.
</Callout>
