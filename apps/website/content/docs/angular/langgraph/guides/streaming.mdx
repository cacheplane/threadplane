# Streaming

<DocsDemoVideo demo="streaming" frontend="angular" />

Streaming lets a traveler begin reading an itinerary before the backend finishes the answer. Instead of waiting for one final response body, the browser receives a sequence of Server-Sent Events (SSE). The LangGraph session turns those events into snapshots, the injected agent exposes each snapshot field as an Angular Signal, and the UI renders each meaningful update.

Start with the [learning workbench](/docs/angular/getting-started/workbench) to follow one turn, inspect partial text and completion, and connect each observation to source. This page keeps the full streaming example in **Run**, **Code**, and **API**.

<Callout type="tip" title="Prerequisites">
Make sure you have completed the Installation guide first.
</Callout>

## One response, many updates

A user turn starts with an intention such as “Plan a weekend in Portland.” The backend may make several model calls or execute tools while answering it. Streaming describes how the browser observes that work; it does not mean there is one HTTP request per token.

<TurnSequence />

The draft, the answer, and the run status have different lifetimes. Clear the accepted draft when submitting, append or update messages as events arrive, and keep the run busy until its completion is known. A pause for approval or an interrupted connection needs its own UI state. [Follow a conversation](/docs/angular/langgraph/concepts/conversation-turns) introduces those boundaries before tools and persistence enter the picture.

## What the demo does

The Run tab hosts one agent and the prebuilt `<chat>` composition. Send a message and the answer fills in token by token while the typing indicator runs. The composition owns message rendering, the input, and error display, so the demo component adds little: a New conversation button, the two suggestions, and a recorder that reports each submission and state change to the page that hosts the demo.

Two welcome suggestions are wired up. "Stream a long answer" asks for a 200-word explanation of LangGraph checkpointing, which is long enough to watch the tokens land one at a time. "How agents pick tools" asks the agent to explain tool selection, and the [chat-tool-calls component guide](/docs/angular/chat/components/chat-tool-calls) covers how those calls are rendered.

## How it is built

Three files carry the visible integration: the graph that streams, the provider that points Angular at it, and the component that renders it. A fourth, small file declares the typed agent ref they share. Open the Code tab to read the three in place.

### The streaming graph

The backend is a single node. `MessagesState` gives the LangGraph SDK a message list it already understands, the model is constructed with `streaming=True`, and the node prepends a system prompt read from the capability's prompt file before it awaits the model. The compiled graph is exported as `graph`, which is the symbol `langgraph.json` points at.

<ExampleCode file="graph.py" />

The node awaits a single `ainvoke` call. `streaming=True` is what lets the model emit tokens through LangGraph's callbacks, and which of those reach the browser is decided by the stream modes the client asks for.

### The agent provider

`provideAgent()` from `@threadplane/angular` registers the agent once for the whole application, keyed by the typed ref declared in `agent-ref.ts`. The ref itself is one line, typed by the session the provider creates:

```typescript
import { createAgentRef } from '@threadplane/angular';
import type { LangGraphSession } from '@threadplane/langgraph';

export const STREAMING_AGENT = createAgentRef<LangGraphSession>('streaming');
```

The streaming graph is a plain `MessagesState`, so its messages are `agent.messages()` and there is no other state to describe.

The provider's config supplies `createSession`, a function that builds a session with `createSession()` from `@threadplane/langgraph`. The agent calls it once at start and again for each thread switch. The example resolves its connection details at runtime from the host that serves the demo, which is why it wraps the config in a factory that reads them rather than hard-coding them. It is the only provider this example needs.

<ExampleCode file="app.config.ts" />

Your own application does not need the outer factory. Pass the two connection values directly, and forward the thread the agent hands you:

```typescript
provideAgent(STREAMING_AGENT, {
  createSession: (context) =>
    createSession({
      ...context,
      apiUrl: 'https://your-deployment.langgraph.app',
      assistantId: 'streaming',
    }),
}),
```

`assistantId` must match the graph name in `langgraph.json`.

<Callout type="warning" title="Keep the API key on the server">
Never expose a LangSmith API key in client-side code. Point `apiUrl` at a deployment that authenticates the browser another way, or proxy the requests through your own server and attach the key there.
</Callout>

### The chat component

`injectAgent(STREAMING_AGENT)` returns the agent registered above, typed by that ref: the session's snapshot fields as signals, plus its commands. The component hands it to `<chat>`, renders the two welcome suggestions and forwards the selected one into `submit()`. The New conversation button calls `switchThread(null)`, which moves the agent to a new, empty thread.

<ExampleCode file="streaming.component.ts" />

The demo does not pass the injected agent to `<chat>` directly. It passes a view of it whose `submit` records the call for the host page's inspector and then calls the real `submit`, so a typed message and a clicked suggestion cross the same boundary. The view is a `Proxy` rather than a spread copy because the agent reads each member from its current session at the moment it is asked. Your own component can bind `[agent]` to the injected agent as it is.

`submit({ message })` opens the stream, and every signal the composition reads updates as chunks arrive. There is no service layer to write: the session owns the connection, the state, and error recovery, and the agent owns the session.

<Callout type="info" title="Injection context">
`injectAgent()` must run inside an Angular injection context: a field initializer, as it is here, or a constructor body.
</Callout>

## Stream status

The `status()` signal reports where the current run stands. It has three values:

<Steps>
<Step title="idle">
No active stream. The agent is ready to accept a new message.
</Step>
<Step title="running">
The run is active. It may be waiting for the first token, generating text, or executing a tool; signal values update as events arrive.
</Step>
<Step title="error">
The connection was interrupted or the run failed. Inspect `error()` for the kind of failure, the display text, and the recovery the session can offer.
</Step>
</Steps>

## Stream modes

On the server, `astream()` decides what a run emits, and `astream_events()` adds raw run events. The three modes you will meet most often:

```python
async def main():
    # "values" — full state snapshot after each node
    async for chunk in graph.astream({"messages": [("user", "Hello")]}, stream_mode="values"):
        print(chunk)

    # "messages" — individual message tokens as they are generated
    async for chunk in graph.astream({"messages": [("user", "Hello")]}, stream_mode="messages"):
        print(chunk)

    # "events" — raw run events (on_chain_start, on_llm_stream, etc.)
    async for event in graph.astream_events({"messages": [("user", "Hello")]}, version="v2"):
        print(event["event"], event.get("data"))
```

The client asks for `messages-tuple` to receive the token tuples that `stream_mode="messages"` produces on the server; `messages` is a separate client mode, so the lists below name `messages-tuple`.

You rarely call those directly from an Angular app. On its own transport, the session asks the LangGraph API for the stream modes it needs to fill the snapshot: `values`, `messages-tuple`, `updates`, `custom`, and `checkpoints`. The transport also enables `streamSubgraphs` unless a run sets it, so namespaced subgraph events can reach the client.

A run can add modes; it cannot remove the ones the session needs. Per-run LangGraph settings are grouped under `run` in the submit options, so `streamMode` is a submit option, not a `createSession()` option, and a `streamMode` at the root of the options is never read.

<Tabs>
<Tab label="tool progress">

```typescript
// Adds the `tools` mode, which the session does not request by default
// because older servers reject it. Running tools then report progress.
const agent = injectAgent(STREAMING_AGENT);

await agent.submit(
  { message: 'Look up the weather in Portland.' },
  { run: { streamMode: ['tools'] } },
);

// agent.toolProgress() lists one entry for each tool of the current run
```

</Tab>
<Tab label="custom events">

```typescript
// The `custom` mode is always requested, so nothing is added here.
const agent = injectAgent(STREAMING_AGENT);

// Everything the current run has emitted so far, oldest first.
const progress = computed(() => agent.customEvents());

// Or receive each event as it arrives. Call the returned function to stop.
const release = agent.onCustomEvent((event) => {
  console.log(event.name, event.data);
});
```

</Tab>
<Tab label="without subgraphs">

```typescript
// Sends `streamSubgraphs: false` with one run's request, in place of the
// transport default, for a turn where child graph events are not needed.
const agent = injectAgent(STREAMING_AGENT);

await agent.submit(
  { message: 'Summarize this thread.' },
  { run: { streamSubgraphs: false } },
);
```

</Tab>
</Tabs>

<Callout type="info" title="Choosing a mode">
Use the default modes for most chat UIs. They keep `messages()`, `state()`, `toolCalls()`, `customEvents()`, and `subagents()` populated from the same run. Add a mode only for a signal that needs it, such as `tools` for `toolProgress()`.
</Callout>

## Error handling

If the SSE connection drops or the run fails, `status()` flips to `'error'` and `error()` is populated. The prebuilt `<chat>` composition renders the failure for you; a hand-built UI reads the same two signals.

<Tabs>
<Tab label="chat.component.ts">

```typescript
import { computed } from '@angular/core';
import { injectAgent } from '@threadplane/angular';
import { STREAMING_AGENT } from './agent-ref';

export class ChatComponent {
  protected readonly agent = injectAgent(STREAMING_AGENT);

  readonly hasError = computed(() => this.agent.status() === 'error');

  // The session offers a check when it can read the thread's history.
  readonly canCheck = computed(
    () => this.agent.error()?.recovery === 'check' && this.agent.checkStatus !== undefined,
  );

  // It offers a retry only for a run the backend reported as failed.
  readonly canRetry = computed(
    () => this.agent.error()?.recovery === 'retry' && this.agent.retry !== undefined,
  );

  retry() {
    // Sends the failed command again on the same thread
    void this.agent.retry?.();
  }

  checkStatus() {
    // Read-only: asks the backend what happened, resubmits nothing
    void this.agent.checkStatus?.();
  }
}
```

</Tab>
<Tab label="chat.component.html">

```html
@if (hasError()) {
  <div class="error-banner">
    <p>{{ agent.error()?.message }}</p>
    @if (agent.error()?.detail; as detail) {
      <p>{{ detail }}</p>
    }
    @if (canCheck()) {
      <button (click)="checkStatus()">Check status</button>
    } @else if (canRetry()) {
      <button (click)="retry()">Retry</button>
    }
  </div>
}
```

</Tab>
</Tabs>

`retry()` and `checkStatus()` are optional commands, which is why the component asks whether each exists. `retry()` sends the failed command again and resolves with the outcome of the new run. It applies only to an error whose `recovery` is `'retry'`: a run the backend itself reported as failed, or a first submission whose thread could not be created. It resolves `'aborted'` without sending while a request is active and when nothing failed, and it rejects for any other error. `checkStatus()` is read-only: it asks the backend what happened to the run and settles the turn without resubmitting anything. `submit(null)` starts a run with no input, so the graph continues from the thread's saved state and no user message is added. Pass `submit({ message })` only when you have new input to send.

<Callout type="warning" title="Network errors vs agent errors">
`error()` returns an `AgentError` from `@threadplane/core`. It is a plain frozen object, not an `Error` instance, so read its fields rather than testing `instanceof`. `kind` distinguishes the failure class (`'connection'`, `'auth'`, `'server'`, `'interrupted'`, or `'aborted'`), `status` carries the HTTP status code when the failure came from an HTTP response, `retryable` and `recovery` say what the session can safely offer, and `message` and `detail` are the display text. The error does not carry the raw cause: `errorDiagnostic()` describes what it was classified from, when the session kept that. A stream that closed without a terminal event may have left a run that carried on and committed work on the server, so the session never marks one retryable. `recovery` is `check` when the transport can read thread history, and `checkStatus()` then re-reads it to settle the turn without resubmitting anything; otherwise it is `none`, and the message says the outcome could not be confirmed.
</Callout>

## Throttle configuration

By default the session delivers every change as it arrives, and the agent's signals follow. `throttle` sets the least time, in milliseconds, between two deliveries while a run streams, which keeps a fast SSE stream from triggering hundreds of renders per second. It is a `createSession()` option.

```typescript
// app.config.ts
provideAgent(STREAMING_AGENT, {
  createSession: (context) =>
    createSession({
      ...context,
      apiUrl: '...',
      assistantId: 'streaming',
      // Deliver changes to the signals at most once every 50 ms
      throttle: 50,
    }),
});
```

The value is in milliseconds. Omit it, or pass `false` or `0`, to deliver every change at once. Throttling never drops the end of a run: the last change is always delivered, and a change that ends the run is delivered immediately.

For me, leaving it off is the right starting point, and 16 ms, close to a 60 fps render cadence, is the first value to try. The tradeoff of raising it is straightforward: a larger window costs you a touch of perceived latency to save renders, so only reach for it when profiling shows streamed updates are the bottleneck.

| Use case | Recommended throttle |
|---|---|
| Token-by-token typing effect | off, or 16 ms |
| Standard chat bubble | 16 ms or 50 ms |
| Background summarisation | 150 ms |

<Callout type="tip" title="SSE connection behavior">
Each call to `agent.submit()` opens a new SSE connection. Connections close when the run completes or the injector that owns the provider is destroyed, because the agent disposes its session with that injector. A component-scoped provider follows that component; an application-root provider remains alive when a consuming component unmounts. Choose the provider scope to match the intended conversation lifetime.
</Callout>
