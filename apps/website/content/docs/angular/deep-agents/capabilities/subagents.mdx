# Subagents

Angular is the default example on this guide. Choose React in **Framework** for native parent task cards and separate current-session child observations. Both frontends share the same Python graph, prompt and runtime. The cards and the sidebar described below are the Angular example's.

Delegation in Deep Agents is one tool. `SubAgentMiddleware` registers a tool named `task` taking `{ description, subagent_type }`, and each call runs a real child graph with its own system prompt, its own tools, and its own transcript. Nothing about that is special on the wire — it is an ordinary tool call — and yet the browser renders it as a child agent, because `task` is the tool name the session already treats as starting a child. The running example is an aviation dispatch desk, and this page walks the three files behind it.

## What the Angular demo does

The Angular Run tab shows the prebuilt `<chat>` composition beside a specialist roster and live dispatch count. The first suggestion requests field data and weather for KASE and KDEN; the second asks for field data at KSFO. The prompt requests parallel tasks with one airport per dispatch. Actual model behavior determines the number and type of calls; four calls, mandatory delegation and exclusive use of the two named specialists are not guaranteed. The graph can respond without a task call, use generic tools or dispatch to general-purpose. All airport and weather lookups use fixed sample tables.

Three files carry the capability: a Python graph holding the lookup tools, the specialist specs, and the agent; an application config; and the Angular component that reads the dispatches into a sidebar. Open the Code tab to read them in place.

### Declaring a specialist

A `SubAgent` is a `TypedDict` with three required fields and a handful of optional ones. `name` is what the orchestrator passes as `subagent_type`, `description` is what the orchestrator reads when it decides where to send work, and `system_prompt` governs the child once it starts. Handing each spec its own `tools` is what splits the two jobs apart.

Omitting `tools` would inherit the main agent's tools instead, which is the opposite of what this demo wants.

### Installing the task tool

`create_deep_agent` assembles a middleware stack, and `SubAgentMiddleware` is already on it: the factory adds a `general-purpose` subagent unless that one is explicitly disabled, so the `task` tool ships by default. Passing `subagents` is what puts your own specialists on that tool. The demo passes no custom lookup tools to the orchestrator; middleware can still supply generic tools, and a model response need not delegate.

### Asking for the dispatches in one turn

The middleware supplies a tool, not a policy. A model may dispatch sequentially or in parallel. Two paragraphs in `prompts/subagents.md` request parallel work; they do not guarantee its shape or call count.

```markdown
Give each dispatch a `description` that names the airport and says exactly what
you want back. One airport per dispatch — never ask a specialist to cover two.

When a request covers more than one airport or more than one kind of data,
issue every dispatch you need **in a single turn** so the specialists work in
parallel. Do not wait for one to report before sending the next.
```

Both halves matter, and the first one matters for a reason worth reading the next section for.

### Providing the Angular agent

`provideAgent()` from `@threadplane/angular` registers the agent at the application root, and it is the only provider the `<chat>` composition requires. Its `createSession` function calls `createSession()` from `@threadplane/langgraph`. `subagentToolNames: ['task']` is already that session's default, so the line changes nothing at runtime and is there to say which tool call means that a child started. The example resolves its connection at runtime because the host that serves the demo decides which runtime is attached; your own application passes `apiUrl` and `assistantId` to `createSession()` directly.

### Reading Angular dispatches

`injectAgent()` returns the agent, and `agent.subagents()` is a signal holding a plain list of the child agents the current run reported, in start order. A child the session related to a `task` call carries that call's id as `toolCallId`. The sidebar filters the list down to those once and derives both numbers from the result, so the two counts can never disagree.

Each entry is plain data, so `status` is read as a property: `running` while the child works, then `complete` or `error` once its `task` call has a result.

## How an Angular dispatch becomes a card

Two independent things have to happen for a `task` call to render as a child agent, and they come from opposite ends of the run.

The first is the dispatch. When the orchestrator's message carries a `task` tool call, the session counts it as a delegation, reading `subagent_type` and `description` out of the arguments. That type becomes the card's label, and a call with no usable `subagent_type` is not counted. The relation is also what makes the card its own thing in the transcript: `<chat-tool-calls>` groups adjacent calls of the same name into one collapsed strip, but a call that started a child is always its own group, so four `task` calls in one turn stay four cards instead of collapsing into a single grouped strip. A child is listed in `subagents()` only once its child graph reports, because LangGraph names a child by a namespace that exists only once the child runs, so those four calls briefly render as one grouped tool-call strip before their cards appear.

The second is attribution: deciding which child stream belongs to which dispatch. This is the part that is not free. A child runs under a `tools:<id>` namespace whose id is a checkpoint identifier assigned independently of the parent's tool-call id, and the two are not linked anywhere on the wire. So the session matches on content instead. `SubAgentMiddleware` seeds each child with a single human message whose content is the dispatch `description`, verbatim, and the session matches that first message against the `description` argument of each unrelated dispatch — exactly first, then by containment either way.

<Callout type="warning" title="Why the prompt insists on one airport per dispatch">
The deepagents `task` tool cannot announce its binding, so inside this graph the description is the only signal that survives fan-out; a graph that announces its children through the [Threadplane middleware](/docs/angular/langgraph/guides/subgraphs) gets an exact binding instead. With one dispatch outstanding the session can fall back to claiming that single unrelated dispatch, but with four outstanding at once there is nothing positional to fall back on: arrival order is not dispatch order, and guessing would put one specialist's transcript in another specialist's card. Descriptions that name their airport keep the four apart. Two dispatches whose descriptions are identical give the ladder nothing to tell them apart: the exact rung claims the first unrelated dispatch, so a child can land on its sibling's card.
</Callout>

A child the session has not related yet is still listed in `subagents()`, with its own messages and no `toolCallId`, and a relation never changes once it is made. The sidebar's filter leaves an unrelated child out of both counts. Description matching is a heuristic and can misattribute children, particularly when descriptions are identical. The native React preview presents its child observations separately from the parent task cards.

<Callout type="tip" title="The description is doing two jobs">
A dispatch `description` is both the child's opening instruction and the key the session attributes its output by. A vague description costs twice: the child starts with less to go on, and its stream is harder to tell from its siblings.
</Callout>
