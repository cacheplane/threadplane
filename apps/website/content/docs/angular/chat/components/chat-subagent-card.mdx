# ChatSubagentCardComponent

`ChatSubagentCardComponent` renders one delegated subagent as an expandable card: its name, a status pill, a message count, and — once expanded — the subagent's own transcript. The running example is a trip planner whose orchestrator delegates research, booking, and itinerary work to a child graph, and this page walks the files that make each dispatch show up as a card.

**Selector:** `chat-subagent-card`

**Import:**

```typescript
import { ChatSubagentCardComponent } from '@threadplane/chat';
```

## What the demo does

The Run tab shows the prebuilt `<chat>` composition beside a sidebar that lists the pipeline: orchestrator, then a research subagent, a booking subagent, and an itinerary subagent. One welcome suggestion, "Plan a trip from LAX to JFK", starts the run.

Send it and the orchestrator calls one `task` tool three times, in that order. Each call renders in the transcript as a subagent card rather than as a generic tool-call chip. A card opens while its subagent is running, streams that subagent's answer inside itself, and collapses to a one-line summary when the dispatch completes. The cards stay in the transcript afterwards, so the finished run reads as three collapsed dispatches followed by the orchestrator's own summary of the trip.

## How it is built

A child graph the orchestrator can invoke, a `task` tool that invokes it, one session option that says `task` means delegation, a helper that binds the child stream to its tool call, the orchestrator's own tool-calling loop, and a component that renders the standard `<chat>` composition carry the feature together. Open the Code tab to read them in place.

### The subagent subgraph

Each specialist is the same compiled child graph, parameterized by a `subagent_type` that selects its system prompt. The child keeps its own state schema, so the task description arrives as a field rather than as a chat message.

<ExampleCode file="graph.py" region="subagent-graph" title="graph.py — the child graph" />

Invoking that compiled graph from inside a tool is what makes LangGraph nest its run under a `tools:<id>` namespace, and everything the card shows comes from that namespaced stream.

### The task tool

The tool is an ordinary LangChain tool. It takes the specialist to dispatch and a plain-English description of the work, invokes the child graph, and returns the child's final text to the orchestrator.

<ExampleCode file="graph.py" region="task-tool" title="graph.py — the delegation tool" />

`subagent_type` is a `Literal`, which matters twice: it constrains what the model may dispatch, and it becomes the card's label.

### Binding the child stream to its tool call

Nothing on the wire links the child's `tools:<uuid>` namespace to the parent's `call_*` tool-call id — the uuid is a checkpoint id assigned independently. Inside the tool body both halves are known, so the example emits them together as one custom event.

<ExampleCode file="graph.py" region="announce" title="graph.py — announcing the binding" />

The LangGraph session reads that `threadplane.subagent_binding` event to relate the child graph to the tool call that started it.

<Callout type="info" title="The binding is authoritative, the fallback is a heuristic">
Without the announcement the session falls back in order: it matches the child's first message against the `description` of one unrelated call, and failing that relates the child only when exactly one unrelated call is still pending or running. With several calls outstanding and nothing to tell them apart, a child stays unrelated. Announcing the binding is what makes parallel fan-out safe. The canonical helper is `threadplane.middleware.langgraph.announce_subagent`; the example inlines it because each example stands alone.
</Callout>

### The orchestrator

The parent is a plain tool-calling loop: a model bound to the single `task` tool, a `ToolNode` that runs it, and a conditional edge back to the model until no tool calls remain.

<ExampleCode file="graph.py" region="orchestrator" title="graph.py — the parent graph" />

The system prompt tells the orchestrator to dispatch research, then booking, then itinerary, which is why the demo produces three cards in a stable order.

### Telling the session that task means delegation

`provideAgent()` from `@threadplane/angular` provides the agent once for the whole application, and it is the only provider the `<chat>` composition requires. The one subagent-specific line is the `subagentToolNames` option of `createSession()`. The default is already `['task']`, so this example states explicitly what it would otherwise inherit.

The example resolves its connection details at runtime from the host that serves the demo, which is why the config is itself a factory that reads them rather than hard-coding them; your own application passes `apiUrl` and `assistantId` to `createSession()` directly.

<ExampleCode file="app.config.ts" />

A tool call counts as a delegation only when its name is in `subagentToolNames` and its arguments carry a plausible `subagent_type`; that argument then becomes the child's `name`, and the call's task becomes its `description`.

### Where the card appears

The component is small on purpose. It renders `<chat>`, a welcome suggestion, and a static sidebar note — and nothing about subagents at all. Subagent cards appear because `<chat-tool-calls>`, inside the `<chat>` composition, cross-references each tool call against `agent.subagents()` by `toolCallId`: a call that started a child agent renders as a standalone `<chat-subagent-card>` instead of a tool-call card, and never groups with adjacent calls.

That cross-reference works because the agent the demo injects publishes the session's `subagents()` for `<chat-tool-calls>` to read.

## Basic usage

Rendering a card directly needs only the subagent:

```html
<chat-subagent-card [subagent]="subagentRef" />
```

## API

### Inputs

| Input | Type | Default | Description |
|-------|------|---------|-------------|
| `subagent` | `AgentSubagent` | **Required** | The child agent to display |
| `toolLabel` | `(name: string) => string \| undefined` | `undefined` | Readable labels for the subagent's own tool calls. `<chat>` and `<chat-tool-calls>` pass their `toolLabel` through. A labelled call shows its technical name inside the opened call |
| `toolOutcome` | `(activity: ToolActivityInfo) => ToolActivityOutcome \| undefined` | `undefined` | Outcomes for the subagent's own completed calls. `<chat>` and `<chat-tool-calls>` pass their `toolOutcome` through. Sources an outcome declares are listed in the Sources panel of the message that started the subagent |

The component exposes no outputs.

## AgentSubagent

The `AgentSubagent` type is defined by `@threadplane/core` and re-exported by `@threadplane/chat`. It is plain, frozen data, not a set of signals: `agent.subagents()` publishes a new list when a child changes.

| Property | Type | Description |
|----------|------|-------------|
| `id` | `string` | Stable for the life of the session |
| `name` | `string \| undefined` | Optional human-readable name. The card falls back to the literal `Subagent` when it is absent |
| `description` | `string \| undefined` | The task the child was given, in the root agent's words |
| `toolCallId` | `string \| undefined` | The root tool call that started this child, when the backend relates the two |
| `parentId` | `string \| undefined` | The `id` of the child that started this one; absent for a child of the root agent |
| `status` | `'pending' \| 'running' \| 'complete' \| 'error' \| 'unknown'` | Where the child stands |
| `messages` | `readonly Message[]` | Messages produced by the child. They are not repeated in the root transcript |
| `toolCalls` | `readonly ToolCall[]` | The child's own tool calls, referenced by each message's `toolCallIds` |
| `streamingToolCalls` | `readonly StreamingToolCall[] \| undefined` | The child's tool calls whose arguments are still streaming, when the session shows them |
| `state` | `Readonly<Record<string, PlainValue>> \| undefined` | The child's own state, when the backend reports one |
| `error` | `string \| undefined` | Display text for the failure when `status` is `'error'` |

In the running example `name` is the `subagent_type` argument (`research`, `booking`, `itinerary`), `description` is the task the orchestrator wrote, and `state` is the child graph's state.

<Callout type="info" title="A dispatch becomes visible when its child stream starts">
The LangGraph session never reports `pending`: LangGraph names a child by a namespace that exists only once the child runs. A child appears as `running` when its stream starts, and turns `complete` (or `error`) when the tool call that started it has a result. `unknown` means the child started, no ending was seen, and no run is active that could still report one.
</Callout>

## What the card renders

### Header

The header is the `<chat-trace>` toggle button. It shows a chevron reflecting the expanded state, the `name` (or the literal `Subagent`), a color-coded status pill, and the message count ("1 message", "3 messages"). The spawning call's ID is not shown.

### Expansion

Expansion is delegated to [`<chat-trace>`](/docs/angular/chat/components/chat-trace): the card expands automatically while the status is `running` or `error`, and otherwise stays collapsed. Clicking the header sets a manual override that wins from then on. Re-entering `running` or `error` from another state clears that override, so a card that is dispatched again opens again.

### Transcript

When expanded, the card renders the subagent's entire message list, not just the latest message. For each message, in order:

- Any `reasoning` text, as a muted italic line
- The message content, rendered through `<chat-streaming-md>` so it streams as markdown
- A [`<chat-tool-call-card>`](/docs/angular/chat/components/chat-tool-call-card) for each tool call the message references and the child's `toolCalls` list holds

### Status pill colors

The pill reads **Pending**, **Running**, **Complete**, **Failed** or **Status unavailable**. It is styled through a `data-status` attribute that keeps the raw status value, and CSS selectors. The exported `statusColor()` helper returns the equivalent inline style string and is retained for existing consumers.

| Status | Background | Text color |
|--------|-----------|------------|
| `pending` | `--tplane-chat-surface-alt` | `--tplane-chat-text-muted` |
| `running` | `--tplane-chat-warning-bg` | `--tplane-chat-warning-text` |
| `complete` | (none) | `--tplane-chat-success-text` |
| `error` | `--tplane-chat-error-bg` | `--tplane-chat-error-text` |
| `unknown` | `--tplane-chat-surface-alt` | `--tplane-chat-text-muted` |

## Cards outside the transcript

The example needs no explicit markup because the `<chat>` composition places each card inline. To render cards somewhere else — a sidebar tray, for instance — use the `ChatSubagentsComponent` primitive, which iterates `agent.subagents()` and drops the ones that already reached `complete` or `error`:

```html
<chat-subagents [agent]="agent">
  <ng-template let-subagent>
    <chat-subagent-card [subagent]="subagent" />
  </ng-template>
</chat-subagents>
```

The template is optional. Without one, `<chat-subagents>` renders a `<chat-subagent-card>` for each active subagent itself.

## Styling

The card reads these CSS custom properties:

| Variable | Applied to |
|----------|-----------|
| `--tplane-chat-text` | Subagent name |
| `--tplane-chat-text-muted` | Tool call id, message count, reasoning line, `pending` pill text |
| `--tplane-chat-font-mono` | Tool call id |
| `--tplane-chat-separator` | Divider between successive transcript messages |
| `--tplane-chat-surface-alt` | `pending` pill background |
| `--tplane-chat-warning-bg` / `--tplane-chat-warning-text` | `running` status pill |
| `--tplane-chat-success-text` | `complete` status pill |
| `--tplane-chat-error-bg` / `--tplane-chat-error-text` | `error` status pill |

The card draws no background, border, or radius of its own. The only border anywhere in this pairing is the left rule on the expanded body, drawn by [`<chat-trace>`](/docs/angular/chat/components/chat-trace); any surrounding chrome comes from the host that places the card.

## Accessibility

The header is a real `<button>` and exposes `aria-expanded` reflecting the current state, so the card is operable from the keyboard and announced as a disclosure.
