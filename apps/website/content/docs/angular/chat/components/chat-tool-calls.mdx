# ChatToolCallsComponent

`ChatToolCallsComponent` renders readable tool activity in a compact, initially collapsed row. Technical names, call IDs, arguments, results and errors remain available in **Details**. Adjacent built-in calls group across names by default; custom templates and subagent cards retain their own boundaries. The aviation example mounts this component in the conversation and in a sidebar.

**Selector:** `chat-tool-calls`

## Show the work behind an answer

A traveler may see several lookups before receiving an itinerary. Each lookup has an identity, a name, arguments, and eventually a result or error. Keep that structured information with the assistant message that requested it so two calls to the same tool remain distinguishable.

`ChatToolCallsComponent` observes and presents calls. The backend or client-tool coordinator executes them. A card becoming visible does not itself run the tool. See [Client tools](/docs/angular/chat/guides/client-tools) when your application needs to implement the requested capability.

## What the demo does

The Run tab shows a conversation on the left and a sidebar headed "Tool Calls" on the right, with an "Available Tools" list below it naming the three aviation tools the agent can call. One welcome suggestion, "Check a flight status", asks for the status of flight UA123.

The agent answers by calling `lookup_flight`. The sidebar and transcript show “Looking up flight information,” its explicit status, and a validated flight status/gate preview when the result arrives. Open **Details** to inspect the technical name, arguments and full flight record. A malformed aviation record does not receive a successful result preview. Ask for flight UA999, which is not in the dataset, and the call shows as failed with the tool's own message.

Grouping is easier to see with a second request. Ask the assistant to compare LAX and JFK: two airport lookups can share a compact activity strip. Confirmed airport summaries remain outside the technical disclosure; expand the strip to inspect each distinct call. Concise counts distinguish completed, running and failed activities in a mixed group.

## How it is built

Three files carry the example: the graph that binds the tools and loops until the model stops calling them, the provider that points Angular at that graph, and the component that places the panel.

### The tools and the model that calls them

`ALL_TOOLS` in the example's tool module holds three LangChain tools: `lookup_flight(flight_number)`, `get_airport_info(airport_code)` and `find_routes(from_code, to_code, date_offset_days)`, each returning a dictionary from a small mock aviation dataset. Binding them to the model is what makes the model able to emit tool calls at all; the agent node then prepends the capability's prompt file and awaits the model.

### Confirmed result previews

Pass a stable `toolOutcome(activity)` callback to `<chat>` or `<chat-tool-calls>` to return app-authored `{ text, sources?: [{ title, url }] }` evidence for a validated result. The readonly activity includes its explicit phase and literal result text. Inspect the tool's known schema in your application before returning an outcome; arbitrary JSON and completed delivery do not establish business or persistence success.

`ChatToolActivityComponent` and `ChatToolActivityGroupComponent` accept the same metadata in `ToolActivityInfo.outcome`. Only complete activities expose previews. Group previews and deduplicated sources remain visible outside technical Details; the first three summaries and sources are visible, with the rest under **More results** and **More sources**. Source links require absolute HTTP(S) URLs without credentials. Mixed groups announce concise status counts politely without announcing raw streaming payloads.

Custom tool templates retain ownership. Project approval controls outside technical Details and dispatch decisions through the current adapter interrupt generation. A failed read can offer an explicit retry while retaining the successful prefix and failed attempt. Reconcile an uncertain write before retrying it.

### Declare a failed result

A tool can finish delivery and still report that it failed.
`lookup_flight` returns `{"error": "Flight UA999 not found in dataset"}` for an unknown flight, and the call still completes.
By default the row stays complete, because the library does not guess what a payload means.

Decode the tool's declared schema in `toolOutcome` and return `status: 'failed'` only for its declared error shape.

```typescript
import type { ToolActivityInfo, ToolActivityOutcome } from '@threadplane/chat';

const toolOutcome = (activity: ToolActivityInfo): ToolActivityOutcome | undefined => {
  if (activity.name !== 'lookup_flight' || !activity.resultText) return undefined;
  try {
    const result = JSON.parse(activity.resultText);
    return typeof result?.error === 'string'
      ? { status: 'failed', text: result.error }
      : undefined;
  } catch {
    return undefined;
  }
};
```

A failed call shows as failed, its `text` becomes the error explanation, and a settled group counts it.
For example, a group of three calls with one failure reads **Used 3 tools · 1 failed**.
Values such as `false`, `0`, `""`, `[]` and `null` are literal results, not failures.
Returning `undefined` keeps the call as it was.
Only a call that completed can be marked failed, so a running or stopped call is never rewritten.

This changes what is shown, not what the model receives.
The model still sees the original tool result.
If a tool should tell the model that it failed, set the error flag your protocol provides on the tool message.
The cost is that you maintain a decoder per tool, and a decoder that drifts from the tool's real schema shows the wrong state.
`ChatToolActivityComponent` and `ChatToolActivityGroupComponent` apply the same resolution to a failed outcome you pass them directly.
`resolveToolOutcome(activity, outcome)` is exported if you render activities with your own markup and want the same resolution.

### Add content to one call

Project an `ng-template` carrying `chatToolResultTemplate` into `<chat>` or `<chat-tool-calls>` to add content to a single call's row, such as a retry button or a rich result.

```html
<chat [agent]="agent" [toolOutcome]="toolOutcome">
  <ng-template chatToolResultTemplate="lookup_flight" let-activity>
    @if (activity.phase === 'error') {
      <button type="button" (click)="retryLookup(activity.id)">Retry flight lookup</button>
    }
  </ng-template>
</chat>
```

The context is the resolved `ToolActivityInfo` as `$implicit`, after `toolOutcome` ran, so a declared failure arrives with `phase: 'error'`.
Its content renders outside **Details** and is shown below a collapsed group.
Below a collapsed group, name the call in the control, such as **Retry UA999 lookup**, because a bare **Retry** does not say which call it acts on.
A literal `"*"` matches any tool without a template of its own, and a name match wins over it.
A tool with a `chatToolCallTemplate` keeps that full replacement, and result templates do not apply to it.
The slot only displays what you render.
It does not run, approve or retry anything, so the handler you bind owns that work.

### Recover from a partial failure

One read fails, another succeeds, and the user wants the missing piece without losing the rest.
You declare what each tool's result means, and the library does the rest of the display work.
The example tools are `read_reference`, which declares a recoverable `{"error": string, "recoverable": true}` result, and `save_note`, which returns `{"saved": true, "id": string}` only after an approved save.

```typescript
import { toolOutcomes } from '@threadplane/chat';

const toolOutcome = toolOutcomes({
  read_reference: ({ args, result }) => {
    const { id } = args as { id: string };
    const read = result as { error?: string; recoverable?: boolean; title?: string; url?: string; summary?: string };
    if (read.recoverable === true && typeof read.error === 'string') {
      return { status: 'failed', text: read.error, retry: { label: `Retry ${id} read` } };
    }
    return typeof read.summary === 'string' && typeof read.title === 'string' && typeof read.url === 'string'
      ? { text: read.summary, sources: [{ title: read.title, url: read.url }] }
      : undefined;
  },
  save_note: ({ result }) => {
    const save = result as { saved?: boolean; id?: string } | null;
    return save?.saved === true && typeof save.id === 'string'
      ? { status: 'receipt', text: `Note ${save.id} in Comparisons.` }
      : undefined;
  },
});
```

`toolOutcomes` takes one decoder per tool name and returns a `toolOutcome` callback.
It parses the arguments and the result once, and runs a decoder only for a completed call of its own tool.
A running, stopped or already failed call never reaches a decoder, and neither does a tool you did not list.
**Decode each tool's declared schema, and nothing else.**
`false`, `0`, `""`, `[]` and `null` arrive unchanged and mean nothing until your decoder says so.

Each call keeps its own outcome.
The successful read keeps its summary and source link beside the failed one, and the group reads **Used 2 tools · 1 failed**.
Sources render as links outside **Details**, and the literal JSON stays inside it.

#### Declare a retry

`retry: { label }` on a failed outcome offers a retry for that one call.
The failure appears in one panel below the group, with the retry after the explanation.

```html
<chat [agent]="agent" [toolOutcome]="toolOutcome" (toolRetry)="retryRead($event)" />
```

`(toolRetry)` emits the failed activity.

The library decides only *when* the control is worth showing.
It hides it while anything is running, and removes it once a later call repeats the same tool and arguments.
Your handler decides what a retry does.
Send it as a new request in the same conversation, and have your backend run only the failed read again as a new call.
Name the call in the label, such as **Retry toSorted read**, because the group may be collapsed above it.
While that repeat call is still running, the failure panel leads with **Retrying toSorted read**, built from your label, and the line shimmers like the current step in the progress view. A label that does not start with "Retry" gives a plain **Retrying**.
`<chat-tool-activity-group>` emits the same `(toolRetry)`, and takes a `context` input with every observed call so it can apply the same rule across messages.
While a per-call retry is offered, the `<chat>` error banner drops its own **Retry response**, because that one re-sends the whole request.

I would not declare a retry for a write.
A write that failed with an uncertain acknowledgment needs reconciliation before another attempt.

#### Show a receipt

`status: 'receipt'` records a write your application confirmed.
It renders as a success panel with the lead **Saved.**, or your own `lead`, followed by your `text`.
Return it only from the decoded save result, never from the approval.
An approval that has not produced `saved: true` shows no receipt, and neither does a denied one.

#### The status panel

Failures and receipts use `<chat-status-panel>`, which you can also use for your own approvals and notices.

```html
<chat-status-panel tone="warning" lead="Waiting for your approval.">
  <p>Save the comparison note to your workspace?</p>
  <button chatStatusPanelActions type="button" (click)="save()">Save note</button>
</chat-status-panel>
```

`tone` is `danger`, `warning`, `success` or `neutral`.
The lead sentence carries the meaning and the colour only reinforces it.
Set `role="alert"` for failures only.
The panel displays what you give it and runs nothing.

The cost of all this is one decoder per tool, kept in step with that tool's real schema.
A decoder that drifts shows the wrong state.

### The agent and tool loop

`should_continue` looks at the last message and routes to the `tools` node whenever it carries tool calls, and the `tools` edge goes straight back to `agent`. That is the loop: the model calls a tool, `ToolNode` runs it, the result returns as a tool message, and the model is invoked again within the same user turn. ### The agent provider

`provideAgent()` registers the agent once for the whole application, and it is the only provider the `<chat>` composition requires. The example passes a factory because it resolves its connection details at runtime from the host that serves the demo. Your own application does not need the factory.

## Scoping to one message

With no `message`, the component renders `agent.toolCalls()` unchanged. With an assistant message it renders only that message's calls, resolved in this order:

1. `message.toolCallIds`, when the adapter populated it. The LangGraph adapter fills it from the message's `tool_calls` array.
2. Otherwise the `tool_use` content blocks on the message, which is how Anthropic-shaped content is linked.
3. Otherwise nothing: an assistant message with no linkage emitted no calls.

A non-assistant message falls back to the full list, so pass the message only where it is an assistant bubble.

## Grouping

With `grouping` at `'auto'` and `groupRelated` at its default `true`, adjacent built-in calls share one activity row across tool names. Custom templates and subagent cards keep their own boundaries. Grouping remains local to the message or calls supplied to this component.

The borderless row starts collapsed, including for a single call. Opening it reveals individual calls and their technical Details. A row opened by the user remains open as calls arrive or settle. Confirmed results, source links and approval controls stay outside the collapsed technical subtree.

Set `[groupRelated]="false"` to retain same-name adjacency grouping: `search_web`, `read_file`, `search_web` then produces three separate activities. Under that opt-out, a single call renders directly and consecutive calls of the same name still group. Set `grouping="none"` to disable grouping entirely.

`excludeToolNames` is applied before grouping, so an excluded name cannot break a group in two.

## Default group summaries

While a tool is running, the collapsed row shows the current call's `toolLabel` with a subtle text shimmer, falling back to **Running tools…**, followed by the elapsed time and a **Stop** button that stops the run, like the composer's Stop. Expanded, the row reads **Working · 1 of 3 done**: finished calls show a tick, the running call carries the shimmer and pending calls are dimmed. When the agent declared a plan (`agent.plan`), its pending steps follow the calls, dimmed, so the list shows what is still to come. Without a plan, the list holds only the calls that have started. The elapsed time is measured in the browser from when the group starts running. Screen readers hear the current step through the polite status region, not the animation. Explicitly completed calls settle to **Used 4 tools**, with the appropriate count; when some failed it reads **Used 4 tools · 1 failed**. There is no additional completion-count subline. A tool count does not establish a successful business operation or persisted write.

Queued, paused, stopped and unavailable activity uses static wording. **Tool activity paused** does not imply approval. A failed call can coexist with running work; the activity row preserves a static failure cue while actual work remains active. Reduced motion and forced colors use readable static text. Meaningful state changes remain available in a polite status region without raw payloads or timer ticks.

Tool-name prefixes do not prove whether a call searched sites, read files, or completed a business operation. Pass `groupSummary` for application-specific wording; explicit summary overrides retain precedence:

```html
<chat-tool-calls [agent]="agent" [message]="msg" [groupSummary]="summarize" />
```

```typescript
const summarize = (name: string, count: number): string =>
  name === 'lookup_flight'
    ? `Looked up ${count} flights`
    : `${name} × ${count}`;
```

The `<chat>` composition defaults `groupRelatedTools` to `true` and forwards it with `toolLabel` to its per-message activity region. Set `[groupRelatedTools]="false"` to retain same-name grouping. `ChatToolActivityComponent` and `ChatToolActivityGroupComponent` are also available as readonly presentation primitives. Supply literal evidence and an explicit `phase`; omitted status is shown as unavailable. Their projected content stays mounted outside technical Details, so a rich result or approval control can remain visible. Inside a group, rows name a failure only by their **Failed** status word; the failure message and any retry appear once, in the group's danger panel. Set `[grouped]="true"` on `ChatToolActivityComponent` when you render rows inside your own group panel. These primitives never execute, resume, approve, or persist work. A tool result is separate from application confirmation of saved data.

For AG-UI, `TOOL_CALL_END` closes argument streaming. The adapter keeps execution running until `TOOL_CALL_RESULT`; it does not infer execution success from finalized arguments. Stopped, interrupted and paused response outcomes remain distinct.

## Per-tool templates

Project an `ng-template` carrying the `chatToolCallTemplate` directive to replace the card for one tool name. A literal `"*"` registers a wildcard used for any name without a template of its own; a name-specific template wins over it.

```html
<chat-tool-calls [agent]="agent" [message]="msg">
  <ng-template
    chatToolCallTemplate="lookup_flight"
    let-call
    let-status="status"
  >
    <my-flight-card
      [flightNumber]="call.args.flight_number"
      [status]="status"
    />
  </ng-template>
</chat-tool-calls>
```

The template context is the `ToolCall` as `$implicit` and its status as `status`. Calls handled by a template never render a strip: each one is rendered through the template, so the density is yours to manage. The directive is covered in full on [chatToolCallTemplate](/docs/angular/chat/components/chat-tool-call-template).

## Calls that spawned a subagent

When the agent exposes a subagent whose `toolCallId` matches a call, that call renders as a `<chat-subagent-card>` instead of a tool-call card, and it never joins a group on either side. Adapters key their subagent map differently, so the match is made on the subagent's `toolCallId` field rather than the map key.

## The activity inside the row

Calls without a custom template or subagent card use `ChatToolActivityComponent` inside the group's disclosure. Each activity retains its readable label, explicit phase, and technical **Details**. The outer row starts collapsed and preserves the user's expansion choice through running and settled states. An error explanation and application-owned rich results remain outside the collapsed group.

[ChatToolCallCard](/docs/angular/chat/components/chat-tool-call-card) remains available for applications that explicitly choose its separate card presentation.

## Styling

The host is a block with a 20 pixel bottom margin. The default activity row has no border or card background and reads these properties from the chat theme:

| Variable                    | Applied to                                            |
| --------------------------- | ----------------------------------------------------- |
| `--tplane-chat-text-muted` | Quiet activity text and shimmer base                  |
| `--tplane-chat-text`       | Activity text and shimmer highlight                   |
| `--tplane-chat-primary`    | Keyboard focus indicator                              |

Setting the variables is covered in the [theming guide](/docs/angular/chat/guides/theming).
