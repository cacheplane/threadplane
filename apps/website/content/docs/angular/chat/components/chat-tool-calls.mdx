# ChatToolCallsComponent

`ChatToolCallsComponent` renders readable tool activity with explicit lifecycle status. Technical names, call IDs, arguments, results and errors remain available in collapsed **Details**. Consecutive same-name calls group by default; grouping across names is opt-in. The aviation example mounts this component in the conversation and in a sidebar.

**Selector:** `chat-tool-calls`

## Show the work behind an answer

A traveler may see several lookups before receiving an itinerary. Each lookup has an identity, a name, arguments, and eventually a result or error. Keep that structured information with the assistant message that requested it so two calls to the same tool remain distinguishable.

`ChatToolCallsComponent` observes and presents calls. The backend or client-tool coordinator executes them. A card becoming visible does not itself run the tool. See [Client tools](/docs/angular/chat/guides/client-tools) when your application needs to implement the requested capability.

## What the demo does

The Run tab shows a conversation on the left and a sidebar headed "Tool Calls" on the right, with an "Available Tools" list below it naming the three aviation tools the agent can call. One welcome suggestion, "Check a flight status", asks for the status of flight UA123.

The agent answers by calling `lookup_flight`. The sidebar and transcript show “Looking up flight information,” its explicit status, and a validated flight status/gate preview when the result arrives. Open **Details** to inspect the technical name, arguments and full flight record. A failed or malformed aviation record does not receive a successful result preview.

Grouping is easier to see with a second request. Ask the assistant to compare LAX and JFK: two airport lookups can share a compact activity strip. Confirmed airport summaries remain outside the technical disclosure; expand the strip to inspect each distinct call. Concise counts distinguish completed, running and failed activities in a mixed group.

## How it is built

Three files carry the example: the graph that binds the tools and loops until the model stops calling them, the provider that points Angular at that graph, and the component that places the panel.

### The tools and the model that calls them

`ALL_TOOLS` in the example's tool module holds three LangChain tools: `lookup_flight(flight_number)`, `get_airport_info(airport_code)` and `find_routes(from_code, to_code, date_offset_days)`, each returning a dictionary from a small mock aviation dataset. Binding them to the model is what makes the model able to emit tool calls at all; the agent node then prepends the capability's prompt file and awaits the model.

These technical names identify and group calls. App-authored `toolLabel` metadata supplies readable activity labels without changing execution.

### Confirmed result previews

Pass a stable `toolOutcome(activity)` callback to `<chat>` or `<chat-tool-calls>` to return app-authored `{ text, sources?: [{ title, url }] }` evidence for a validated result. The readonly activity includes its explicit phase and literal result text. Inspect the tool's known schema in your application before returning an outcome; arbitrary JSON and completed delivery do not establish business or persistence success.

`ChatToolActivityComponent` and `ChatToolActivityGroupComponent` accept the same metadata in `ToolActivityInfo.outcome`. Only complete activities expose previews. Group previews and deduplicated sources remain visible outside technical Details; the first three summaries and sources are visible, with the rest under **More results** and **More sources**. Source links require absolute HTTP(S) URLs without credentials. Mixed groups announce concise status counts politely without announcing raw streaming payloads.

Custom tool templates retain ownership. Project approval controls outside technical Details and dispatch decisions through the current adapter interrupt generation. A failed read can offer an explicit retry while retaining the successful prefix and failed attempt. Reconcile an uncertain write before retrying it.

### The agent and tool loop

`should_continue` looks at the last message and routes to the `tools` node whenever it carries tool calls, and the `tools` edge goes straight back to `agent`. That is the loop: the model calls a tool, `ToolNode` runs it, the result returns as a tool message, and the model is invoked again within the same user turn. A model response with no tool calls falls through to the title node instead.

### The agent provider

`provideAgent()` registers the agent once for the whole application, and it is the only provider the `<chat>` composition requires. The example passes a factory because it resolves its connection details at runtime from the host that serves the demo. Your own application does not need the factory.

Pass the values directly:

```typescript
provideAgent({
  apiUrl: 'https://your-deployment.langgraph.app',
  assistantId: 'c-tool-calls',
});
```

`assistantId` must match the graph name in `langgraph.json`.

## Inputs

| Input               | Type                                                     | Default      | Description                                                                                                                                                                                                       |
| ------------------- | -------------------------------------------------------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `agent`             | `Agent`                                                  | **Required** | The agent whose `toolCalls()` signal is rendered.                                                                                                                                                                 |
| `message`           | `Message \| undefined`                                   | `undefined`  | Scopes rendering to one assistant message. Omit it and the whole thread's calls are rendered.                                                                                                                     |
| `grouping`          | `'auto' \| 'none'`                                       | `'auto'`     | With `'auto'`, consecutive calls to the same tool collapse into one strip. With `'none'`, every call renders on its own.                                                                                          |
| `groupSummary`      | `((name: string, count: number) => string) \| undefined` | `undefined`  | Replaces the generic activity count.                                                                                                                                                                              |
| `groupRelated`      | `boolean`                                                | `false`      | Allows adjacent default calls with different names to group. `grouping="none"` still disables grouping. Custom templates and subagents stay separate.                                                             |
| `toolLabel`         | `(name: string) => string \| undefined`                  | `undefined`  | Supplies a readable label; unknown names use “Tool activity.” The technical name stays in Details.                                                                                                                |
| `toolOutcome`       | `(activity: ToolActivityInfo) => ToolActivityOutcome \| undefined` | `undefined` | Supplies validated, app-authored previews and source links for default rows. Custom templates retain ownership. |
| `excludeToolNames`  | `readonly string[]`                                      | `[]`         | Tool names to hide entirely. Compositions use it to keep internal orchestration tools out of the transcript.                                                                                                      |
| `toolCallTemplates` | `readonly ChatToolCallTemplateDirective[]`               | `[]`         | Per-tool templates supplied by a parent composition, such as the ones `<chat>` collects from its own content. A template projected directly into `<chat-tool-calls>` wins over a supplied one with the same name. |

The component has no outputs.

## Scoping to one message

With no `message`, the component renders `agent.toolCalls()` unchanged. With an assistant message it renders only that message's calls, resolved in this order:

1. `message.toolCallIds`, when the adapter populated it. The LangGraph adapter fills it from the message's `tool_calls` array.
2. Otherwise the `tool_use` content blocks on the message, which is how Anthropic-shaped content is linked.
3. Otherwise nothing: an assistant message with no linkage emitted no calls.

A non-assistant message falls back to the full list, so pass the message only where it is an assistant bubble.

## Grouping

With `grouping` at `'auto'`, the component walks the calls in order and appends a call to the previous group when the names match. Grouping is adjacency-based, so `search_web`, `read_file`, `search_web` produces three groups rather than two.

A group holding more than one call renders as a collapsible strip: a header button carrying the summary label and a chevron, collapsed on first render, expanding to the individual cards when clicked. A group holding a single call renders that card directly, with no strip around it.

`excludeToolNames` is applied before grouping, so an excluded name cannot break a group in two.

## Default group summaries

The default is “N tool activities.” Tool-name prefixes do not prove whether a call searched sites, read files, or completed a business operation. Pass `groupSummary` for application-specific wording:

```html
<chat-tool-calls [agent]="agent" [message]="msg" [groupSummary]="summarize" />
```

```typescript
const summarize = (name: string, count: number): string =>
  name === 'lookup_flight'
    ? `Looked up ${count} flights`
    : `${name} × ${count}`;
```

The `<chat>` composition forwards `toolLabel` and `groupRelatedTools` to its per-message activity region. `ChatToolActivityComponent` and `ChatToolActivityGroupComponent` are also available as readonly presentation primitives. Supply literal evidence and an explicit `phase`; omitted status is shown as unavailable. Their projected content stays mounted outside technical Details, so a rich result or approval control can remain visible. These primitives never execute, resume, approve, or persist work. A tool result is separate from application confirmation of saved data.

For AG-UI, `TOOL_CALL_END` closes argument streaming. The adapter keeps execution running until `TOOL_CALL_RESULT`; it does not infer execution success from finalized arguments. Stopped, interrupted and paused response outcomes remain distinct.

## Per-tool templates

Project an `ng-template` carrying the `chatToolCallTemplate` directive to replace the card for one tool name. A literal `"*"` registers a wildcard used for any name without a template of its own; a name-specific template wins over it.

```html
<chat-tool-calls [agent]="agent" [message]="msg">
  <ng-template
    chatToolCallTemplate="lookup_flight"
    let-call
    let-status="status"
  >
    <my-flight-card
      [flightNumber]="call.args.flight_number"
      [status]="status"
    />
  </ng-template>
</chat-tool-calls>
```

The template context is the `ToolCall` as `$implicit` and its status as `status`. Calls handled by a template never render a strip: each one is rendered through the template, so the density is yours to manage. The directive is covered in full on [chatToolCallTemplate](/docs/angular/chat/components/chat-tool-call-template).

## Calls that spawned a subagent

When the agent exposes a subagent whose `toolCallId` matches a call, that call renders as a `<chat-subagent-card>` instead of a tool-call card, and it never joins a group on either side. Adapters key their subagent map differently, so the match is made on the subagent's `toolCallId` field rather than the map key.

## The card each call renders

Every call the component does not hand to a template or a subagent card is rendered by `ChatToolCallCardComponent`: the tool name, a status pill, an Inputs section holding the arguments, and an Output section that appears only once a result exists. A card whose status is `running` or `error` expands itself; a completed one stays collapsed until it is clicked. See [ChatToolCallCard](/docs/angular/chat/components/chat-tool-call-card) for its own inputs.

## Styling

The host is a block with a 20 pixel bottom margin. The strip reads three custom properties from the chat theme:

| --------------------------- | ----------------------------------------------------- |
| `--tplane-chat-separator`   | Strip border, and the divider above the expanded body |
| `--tplane-chat-radius-card` | Strip corner radius                                   |
| `--tplane-chat-text`        | Strip header text                                     |

Setting the variables is covered in the [theming guide](/docs/angular/chat/guides/theming).
