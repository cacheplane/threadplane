# Message model

`@threadplane/angular/chat` renders the backend-neutral message model `@threadplane/core` defines. A session translates backend-specific messages into this shape, and components render from that shape alone.

This matters because provider message formats are not stable enough to build product UI against directly. LangGraph, AG-UI, OpenAI, Anthropic, and custom backends all carry different event and content shapes, and the chat layer needs one model. The running example is the smallest thing that shows it whole: a message list with no default templates, so every role in the model is a template you can read.

## A message is one part of a turn

A Portland planning request is one user message. Its answer may contain several assistant messages, tool requests, tool results, and a final summary. Keep message identity separate from array position and from the user turn that produced it.

The session normalizes those messages before the UI reads them. Display text, delivery status, tool identity, and citations stay structured so a component can render progress without parsing the assistant's prose. [Follow a conversation](/docs/angular/langgraph/concepts/conversation-turns) places messages inside the larger request and persistence flow.

## What the demo does

The Run tab shows a conversation under the heading "Chat messages", with a panel on the right naming the primitives it uses. The agent behind it is an aviation assistant whose mock dataset covers ten United States airports and four airlines.

Ask it something like which airlines fly out of SFO. The status line under the input reads "Receiving response…" while the run is in flight and "Response complete." once it settles. Then ask a follow-up: the previous answer stays exactly as it was while the new one streams, which is the delivery lifecycle described below doing its job.

## How it is built

Three files carry the example: the graph that produces the messages, the provider that points Angular at it, and the component that renders one template per role.

### The graph that produces the messages

The visible node is `generate`. `MessagesState` gives LangGraph a message list the SDK already understands, the model is constructed with `streaming=True`, and the node prepends a system prompt read from the capability's prompt file before it awaits the model. A second node, `generate_title`, runs after it and writes a short thread title back through the LangGraph SDK.

Every message the browser renders begins as an entry in that returned list.

### The application configuration

`provideAgent()` from `@threadplane/angular` provides the agent for the whole application, keyed by a typed ref, and it is the only provider the chat components require. Its `createSession` factory returns a LangGraph session for the thread the agent asks for, and `stateType` declares the graph state's type. This example resolves its connection details at runtime from the host that serves the demo, which is why the config is itself a factory that reads them rather than hard-coding them.

Your own application does not need the outer factory: pass `apiUrl` and `assistantId` to `createSession()` directly, where `assistantId` is the graph name declared in `langgraph.json`, which is `c-messages` for this example.

### One template per role

`ChatMessageListComponent` renders nothing by itself. It iterates the agent's messages, maps each message's `role` to a template name, and looks for a projected `<ng-template chatMessageTemplate="...">` with that name. A message whose template is missing renders nothing at all, which is how the demo hides tool results: the `tool` template is deliberately empty. `messageContent()` returns the message's visible text.

The template context is the message itself as `$implicit`, plus `index`.

`<chat>` provides its own default templates internally. Projecting templates by hand is the price and the point of building from primitives: nothing renders that you did not write.
</Callout>

### Delivery drives the assistant bubble

The assistant template is the only one that reads `delivery`. `streaming` on `<chat-message>` comes straight from `message.delivery.phase`, and `markdownDocument()` pairs the text with the same delivery so that the streaming markdown renderer can tell an append from a new answer.

<ExampleCode file="messages.component.ts" region="assistant-template" title="messages.component.ts — the assistant template" />

`markdownDocument(content, delivery)` returns `{ generation, phase, content }`, and the renderer treats a change of `generation` as a new document rather than an edit of the old one.

### The input strip

The input takes the agent and needs nothing else. `<chat-input>` calls `agent.submit()` itself, which is what turns a keystroke into a `user` message in the list above, and then emits `submitted` with the same trimmed text.

<ExampleCode file="messages.component.ts" region="input-strip" title="messages.component.ts — the input strip" />

<Callout type="warning" title="Do not submit from (submitted)">
The output fires after the message has already been sent. A handler that calls `submit()` again posts the user message twice. The demo binds it only to set the flag behind its status line; bind `(submitted)` only for side effects such as that or analytics, never for submission.
</Callout>

`injectAgent()` resolves the same ref the provider registered, typed by the session type declared beside it, so `agent.state()` is a typed read of the graph state. The agent has no separate loading flag, so the class derives one from `agent.status()`. The two imported helpers are exposed as fields so the inline template can call them.

## The message shape

Everything above renders instances of one interface:

```ts
interface Message {
  readonly id: string;
  readonly delivery: MessageDelivery;
  readonly role: 'user' | 'assistant' | 'system' | 'tool';
  readonly content: string;
  readonly blocks?: readonly ContentBlock[];
  readonly toolCallId?: string;
  readonly name?: string;
  readonly reasoning?: string;
  readonly reasoningDurationMs?: number;
  readonly extra?: Readonly<Record<string, PlainValue>>;
  readonly citations?: readonly Citation[];
  readonly toolCallIds?: readonly string[];
}
```

The fields are intentionally few, and every message is frozen plain data owned by the session. Portable UI state goes in the known fields; backend-specific data goes in `extra`. The session must supply `delivery` for every message.

`toolCallId` and `toolCallIds` point in opposite directions. The singular field is the call a `tool` message answers. The plural field lists the calls emitted by an assistant message, and `<chat-tool-calls>` uses it to scope its rendering to one message instead of falling back to the agent's global list.

## Delivery lifecycle

`Message.delivery` is the session's authoritative lifecycle state for one response attempt:

```ts
type CompleteOutcome = 'success' | 'error' | 'aborted' | 'interrupted' | 'paused';

type MessageDelivery =
  | { readonly generation: string; readonly phase: 'streaming' }
  | {
      readonly generation: string;
      readonly phase: 'complete';
      readonly outcome: CompleteOutcome;
    };
```

`paused` is an intentional stop awaiting resumable input; `interrupted` means the stream ended unexpectedly. Use the public helpers rather than repeating the object literals:

```ts
import {
  completeDelivery,
  staticDelivery,
  streamingDelivery,
} from '@threadplane/angular/chat';

const partial = streamingDelivery('attempt-7');
const finished = completeDelivery('attempt-7', 'success');
const historical = staticDelivery('message-42');
```

Every message produced by one response attempt shares that attempt's `generation`, and it stays stable as the attempt moves from streaming to complete. Streaming content is append-only; once complete, content and delivery are immutable. A retry or a replacement attempt gets a new generation. `staticDelivery(messageId)` is the concise choice for user messages, tool results, and restored history, which have no live delivery of their own.

Components consume this field directly. Do not derive a message's phase from the agent-wide `status()`: concurrent work, interruptions, retries, and restored history all make that inference wrong. The demo's assistant template is the shortest illustration, and `<chat>` goes further, keying its per-message content classifier on `generation` so a regenerated answer starts from a clean parse.

## Roles and template names

Message roles are:

| Role | Meaning |
|---|---|
| `user` | Human input submitted through the UI or the session. |
| `assistant` | Model output. May carry markdown, reasoning, tool calls, citations, or generated UI payloads. |
| `tool` | Tool result associated with a tool call. |
| `system` | System or runtime message shown as context. |

Template names are a separate vocabulary, and the message list translates between them:

| Role | Template name |
|---|---|
| `user` | `human` |
| `assistant` | `ai` |
| `tool` | `tool` |
| `system` | `system` |

A fifth template name, `function`, is accepted by the directive for compatibility with older function-call vocabulary, but no role maps to it, so such a template is never selected. Normalize function results into `tool` messages, or carry backend-specific detail in `extra`.

## Content

`content` is always text. A message that holds more than text also carries `blocks`:

```ts
type ContentBlock =
  | { type: 'text'; text: string }
  | { type: 'image'; url: string; alt?: string }
  | { type: 'tool_use'; id: string; name: string; args: PlainValue }
  | { type: 'tool_result'; toolCallId: string; result: PlainValue; isError?: boolean };
```

Plain text is the common case, and it is the only case in the demo. When `blocks` is present, `content` holds the text of its `text` blocks, so a template that renders text only needs no second path. `contentBlocksText(blocks)` computes the same string from a block list.

Custom templates can therefore interpolate `content` directly, and read `blocks` only when they render images or inline tool data:

```ts
function imagesOf(message: Message): readonly string[] {
  return (message.blocks ?? [])
    .filter((block) => block.type === 'image')
    .map((block) => block.url);
}
```

`submit()` takes the message text, or `{ message, blocks }` to send structured content; `message` is then the text shown where blocks are not rendered. What reaches the backend is the session's decision. The LangGraph session sends `text` and `image` blocks as the human message's content and rejects a tool block before anything is sent.

## Markdown

Assistant text is rendered as markdown by the `<chat>` composition. Its markdown renderer also resolves citation references when citations are present.

With primitives, markdown is your decision. The demo makes it by importing `ChatStreamingMdComponent`; `renderMarkdown()` and your own renderer are equally valid choices.

This matters because markdown is presentation policy. A customer support chat, a code assistant, and an audit trail need different rules for links, tables, code blocks, and images.

## Reasoning

Reasoning is separate from visible answer content:

```ts
message.reasoning;
message.reasoningDurationMs;
```

The LangGraph session populates `reasoning` from provider-specific reasoning or thinking blocks, and the AG-UI session populates it from reasoning events. The surfaced value is always a plain string. Provider-specific encrypted blocks, summaries, and step metadata are absorbed by the session rather than leaking into portable UI code. `reasoningDurationMs` is set only when the session measured the reasoning; absent means unknown, so show no time for it.

`<chat>` renders reasoning with `<chat-reasoning>` above the answer, merging a run of consecutive reasoning steps into a single pill and summing their durations. If you build from primitives, as the demo does, reasoning renders nowhere until you place it.

## Tool calls

Tool calls have their own normalized shape, carried on `agent.toolCalls()`:

```ts
export type ToolCallStatus = 'pending' | 'running' | 'complete' | 'error';

type ToolCall = {
  readonly id: string;
  readonly name: string;
  readonly args: PlainValue;
} & (
  | { readonly status: 'pending' | 'running' }
  | { readonly status: 'complete'; readonly result: PlainValue; readonly parts?: readonly PlainValue[] }
  | { readonly status: 'error'; readonly error: string; readonly parts?: readonly PlainValue[] }
);
```

Use `toolCalls()` when rendering cross-message tool status, and `tool` messages when rendering tool output inside the transcript. Pair the two through `toolCallId`. `result` exists only on a `complete` call and `error` only on an `error` call; `toolCallResult(call)` and `toolCallError(call)` from `@threadplane/angular/chat` read them without narrowing first.

This matters because tool calls stream. A call in `toolCalls()` already has decoded, final arguments. A call the model is still writing is listed apart, in `agent.streamingToolCalls()`, with the argument text so far in `argsText` and a best-effort `args`. `agentToolCalls(agent)` from `@threadplane/angular/chat` merges the two lists, showing a streaming call as a `running` call until its finished form arrives under the same `id`.

## Citations

Messages can carry provider-agnostic citations on `message.citations`:

```ts
interface Citation {
  readonly id: string;
  readonly index: number;
  readonly title?: string;
  readonly url?: string;
  readonly snippet?: string;
  readonly extra?: Readonly<Record<string, PlainValue>>;
  readonly sourceType?: string;
  readonly iconUrl?: string;
  readonly publishedAt?: string | number;
}
```

`id` is matched against `[^id]` markers in the content, and `index` is the 1-based display order, stable per message. `@threadplane/langgraph` exports `extractCitations(message)`, which reads the citations in a wire message's `additional_kwargs` as core `Citation` values.

Citation display derives a type badge from `sourceType`; when it is absent and `url` is present, the source is treated as `web`, and otherwise as `unknown`. `iconUrl` takes precedence over generated source icons and monograms, and the library never fetches a favicon on its own.

`<chat-message>` renders `<chat-citations>` for an assistant message only when it is given the whole message:

```html
<chat-message [role]="'assistant'" [message]="message" />
```

The demo passes `role`, the streaming flag read from `delivery`, and a `current` flag computed from the index, but not `message`, so no citation strip appears under its answers.

The resolve path from a `[^id]` marker to a rendered citation runs through `CitationsResolverService`, exported from `@threadplane/angular/chat`. A custom citation renderer provides the service, sets the current message, then calls `lookup(refId)`, which returns a `Signal<ResolvedCitation | null>` matching the marker id against `message.citations` and falling back to inline markdown definitions:

```ts
import { Component, computed, inject, input } from '@angular/core';
import { CitationsResolverService } from '@threadplane/angular/chat';
import type { Message } from '@threadplane/angular/chat';

@Component({
  selector: 'app-citation-ref',
  standalone: true,
  providers: [CitationsResolverService],
  template: `@if (resolved(); as r) {<sup>[{{ r.citation.index }}]</sup>}`,
})
export class CitationRefComponent {
  private readonly resolver = inject(CitationsResolverService);

  readonly message = input.required<Message>();
  readonly refId = input.required<string>(); // the `id` from a [^id] marker

  // lookup() returns a Signal; resolved.source is 'message' or 'markdown'.
  protected readonly resolved = computed(() => {
    this.resolver.message.set(this.message());
    return this.resolver.lookup(this.refId())();
  });
}
```

Keep citation data on the message that owns the content. Avoid a separate global citation store unless your product has a cross-message source panel.

## Interrupts

Interrupts are not messages. They are optional agent state:

```ts
agent.interrupts(); // readonly AgentInterrupt[] | undefined
```

A run that pauses for a person settles with the `'paused'` outcome and lists what it waits on. An interrupt carries an `id` and may carry an opaque backend-specific `value` the application renders, a `reason`, a display `message` and the `toolCallId` it is about. `resumable` is `false` for an interrupt the session can show and cannot answer. Answer the pending interrupts with the optional `resume` command, one response for each:

```ts
const [interrupt] = agent.interrupts() ?? [];
if (interrupt && agent.resume) {
  await agent.resume([
    { interruptId: interrupt.id, status: 'resolved', value: { approved: true } },
  ]);
}
```

This matters because an interrupt is lifecycle state, not transcript content. Render it as a banner, a dialog, or an approval panel, but keep the canonical state on `agent.interrupts()`.

## Subagents

Subagents are also optional agent state:

```ts
agent.subagents(); // readonly AgentSubagent[] | undefined
```

The list holds the child agents the root agent started, in start order. Each `AgentSubagent` is plain data: an `id`, an optional `name` and `description`, a `status` of `pending`, `running`, `complete`, `error` or `unknown`, and its own `messages` and `toolCalls`, which are not repeated in the root transcript. `toolCallId` relates a child to the root tool call that started it, and `parentId` to the child that did. A backend that reports state for children adds `state`.

Use subagents when the backend delegates work to child graphs or specialized workers. Do not encode subagent progress as invented assistant messages when the backend can expose structured state instead. Structured state lets UI render progress, nested transcripts, and failure states without parsing prose.

## Generated UI in assistant content

Generated UI arrives through ordinary assistant content. `<chat>` classifies that text from its first non-whitespace character:

- json-render when the first character is `{`.
- A2UI when the text starts with `---a2ui_JSON---`.
- Markdown otherwise.

Classification stays pending while the content is empty or whitespace, or while a leading `-` is still a prefix of the `---a2ui_JSON---` sentinel. A leading `{` commits to a specification immediately, and any other first character commits to markdown right away. json-render uses a single spec object; A2UI uses a stream of JSONL envelopes that update surfaces, data models, and rendering state.

The message remains an assistant message either way. Generated UI is an interpretation of its content, not a new role. The classifier belongs to the composition, which is why the demo, built from primitives, renders a spec as literal markdown text instead.

## Practical rules

Normalize at the session boundary. Components should not inspect raw LangGraph SDK messages or AG-UI events unless they are backend-specific tools.

Treat `content` as the text of a message and `blocks` as its optional structured form. Do not assume every message has blocks.

Use the exported type guards when role-specific code helps:

```ts
import {
  isUserMessage,
  isAssistantMessage,
  isToolMessage,
  isSystemMessage,
} from '@threadplane/angular/chat';
```

Put backend-specific fields in `extra`, and document them with your session. Portable UI should survive when `extra` is absent.

## Cross-origin iframe hosts

A cross-origin child cannot read the parent’s visible viewport. On iOS Safari,
the software keyboard can shrink the parent’s `visualViewport` while the child
continues to see the iframe’s full fixed height. Size the frame in the parent;
changing the child’s `100dvh` alone does not solve this.

The built-in docs workspace handles parent sizing for Angular and React
examples. For a custom full-screen parent with a frame normally capped at 580px,
use a flex host so its header and footer share the same visible height:

```html
<section class="runtime-host">
  <header>Your chat</header>
  <iframe title="Chat" src="https://your-chat.example"></iframe>
  <footer>Your parent controls</footer>
</section>
```

```css
.runtime-host {
  position: fixed;
  inset-inline: 0;
  top: var(--runtime-top, 0px);
  height: min(580px, var(--runtime-height, 100dvh));
  display: flex;
  flex-direction: column;
}
.runtime-host > header,
.runtime-host > footer {
  flex: none;
}
.runtime-host > iframe {
  flex: 1;
  min-height: 0;
  width: 100%;
  border: 0;
}
```

```js
function fitRuntimeHost(host) {
  const viewport = host.ownerDocument.defaultView?.visualViewport;
  if (!viewport) return () => {};
  const names = ['--runtime-height', '--runtime-top'];
  const previous = names.map((name) => [
    host.style.getPropertyValue(name),
    host.style.getPropertyPriority(name),
  ]);
  const update = () => {
    if (viewport.scale !== 1) return;
    host.style.setProperty(names[0], `${viewport.height}px`);
    // This host is fixed, so use offsetTop, not document-relative pageTop.
    host.style.setProperty(names[1], `${viewport.offsetTop}px`);
  };
  update();
  viewport.addEventListener('resize', update);
  viewport.addEventListener('scroll', update);
  return () => {
    viewport.removeEventListener('resize', update);
    viewport.removeEventListener('scroll', update);
    names.forEach((name, index) => {
      const [value, priority] = previous[index];
      if (value) host.style.setProperty(name, value, priority);
      else host.style.removeProperty(name);
    });
  };
}
```

Call `fitRuntimeHost` once when the parent host mounts and run its returned
cleanup when it unmounts—for example, return it from a React effect or register
it with Angular’s `DestroyRef.onDestroy`. Keep the iframe node and `src` stable
while resizing so the child retains its conversation, draft, focus and reading
position. This pattern does not require reading the child DOM or adding a
cross-origin message protocol. Configure the child’s allowed embedding origins
separately if its application requires them.
