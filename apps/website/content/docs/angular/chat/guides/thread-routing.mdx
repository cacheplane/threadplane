# Thread Routing

A chat that holds more than one conversation needs two things: a store that knows which threads exist, and a single signal that says which one is active. `provideThreadDirectory()` from `@threadplane/angular` supplies the store over `createLangGraphThreadDirectory()` from `@threadplane/langgraph`, `provideAgent({ threadId })` watches the signal, and `injectThreadRouting()` binds that signal to the Angular Router when you want conversations to survive a reload and travel in a link. The running example wires the store and the signal, and this guide walks its three files before turning to the URL layer.

## Make a conversation addressable

In the trip planner, a link should identify the Portland conversation without embedding its transcript in the URL. The backend stores that transcript. Routing only selects the thread to load.

Start with one active-thread value, then decide where it lives: page memory for an embedded demo, or a route for a bookmarkable application. A thread title is display metadata; changing it does not change the thread ID or start another agent turn. [Persistence](/docs/angular/langgraph/guides/persistence) explains the server side of this relationship.

## What the demo does

The Run tab shows the prebuilt `<chat>` composition with a thread sidebar beside it. Ask the aviation assistant about a route — a flight from LAX to JFK, for instance — and the backend allocates a thread. The sidebar row starts out labeled `Untitled` and picks up a short generated title once the run finishes.

Press "New chat" at the top of the sidebar to open a second conversation, then move between the rows and watch the transcript swap. Each row also carries a menu with Rename, Pin, Move to project, Archive, and Delete, and pinned rows can be dragged into a new order. Every one of those round-trips through the LangGraph Threads API, and project names are kept in the LangGraph Store. Archived threads move into a collapsible Archived section whose rows offer Unarchive.

## How it is built

Three files carry the feature: a graph that writes a readable title into thread metadata, an application config that provides the thread directory, and a component that owns the active-thread signal and the sidebar. Open the Code tab to read them in place.

### Naming a thread from its first turn

A thread id is a UUID, which makes a poor sidebar label. The `generate_title` node asks a small model to summarize the first human message and writes the result to the thread's `metadata.title`, which is exactly where the thread directory looks for a label. The write itself sits inside a `try`/`except` that swallows failures, so a title write that fails never blocks the run.

### Providing the thread directory

`provideThreadDirectory()` from `@threadplane/angular` gives the application one view of a `ThreadDirectory`: its snapshot as signals and its commands. The config supplies `createDirectory`, and here that calls `createLangGraphThreadDirectory()` from `@threadplane/langgraph`, which wraps `client.threads.*` from `@langchain/langgraph-sdk`. The config is a factory because the base URL comes from an injected connection. The second root provider, `AGENT_CLIENT_OPTIONS`, carries the client options — auth headers, retries — that the directory factory receives as `context.clientOptions`.

Nothing else is registered at the root, because the agent itself is provided at the component instead.

### The agent provider

`provideAgent()` sits in the component's `providers` array rather than in the application config, because `threadId` and `onThreadId` are per-instance configuration.

<ExampleCode file="threads.component.ts" region="agent-provider" title="threads.component.ts — the agent provider" />

`createSession` is called once for each thread the agent opens: `context.threadId` is the thread to open and `context.onThreadId` reports a thread the session creates. The agent watches the `threadId` signal, so assigning a different id to it switches conversations, and the config's `onThreadId` fires when the backend allocates a thread on first submit, which keeps the signal in step without a round-trip through the sidebar.

<Callout type="warning" title="Thread ids come from the server">
Use a confirmed backend thread: one reported through `onThreadId`, or one created/read through the Threads API. A caller may request a UUID when creating a thread, but must confirm the server accepted it before treating it as an existing conversation.
</Callout>

### The sidebar and the thread list

The `<chat>` composition owns the transcript, the input, and the loading and error states, so the template adds the sidebar beside it. `<chat-thread-sidebar>` is connected: it takes the injected view's `directory` and draws New chat, Projects, Recent, and Archived with the row commands the directory supports. It refreshes the directory when it mounts, after each row command, and, given `[agent]`, each time a run ends.

<ExampleCode file="threads.component.ts" region="chat-and-sidebar" title="threads.component.ts — the template" />

The sidebar emits `threadSelected` when a row is chosen. The template listens to `(newChat)`, so New chat runs the same handler as the header's "New conversation" button and clears the unsent draft. Selecting a project emits `projectSelected`; the component keeps the selection in a signal bound to `[selectedProjectId]`, so the sidebar lists only that project's conversations until the project is selected again.

### Row actions

The sidebar performs each row command through the directory. The framework owns the interactions around each call (the inline rename field, the delete confirmation dialog, and the optimistic row update), so the component only handles the one event that changes its own state: the active conversation was deleted.

<ExampleCode file="threads.component.ts" region="thread-actions" title="threads.component.ts — the removed active thread" />

Clearing the signal and calling `switchThread(null)` returns the surface to a new chat.

<Callout type="info" title="Which menu entries appear">
The sidebar offers a command only when the directory can perform it, and the `features` input turns built-in commands off. The LangGraph directory supports them all. The injected view owns it and disposes it with its injector: the sidebar unsubscribes when it is destroyed but never disposes it.
</Callout>

### Refreshing after a run

The store is a snapshot, not a subscription, so something has to re-fetch it. Given `[agent]`, the sidebar refreshes on every transition out of the running state, which is precisely when the title node has finished writing.

<ExampleCode file="threads.component.ts" region="refresh-on-run-end" title="threads.component.ts — refresh" />

Apps that draw their own list can call `refreshOnRunEnd(agent, threads)` from `@threadplane/angular` inside an injection context instead.

### Switching and creating

Two handlers close the loop. Selecting a row tells the agent to load that thread and updates the signal; New chat in the sidebar and the header's "New conversation" button both ask the store for a thread and then activate it. `create()` returns `null` when the request fails, which is why the result is checked before it is used.

<ExampleCode file="threads.component.ts" region="switch-and-create" title="threads.component.ts — switching and creating" />

Each handler calls both `agent.switchThread(id)` and `activeThreadId.set(id)`. `switchThread(id)` replaces the session underneath the agent and reads that thread's saved history, and it reloads the thread when the id is already current. Setting the signal keeps the sidebar highlight, and anything else that reads it, in step; the agent sees an id it is already on and does not switch again.

## Connected sidebar

`<chat-thread-sidebar>` from `@threadplane/chat` draws New chat, Projects, Recent and Archived for any `ThreadDirectory`. `injectThreadDirectory()` exposes the provided one as `directory`, so the minimal setup is the provider plus the component:

```typescript
// app.config.ts
import { provideThreadDirectory } from '@threadplane/angular';
import { createLangGraphThreadDirectory } from '@threadplane/langgraph';

providers: [
  provideThreadDirectory({
    createDirectory: () =>
      createLangGraphThreadDirectory({ apiUrl: 'http://localhost:2024' }),
  }),
];
```

```typescript
import { Component, signal } from '@angular/core';
import { ChatThreadSidebarComponent } from '@threadplane/chat';
import { injectAgent, injectThreadDirectory } from '@threadplane/angular';

@Component({
  selector: 'app-threads',
  imports: [ChatThreadSidebarComponent],
  template: `
    <chat-thread-sidebar
      [directory]="threads.directory"
      [agent]="agent"
      [activeThreadId]="agent.threadId()"
      [selectedProjectId]="projectId()"
      (threadSelected)="agent.switchThread($event)"
      (projectSelected)="selectProject($event)"
      (activeThreadRemoved)="agent.switchThread(null)" />
  `,
})
export class ThreadsPanelComponent {
  protected readonly threads = injectThreadDirectory();
  protected readonly agent = injectAgent();
  protected readonly projectId = signal<string | null>(null);

  protected selectProject(id: string | null): void {
    this.projectId.update((current) => (current === id ? null : id));
  }
}
```

`agent.threadId()` is the thread the agent is on, and `agent.switchThread(id)` moves it to another one, or to a new empty conversation with `null`. With no listener on `(newChat)`, New chat calls `directory.create()` and emits `threadSelected` with the new identifier. The injected view owns the directory: the sidebar unsubscribes when it is destroyed but never disposes it.

### Projects

Project names are stored in the LangGraph Store under the namespace `['threadplane', 'projects']`. Each project is one item whose key is the project identifier and whose value is `{ name }`. A thread joins a project through its `projectId` metadata. To turn projects off, pass `projects: false` to `createLangGraphThreadDirectory()`; to keep the names somewhere else, pass your own `ProjectStore` as `projects`. A server without the Store API still lists threads: the view's `projects()` signal is `undefined`, the sidebar hides the Projects section and project commands fail without affecting the thread list.

`[selectedProjectId]` is controlled by the application. When it holds a project identifier, Recent and Archived list only that project's conversations; `null` lists every conversation. `(projectSelected)` emits the project the user picked so the component above clears the selection when the selected project is picked again. The sidebar lists every conversation when the selected identifier matches no project in the directory, and it emits `(projectSelected)` with `null` after the selected project is deleted from the sidebar.

The injected view also exposes `threads()`, `archivedThreads()`, `status()`, `error()`, `isLoading()` and `projects()` signals for applications that draw their own list. `status()` is `'loading'` until the first successful load and while recovering from an error, `'error'` after a failed load and `'idle'` otherwise. Nothing is read until `refresh()` is called, and a failed load is published through `status()` and `error()` rather than thrown. The directory reads one page of 50 conversations.

### Refreshing the sidebar after a run

The sidebar loads the directory when it mounts and again after each row command. Pass `[agent]` and it also refreshes every time a run ends, which is when the graph has written a generated title.

### The active thread

The sidebar never owns the selection. Bind `[activeThreadId]` to highlight a row and handle `(threadSelected)` to switch. When the user deletes the conversation that is active, `(activeThreadRemoved)` fires after the delete succeeds, so the application can return to a new chat.

### Four levels of customization

1. **Features and labels.** The `[features]` input turns built-in behavior off: `projects`, `archive`, `pin`, `reorder`, `rename` and `remove`. Each defaults to on when the directory supports it. The `[labels]` input replaces text for `newChat`, `projects`, `recent`, `archived`, `archivedEmpty`, `loadError`, `retry` and `empty`.
2. **Slots.** An `ng-template[chatThreadRow]` replaces each conversation row, with the thread as `let-thread` and `isActive` in the context. `[extraActions]` appends application commands to each row menu, and content marked `chatThreadSidebarBefore` or `chatThreadSidebarAfter` places sections around the built-in ones. Rows drawn by a template get no row menu.
3. **Your own directory.** `[directory]` accepts any object that meets `ThreadDirectory`, so an application without a LangGraph server can supply its own list and commands. The sidebar offers a command only when the directory implements it.
4. **Lower-level pieces.** `<chat-thread-list>`, `<chat-project-list>` and `<chat-sidenav>` remain public for applications that want full control over layout and behavior.

## Routing a URL to a thread

The example stops at an in-memory signal, which is the right choice for a surface with no visible URL. When the address bar is visible and the user may share it, `injectThreadRouting()` binds the same signal to the Angular Router: it restores the thread id from the URL on load, stamps signal changes back into the URL, validates stale links, and treats a bare URL as "no thread". The URL is the sole source of truth, and nothing is written to `localStorage`.

| Behavior | Detail |
|---|---|
| Restore on load | Reads the thread id from the URL on startup and seeds the signal |
| Signal to URL | When the signal changes, navigates to the matching URL |
| URL to signal | On every `NavigationEnd`, keeps the signal in sync with the current URL |
| Validate stale links | When `validate` resolves `false`, redirects to the bare path with `replaceUrl: true` |
| Bare URL is the welcome state | When the URL holds no thread segment, the signal is `null` |

Given the module-scoped signal and the directory the example already has, adding the URL layer is one call from an injection context:

```typescript
import { Component } from '@angular/core';
import { injectThreadRouting } from '@threadplane/chat';
import { injectThreadDirectory } from '@threadplane/angular';
import { activeThreadIdState } from './threads.component';

@Component({ /* ... */ })
export class ShellComponent {
  private readonly threads = injectThreadDirectory();

  constructor() {
    injectThreadRouting({
      threadId: activeThreadIdState,
      validate: (id) => this.threads.getThread(id).then(Boolean),
    });
  }
}
```

`injectThreadRouting()` calls `inject(Router)` internally, so it must run in an injection context: a constructor body, as above, or a field initializer. The `validate` callback receives every candidate id the URL produces.

`getThread()` resolves with the thread, resolves `null` when the backend says there is no such thread, and rejects when that could not be determined. The core `ThreadDirectory` contract has no command that reads one thread, and the LangGraph directory lists a single page, so on its own the view can answer only for a thread in that list. Give the provider a `getThread` that asks the backend, so a stale link resolves `null` and redirects:

```typescript
import { provideThreadDirectory } from '@threadplane/angular';
import {
  createLangGraphClient,
  createLangGraphThreadDirectory,
} from '@threadplane/langgraph';

const client = createLangGraphClient('http://localhost:2024');

provideThreadDirectory({
  createDirectory: () => createLangGraphThreadDirectory({ client }),
  getThread: async (threadId) => {
    try {
      const thread = await client.threads.get(threadId);
      const metadata = thread.metadata ?? {};
      return {
        id: thread.thread_id,
        title: typeof metadata['title'] === 'string' ? metadata['title'] : 'New chat',
        pinned: metadata['pinned'] === true,
        archived: metadata['archived'] === true,
        projectId: typeof metadata['projectId'] === 'string' ? metadata['projectId'] : null,
      };
    } catch (error) {
      // 404: no such thread. 422: the id is not a valid UUID.
      const status = (error as { status?: number }).status;
      if (status === 404 || status === 422) return null;
      throw error;
    }
  },
});
```

Rethrowing every other failure matters: a network error then leaves the user on the thread they asked for, and a redirect happens only when the thread is really gone.

### Custom URL shapes

The defaults are `/` for the welcome state and `/<threadId>` for a conversation. Supply `toCommands` and `threadIdFromUrl` for mode-prefixed or nested paths:

```typescript
import { activeThreadIdState } from './threads.component';

const MODES = ['embed', 'popup', 'sidebar'] as const;
type DemoMode = (typeof MODES)[number];

function parseUrl(url: string): { mode: DemoMode; threadId: string | null } {
  const segs = url.split('?')[0].split('#')[0].split('/').filter(Boolean);
  const mode = (MODES as readonly string[]).includes(segs[0])
    ? (segs[0] as DemoMode)
    : 'embed';
  const threadId = segs[1]?.length ? segs[1] : null;
  return { mode, threadId };
}

// Inside the shell constructor — `this.mode()` reads the current mode signal:
injectThreadRouting({
  threadId: activeThreadIdState,
  threadIdFromUrl: (url) => parseUrl(url).threadId,
  toCommands: (id) => (id ? ['/', this.mode(), id] : ['/', this.mode()]),
  validate: (id) => this.threads.getThread(id).then(Boolean),
});
```

`threadIdFromUrl` extracts the id from whatever URL the router lands on, and `toCommands` builds the navigate command array for an id, or for `null` when the conversation is cleared.

### Configuration reference

```typescript
import { injectThreadRouting, type ThreadRoutingConfig } from '@threadplane/chat';
import { WritableSignal } from '@angular/core';
import { NavigationExtras } from '@angular/router';

export interface ThreadRoutingConfig {
  /** App-owned signal that is the source of truth for the active thread. */
  threadId: WritableSignal<string | null>;
  /** Build router commands for a thread id (null = welcome/bare path).
   *  Default: (id) => id ? ['/', id] : ['/'] */
  toCommands?: (id: string | null) => unknown[];
  /** Extract a thread id from a URL string (null = no thread).
   *  Default: the last non-empty path segment. */
  threadIdFromUrl?: (url: string) => string | null;
  /** Async check; on false, redirect to the bare path (replaceUrl: true).
   *  Omit when the backend has no thread-lookup endpoint. */
  validate?: (id: string) => Promise<boolean>;
  /** Extras merged into every navigate call.
   *  Default: { queryParamsHandling: 'preserve' } */
  navigationExtras?: NavigationExtras;
}

function injectThreadRouting(config: ThreadRoutingConfig): void;
```

## When to use URL-backed threads

Reach for `injectThreadRouting()` when both of these hold:

1. **The user sees the URL and may share it.** A standalone application at its own route is the typical case. Inside an iframe whose address is never surfaced, URL persistence adds plumbing and buys nothing; keep the active thread in a plain signal, as the example does.

2. **The backend can restore the conversation from the id.** A LangGraph server backed by a durable checkpointer satisfies this. An in-process `MemorySaver` does not: the id survives the reload but the state behind it does not, so the surface comes back empty while the URL still looks correct.

The principle underneath is that persistence in the interface should match what the backend can actually restore. A stateless server should not offer bookmarkable conversation links.

<Callout type="info" title="AG-UI backends">
The AG-UI protocol is event-stream only, and it defines no server-side thread-lookup endpoint, so there is nothing for `validate` to call. With `@threadplane/ag-ui`, pass no `validate` callback. The agent still follows the `threadId` signal and asks `createSession` for a session on that thread; whether the conversation comes back depends on the `replay` or `persistence` option you give that session. See [AG-UI architecture](/docs/angular/ag-ui/concepts/architecture) for details.
</Callout>
