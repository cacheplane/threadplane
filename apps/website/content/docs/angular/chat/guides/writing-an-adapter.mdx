# Writing an Adapter

Learn how to implement a custom `AgentSession` so `@threadplane/chat` components work with any backend — a custom RPC service, an in-process mock, or an exotic streaming protocol.

## When to Write Your Own Adapter

`@threadplane/langgraph` covers LangGraph backends and `@threadplane/ag-ui` covers any [AG-UI-compatible](https://docs.ag-ui.com) backend. Everything else needs a session of your own. Common scenarios:

- **Custom RPC or HTTP API** — your backend speaks neither LangGraph Server nor the AG-UI protocol.
- **In-process logic** — you want the chat UI without any network call (demos, playgrounds, offline-first apps).
- **Testing** — a deterministic in-process session is faster and more reliable than hitting a real agent in unit tests. Check `createFakeAgentSession` from `@threadplane/core/testing` before writing one for this purpose.
- **Exotic transports** — WebSockets, gRPC-Web, or any other streaming mechanism.

## The Contract

The extension point is `AgentSession` from `@threadplane/core`. It is a plain object with no framework in it: no Angular signals, no RxJS, no dependency injection.

```typescript
import type { AgentSession } from '@threadplane/core';
```

A session publishes one immutable **snapshot** through `getSnapshot()`, tells listeners when it changed through `subscribe()`, and takes **commands**: `submit` to send a message, `stop` to abort the run in flight, and `dispose` to release everything. `provideAgent({ createSession })` from `@threadplane/angular` turns any session into the `Agent` the chat components read: each snapshot field becomes a signal (`agent.messages()`, `agent.status()`) and each command passes through with its own signature.

## Member-by-Member Reference

Required members:

| Member | Type | What you supply |
|---|---|---|
| `getSnapshot` | `() => AgentSnapshot` | The current aggregate. Return the same object until something changes |
| `subscribe` | `(notify: () => void) => () => void` | Register a listener for changes only, and return an idempotent release. Do not notify for the initial state |
| `submit` | `(input, options?) => Promise<CompleteOutcome>` | Send a message. `input` is the text, or `{ message, blocks?, state? }`. Resolve with `'success'`, `'error'`, `'aborted'`, `'interrupted'` or `'paused'` |
| `stop` | `() => Promise<void>` | Abort the run in flight |
| `dispose` | `() => Promise<void>` | Release timers, connections and listeners. Nothing is published afterwards |

Required snapshot fields:

| Field | Type | What you supply |
|---|---|---|
| `status` | `AgentStatus` | `'idle' \| 'running' \| 'error'` |
| `messages` | `readonly Message[]` | The conversation so far. Each message has an `id`, a `role`, text `content` and a `delivery` |
| `toolCalls` | `readonly ToolCall[]` | Tool invocations with finalized arguments, and their results |

Optional snapshot fields, each absent on a session that has nothing to report: `error` (an `AgentError`, only while `status` is `'error'`), `errorDiagnostic`, `state`, `interrupts`, `subagents`, `plan`, `usage`, `streamingToolCalls`, `pendingClientTools`, `checkpoints`, `messageCheckpoints` and `inputBlocked`.

Optional commands:

| Member | Type | What you supply |
|---|---|---|
| `resume?` | `(responses, options?) => Promise<CompleteOutcome>` | Answer the interrupts the snapshot lists and continue the paused work |
| `retry?` | `() => Promise<CompleteOutcome>` | Send the last failed submission again, appending no second user message |
| `regenerate?` | `(messageId, options?) => Promise<CompleteOutcome>` | Answer the prompt behind one assistant message again. Takes the message `id` |
| `runWithoutMessage?` | `(input?, options?) => Promise<CompleteOutcome>` | Run the agent on the conversation as it stands, appending no user message |
| `checkStatus?` | `() => Promise<void>` | Read-only reconciliation of an uncertain run outcome — see [Interruption Recovery](#interruption-recovery-optional) below |
| `onCustomEvent?` | `(listener) => () => void` | Deliver application events while runs stream, and return an idempotent release |
| `clientTools?` | `AgentClientTools` | Client-declared, client-executed tools — see [Client Tools](#client-tools-optional) below |

<Callout type="info" title="Optional members">
A session that cannot do something leaves the command undefined. On the injected `Agent` that command reads as `undefined` too, and the chat components offer no control for it: no regenerate button without `regenerate`, no retry without `retry`.
</Callout>

<Callout type="tip" title="Snapshots and events">
The design invariant is: **state lives in the snapshot; `onCustomEvent` carries only things that are not derivable from it.** Events are not replayed to a listener added later. Publish owned, frozen plain data: no `Error` instances, SDK objects or functions in a snapshot.
</Callout>

## Worked Example: An In-Process Echo Session

Below is a complete `createEchoSession` factory that satisfies the required contract without any network call. It shows the snapshot pattern clearly and is a solid starting point for your own session.

On `submit`, the factory appends a complete user message and starts an assistant delivery generation. After a short delay it completes that same generation with a successful echo; stopping early completes it as aborted. There are no tool calls, custom events, or interrupts.

```typescript
import {
  completeDelivery,
  staticDelivery,
  streamingDelivery,
  type AgentSession,
  type AgentSnapshot,
  type AgentSubmitInput,
  type CompleteOutcome,
  type Message,
} from '@threadplane/core';

export interface EchoSessionOptions {
  /** Delay before the echoed reply appears, in ms. Defaults to 400. */
  delayMs?: number;
}

export function createEchoSession(options: EchoSessionOptions = {}): AgentSession {
  // The snapshot is replaced, never mutated, and every published value is frozen.
  let snapshot: AgentSnapshot = Object.freeze({
    status: 'idle',
    messages: Object.freeze([]),
    toolCalls: Object.freeze([]),
  });
  const listeners = new Set<() => void>();
  let active: { finish(outcome: CompleteOutcome): void } | undefined;
  let disposed = false;
  let sequence = 0;
  const nextId = (prefix: string) => `${prefix}-${++sequence}`;

  function publish(messages: readonly Message[], status: AgentSnapshot['status']) {
    snapshot = Object.freeze({
      ...snapshot,
      status,
      messages: Object.freeze(messages.map((message) => Object.freeze(message))),
    });
    for (const notify of [...listeners]) notify();
  }

  function submit(input: AgentSubmitInput): Promise<CompleteOutcome> {
    if (disposed) return Promise.resolve('aborted');
    // A new submission replaces the reply that is still on its way.
    active?.finish('aborted');

    const text = typeof input === 'string' ? input : input.message;
    const userId = nextId('user');
    const assistantId = nextId('assistant');
    const generation = nextId('generation');

    // Static user input is already complete. The assistant owns a new
    // generation that stays the same until this attempt reaches an outcome.
    publish(
      [
        ...snapshot.messages,
        { id: userId, role: 'user', content: text, delivery: staticDelivery(userId) },
        { id: assistantId, role: 'assistant', content: '', delivery: streamingDelivery(generation) },
      ],
      'running',
    );

    return new Promise<CompleteOutcome>((resolve) => {
      const settle = (outcome: CompleteOutcome, content: string) => {
        clearTimeout(timer);
        active = undefined;
        publish(
          snapshot.messages.map((message) =>
            message.id === assistantId
              ? { ...message, content, delivery: completeDelivery(generation, outcome) }
              : message,
          ),
          'idle',
        );
        resolve(outcome);
      };
      const timer = setTimeout(
        () => settle('success', `You said: ${text}`),
        options.delayMs ?? 400,
      );
      active = { finish: (outcome) => settle(outcome, '') };
    });
  }

  return {
    getSnapshot: () => snapshot,
    // Changes only: a new listener is not called for the current snapshot.
    subscribe(notify) {
      listeners.add(notify);
      return () => {
        listeners.delete(notify);
      };
    },
    submit,
    async stop() {
      active?.finish('aborted');
    },
    async dispose() {
      active?.finish('aborted');
      disposed = true;
      listeners.clear();
    },
  };
}
```

## Wiring It Into a Component

Hand the factory to `provideAgent()` from `@threadplane/angular`. It is the same provider the LangGraph and AG-UI sessions use, so the component code does not change when you swap backends.

```typescript
// app.config.ts
import { ApplicationConfig } from '@angular/core';
import { provideAgent } from '@threadplane/angular';
import { createEchoSession } from './echo-session';

export const appConfig: ApplicationConfig = {
  providers: [
    provideAgent({
      createSession: () => createEchoSession({ delayMs: 250 }),
    }),
  ],
};
```

```typescript
// app.ts
import { Component } from '@angular/core';
import { ChatComponent } from '@threadplane/chat';
import { injectAgent } from '@threadplane/angular';

@Component({
  selector: 'app-root',
  standalone: true,
  imports: [ChatComponent],
  template: `<chat [agent]="agent" />`,
})
export class App {
  protected readonly agent = injectAgent();
}
```

`createSession` receives a context: `threadId` (the thread to open, or `null` for a new conversation), `onThreadId` (call it with the id of a thread your session created), `clientOptions` and `reportOperationFailure`. The echo session ignores it because it has no threads. The agent owns every session the factory returns and disposes it.

<Callout type="tip" title="Typed access to your own members">
`injectAgent()` is typed by the core contract. To reach fields and commands your session adds, create a ref with `createAgentRef<MySession>('my-agent')`, pass it to `provideAgent(ref, config)` and inject with `injectAgent(ref)`. If your session adds an optional command of its own, list its name in the config's `optionalCommands` so the agent reads it as `undefined` while the session lacks it.
</Callout>

## Validating with the Conformance Suite

`@threadplane/core/testing` ships conformance suites that check the required members and a handful of semantic invariants (for example, `getSnapshot()` must return the same object until something changes). `@threadplane/chat/testing` binds them to Vitest, so a spec is one call:

```typescript
// echo-session.conformance.spec.ts
import { runAgentConformance } from '@threadplane/chat/testing';
import { createEchoSession } from './echo-session';

runAgentConformance('createEchoSession', () => createEchoSession());
```

The conformance suite verifies:

- `getSnapshot`, `subscribe`, `submit`, `stop` and `dispose` are present, and every optional command is either undefined or a function.
- The snapshot has a valid `status`, and `messages` and `toolCalls` arrays whose entries have the required shape; an `error` is held only with the `'error'` status.
- The snapshot, `messages` and `toolCalls` are frozen, and the snapshot keeps its reference between changes.
- `subscribe` does not notify for the initial state and its release is idempotent.
- `submit`, `stop` and `dispose` return promises, a settled `submit` resolves with a valid outcome, and a disposed session notifies nobody.

With another test runner, import `runAgentSessionConformance(label, factory, { describe, it })` from `@threadplane/core/testing` and pass that runner's `describe` and `it`. Each suite also has a `...Scenarios` form that returns the checks as a map of named functions.

## History (Optional)

If your backend supports checkpointing or thread history, publish it in the snapshot:

```typescript
import type { AgentCheckpoint } from '@threadplane/core';
```

`snapshot.checkpoints` lists the saved history the session last loaded, oldest first. Each `AgentCheckpoint` has the backend's `id`, a display `label`, and the state `values` at that point. `snapshot.messageCheckpoints` maps an assistant message `id` to the `id` of the checkpoint that first held it. The timeline components and the debug panel read both.

Use `runAgentWithHistoryConformance` from `@threadplane/chat/testing` in your spec instead of `runAgentConformance` to cover the additional fields. Its factory receives a `seed` with the checkpoints the session must publish.

### Hydrating from a server-stored thread

A session belongs to one thread. The injected `Agent` outlives it: `agent.switchThread(id)`, or a change of the configured `threadId` signal, asks `createSession` for a new session with that id in `context.threadId`, then stops and disposes the old one. So a session never has to handle a thread id that changes. It has to answer a narrower question:

**When it is created for a thread it did not just create, should `messages` and `state` re-populate from the server's record of that thread?**

The chat UI assumes "yes" implicitly — clicking a thread in a sidebar list, or rehydrating a saved id on reload, both rely on the session pulling the prior conversation back into view. If the session starts empty, the UI shows an empty welcome surface and the user loses their conversation.

How the sessions in this repo answer the question:

- **`@threadplane/langgraph`** exposes an optional `load()` command that reads the thread's history and publishes the newest checkpoint's messages and state. The Angular agent calls `load()` whenever it opens a session for a non-null thread, and `agent.isThreadLoading()` is true meanwhile. Child agents are rebuilt from history only on a session created with `restoreSubagents: true`, and a reloaded thread carries less than the live view saw; the persistence guide lists what it does and does not show. See the [LangGraph persistence guide](/docs/angular/langgraph/guides/persistence) for the consumer-side shape.
- **`@threadplane/ag-ui`** restores a conversation at creation when the host supplies `replay` or `persistence`. With a `threadId`, `createSession()` can load server-retained events through `replay` and rebuild the view. The protocol does not define a standard history endpoint, so the application supplies that source. See [Restoring a thread from the server](/docs/angular/ag-ui/guides/deployment#restoring-a-thread-from-the-server).

For your own session, either offer a `load()` method, which the agent calls for you and tracks through `isThreadLoading()`, or hydrate inside the factory before accepting commands. State who supplies the history source, and publish `inputBlocked` while the conversation is incomplete so the UI does not send against it.

## Client Tools (Optional)

If your runtime lets the browser declare tools the model can call, implement the optional `clientTools` capability. Consumers then get [client tools](/docs/angular/chat/guides/client-tools) with no further work.

```typescript
import type { AgentClientTools } from '@threadplane/core';
```

| Member | Required | What you supply |
|---|---|---|
| `setCatalog(specs)` | yes | Store the catalog; ship it with every outbound run |
| `resolve(id, result)` | yes | Record the result **and continue the run** |
| `settle?(id, result)` | no | Record the result **without** continuing |
| `flush?()` | no | Make everything recorded via `settle` durable, still without continuing |

The calls awaiting a browser result are not on the capability: publish them as `snapshot.pendingClientTools`. A call is pending when the run is **not** in flight, its name is in the catalog, it has no backend result, and it has not already been settled locally. Each pending call is also listed in `toolCalls`.

### The invariant

> **The server thread must never hold a client tool call without a corresponding tool result.**

Violate it and the thread carries an assistant message with `tool_calls` and no matching tool message; most providers reject that history outright on the next user turn.

`resolve()` alone cannot uphold this, because some groups never continue — every tool in them is terminal (`followUp: false`), the user pressed stop, or a continuation limit tripped. That is what `settle` + `flush` are for.

<Callout type="warning" title="flush() is where durability actually happens">
  If your `settle()` only records locally, you **must** implement `flush()` to write those results to the server. `@threadplane/langgraph` stages each settled result as a tool message and writes the staged messages in one `updateState` call on `flush()`, keeping them staged when the write fails. Omitting `flush()` when your `settle()` is not already durable silently drops results.
</Callout>

### Implementation rules

Four rules keep settlement, persistence, and recovery aligned:

1. **Give every result message a stable ID derived from its tool-call ID.** Replay and overlap are idempotent only when the receiving store uses ID-aware upsert or merge semantics. LangGraph's `add_messages` reducer does; a stable ID alone does not deduplicate an append-only sink.
2. **Snapshot without forgetting, and acknowledge only after that exact handoff reports success.** Failure, interruption, abort, pause, or supersession leaves the result staged for retry or an ordinary later submit. Overlapping operations may carry the same stable ID only when the receiving path provides the ID-aware merge described above.
3. **Chain concurrent flushes instead of short-circuiting them.** Results settled after one snapshot need their own write; returning only the older in-flight promise can report success without persisting the newer batch.
4. **Keep staged results inside the session.** A thread switch disposes the session, so results staged for one thread can never reach another. Make acknowledgments from work that outlives `dispose()` no-ops.

Sessions without a durable write path can fall back to attaching staged results to the next outbound run. The results stay buffered and an ordinary next message can still carry them, but a browser page reload first loses that in-memory fallback and leaves the server thread with an unanswered tool call.

## Interruption Recovery (Optional)

A stream that closes without terminal evidence is an interruption, not a completed turn. Publish it as an `AgentError` with `kind: 'interrupted'`, resolve the command with the `'interrupted'` outcome, keep whatever content and approval state arrived, and say on `recovery` which action you can justify.

| `recovery` | Set it when | `retryable` | `detail` |
|---|---|---|---|
| `retry` | You can prove the request was never dispatched, so replaying it cannot duplicate server-side work | `true` | omit |
| `check` | The outcome is uncertain and your backend can be asked, read-only, what happened | `false` | supply |
| `none` | The outcome is uncertain and nothing can verify it | `false` | supply |

`retry` is the narrow case. Anything the server may already have begun answering is not retryable, because a replay could duplicate a tool call or a booking. The error's `message` and `detail` are display text you write; keep the wording the same for the same recovery across your transports.

Implement `retry` so it sends the last failed submission again without a second user message, resolves `'aborted'` without sending while a request runs or when nothing failed, and rejects for an error whose `recovery` is not `'retry'`.

Implement `checkStatus` on exactly the condition under which you report `recovery: 'check'`, so the control and the recovery it is offered for can never disagree. It must not resubmit the operation and must not append a message; a dropped stream is not proof that the server did nothing. Report the answer in the snapshot — clear `error` and return `status` to idle for a run the backend reports as finished, and leave the error in place when the outcome stays unknown, so the caller can ask again. Reject while a request is in flight, and discard a result that resolves after a newer request has started.

## Interrupts (Optional)

A run that pauses for a person resolves with the `'paused'` outcome and lists what it waits on in `snapshot.interrupts`. Each `AgentInterrupt` has an `id` and may carry the backend's `value`, a `reason`, a display `message` and the `toolCallId` it is about. `resume(responses)` answers them: each response names one pending interrupt and is `resolved`, optionally with a `value`, or `cancelled`. Reject a response that names an interrupt that is not pending, names one twice, or uses a status your backend cannot express.

`runInterruptConformance` from `@threadplane/chat/testing` checks this behaviour through a small harness that drives the pause and a failed request through your real session.

## Publishing Your Adapter

Want to distribute your session as an npm package? Keep the following in mind.

**Peer dependencies** to declare in your `package.json`:

```json
{
  "peerDependencies": {
    "@threadplane/core": ">=0.3.0 <0.4.0"
  },
  "devDependencies": {
    "@threadplane/core": "0.3.7"
  }
}
```

A session imports only `@threadplane/core`, so the package needs no Angular peer and the same build serves any framework binding. If the package also ships Angular code, such as a typed `AgentRef`, a provider helper or components, declare the full supported Angular range beside it:

```json
{
  "peerDependencies": {
    "@angular/core": "^20.0.0 || ^21.0.0 || ^22.0.0",
    "@threadplane/angular": ">=0.3.0 <0.4.0",
    "@threadplane/core": ">=0.3.0 <0.4.0"
  }
}
```

The conformance suites live in `@threadplane/core/testing`, part of the same package, so there is nothing extra to install for them; add `@threadplane/chat` as a development dependency only if you want its Vitest-bound runners.

While `@threadplane/core` is pre-1.0, every minor release can carry a breaking change. Use an explicit range that stops before the next minor, and widen it as you verify newer releases. The backend packages in this repository pin the exact version they were built against.

**Naming convention:** `@your-org/your-backend-session` works well (e.g., `@acme/supabase-realtime-session`). Export a `createSession(options)` factory, as `@threadplane/langgraph` and `@threadplane/ag-ui` do, so an application writes the same `provideAgent({ createSession })` for every backend.

**Library setup:** A session is plain TypeScript. Build it with `tsc` or any bundler and point your `package.json` exports at the compiled output; ng-packagr is only needed if the package also ships Angular components.
