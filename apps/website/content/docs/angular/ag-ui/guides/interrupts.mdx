# Interrupts

Interrupts let an AG-UI agent pause mid-run and hand control to a human. The agent proposes an action, the run freezes, your Angular UI shows an approval card, the person decides, and the agent resumes with that decision. The AG-UI session publishes the pending interrupts, and `injectAgent()` from `@threadplane/angular` surfaces them as an Angular Signal, so the approval flow needs no manual event wiring. The running example is a refund authorization, and this guide walks the four files that make it work.

<HumanApprovalFlow />

<Callout type="info" title="When to use interrupts">
Use interrupts when an agent action is irreversible (sending an email, placing an order, issuing a refund), when the agent needs a human decision it cannot make on its own, or when compliance requires explicit approval before execution.
</Callout>

## What the demo does

The Run tab shows the prebuilt `<chat>` composition in front of a refund graph served over AG-UI. Ask for a refund and the agent acknowledges the draft in the transcript, and then the run stops: an approval panel appears at the end of the conversation with the amount, the customer identifier, and the reason the agent extracted from your request, above three buttons: Issue refund, Edit, and one that declines the refund.

Two welcome suggestions set it up. "Refund a duplicate charge" asks for $47.50 back to customer `cus_a8x2k`, and "Refund a chargeback" asks for $129.00 with a different justification, so you can watch the same pause fire on two different payloads.

Approve resumes the graph, which issues a stand-in refund and posts the refund ID into the transcript. Cancel resumes it with a rejection, and the graph says so and issues nothing. Edit keeps the card open, reveals an amount field, and resumes with an amount the operator chose rather than the one the agent proposed.

### Pausing at interrupt()

`interrupt()` freezes the graph and hands its argument to the transport. The argument is any JSON-serializable value, and it becomes the payload your component renders. When the client resumes, that same call returns the resume value, so the node reads like a straight-line function even though a human answered in the middle of it.

Notice the `kind` field on the payload, which is how the frontend tells this interrupt apart from any other one the graph might raise, and notice that the node treats a resume value that is not a dictionary, or whose `approved` is missing or false, as a rejection.

<Callout type="tip" title="A resumed node re-executes from the top">
LangGraph resumes by running the interrupting node again, and `interrupt()` returns the resume value instead of pausing a second time. Every line above the `interrupt()` call runs again, including on later retries, so keep that stretch free of side effects. Reading state, as the example does, is safe; charging a card there is not.
</Callout>

### Routing on the decision

After the pause the graph branches. A conditional edge sends an approved refund to the node that issues it and sends everything else to the end, which is why the rejection message is written by the interrupting node itself.

<ExampleCode file="graph.py" region="graph" title="graph.py — issuing and routing" />

The graph compiles with `MemorySaver()` because `ag-ui-langgraph` reads the thread's graph state through a checkpointer, so a graph served this way needs one; a paused graph is also a stored checkpoint, which is what the resume reads back.

<Callout type="warning" title="MemorySaver is a development choice">
An in-memory checkpointer loses every paused run when the process restarts. A deployment that must survive a restart needs a durable saver, such as the Postgres checkpointer, behind the same `checkpointer=` argument.
</Callout>

The panel leads with "Waiting for your approval.", then the `title` as the request, the `#body` content, and the actions. Focus moves to the first action when the panel appears. While it waits, the composer reads "Answer the approval to continue", and after you answer, focus returns to the composer.

For an action that cannot be undone, add `[destructive]="true"`. ## The wire format

The example never touches the protocol, but it is worth knowing what crosses it. An interrupt reaches the browser as an AG-UI `CUSTOM` event named `on_interrupt`, carrying the value the graph passed to `interrupt()`:

```json
{
  "type": "CUSTOM",
  "name": "on_interrupt",
  "value": "{\"kind\":\"refund_approval\",\"amount\":47.5,\"customer_id\":\"cus_a8x2k\",\"reason\":\"Duplicate charge\"}"
}
```

The `ag-ui-langgraph` package serializes the payload, so `value` arrives as a JSON string rather than an object. The session parses it before exposing the interrupt. With a transport profile that answers notices, this event begins a pause; the pause becomes ready to answer once the run that carried it has settled, which the run's ordinary `RUN_FINISHED` does.

Resuming travels the other way. For a payload shaped like this one — an application object with no runtime-specific identifiers — `resume(responses)` under `'auto'` sends the response's `value` as `forwardedProps.command.resume`, the convention `ag-ui-langgraph` reads to resume the checkpoint. The request carries no top-level `resume`.

<Callout type="info" title="The backend does not unwrap anything">
In the graph node, `interrupt({...})` returns the resume value directly. The wrapper reads `forwarded_props.command.resume` and applies it before the graph continues.
</Callout>

Other runtimes signal a pause differently: a `RUN_FINISHED` event carrying the protocol's own interrupt outcome records the full batch, and its response goes out as the protocol's top-level `resume` array. That outcome is what a session answers by default, and under `'auto'` it wins over a `CUSTOM on_interrupt` notice in the same run. The [event mapping reference](/docs/angular/ag-ui/reference/event-mapping) covers the event surface in full.

## Pending batches and transport selection

`interrupts()` is the core display field: every interrupt a paused run waits on, from the pause until an answer is sent. For the protocol's own outcome each entry has the protocol's `id`, `reason`, `message` and `toolCallId`, and its `value` is the entry's `metadata`. For a notice there is one entry, `{ id, reason: 'on_interrupt', value, toolCallId? }`. Use `interruptSession(snapshot)` from `@threadplane/ag-ui` for the full batch and its request ownership, or `decisionState(snapshot)` for the smaller view an approval control needs. Both read the `decision` and `run` fields of the snapshot:

```typescript
import { decisionState, interruptSession } from '@threadplane/ag-ui';

const evidence = { decision: agent.decision(), run: agent.run() };
const batch = interruptSession(evidence);   // { phase, id?, interrupts, runId?, command?, attempt? }
const pending = decisionState(evidence);    // undefined, { kind: 'unsupported' }, or { kind: 'native', id, interrupts, phase }
```

Render new decision controls only while the session's phase is `pending`, which `decisionState` reports as `ready`. Answering claims the batch and sends the request in one step, so a second answer cannot be sent concurrently.

| Phase | Meaning and UI behavior |
| --- | --- |
| `collecting` | The pausing run has not settled locally yet; wait. `decisionState` reports `observing`. |
| `pending` | Ready for a decision. `decisionState` reports `ready`. |
| `resuming` | An answer was claimed and its run is going; disable new decisions. `decisionState` reports `answering`. |
| `acknowledged` | The answering run reported `RUN_STARTED` and is going. Only a session with `persistence` records this. |
| `uncertain` | The answering run ended with no proof the backend took the answer. It cannot be sent again. |
| `recovery-required` | The answering run ended after it had started on the backend; reconcile. Only a session with `persistence` reports this. |
| `unsupported` | A pause this session cannot answer, such as a batch with duplicate interrupt IDs, or a notice under the default `'protocol'` transport while its run is still going. |
| `none` | Nothing is waiting. |

Acknowledgement and disappearance of the approval card do not prove backend completion.

`resume` takes one response per pending interrupt:

```typescript
await agent.resume([
  { interruptId: 'approval-1', status: 'resolved', value: { approved: true } },
  { interruptId: 'approval-2', status: 'cancelled' },
]);
```

Use IDs from `interrupts()`, not the illustrative IDs above. Every pending ID must appear exactly once; a missing, duplicate, or unknown ID, and an expired interrupt, reject the call with nothing sent. A cancelled entry cannot carry a value. A resolved entry may omit `value`. The request carries the value as the protocol's `payload`. `resume` also rejects when no interrupt is waiting, and ordinary input cannot abandon a pending approval: `submit` resolves `'error'` without sending, and `inputBlocked()` reads `{ reason: 'decision' }`.

To reject a decision from an old approval control, capture the pause's `id` from `decisionState(snapshot)` or `interruptSession(snapshot)` when rendering it and pass `agent.resume(responses, { pause })`. The session checks this optional pause before claiming the batch or sending anything. The `id` changes with every new pause, even if the runtime reuses interrupt IDs.

Set `interruptTransport` in `createSession()` when the backend requires a specific format:

| Value | Resume format |
| --- | --- |
| `protocol` (default) | Top-level `resume` entries correlated with the protocol's interrupt IDs. A `CUSTOM on_interrupt` notice cannot be answered. |
| `auto` | The protocol's own format when its outcome is present; otherwise the Mastra command for a notice whose value names a `toolCallId`, or the legacy command. |
| `legacy-command` | `forwardedProps.command.resume`, for every pause. |
| `mastra-command` | `forwardedProps.command.resume` plus `command.interruptEvent` containing `toolCallId` and the available `runId`, for every pause. Requires the notice's `toolCallId`. |

Choose `mastra-command` explicitly for the current Mastra command backend, including when it emits both the protocol's outcome and a notice. A command answers exactly one interrupt with a resolved response that has a value: under a command profile `resume` rejects a cancelled response, a missing value, and a batch of several interrupts.

### A single decision with rendered-pause protection

This is a complete standalone component for the refund notice above. Register a session with `interruptTransport: 'legacy-command'` (or `'auto'`) in the application providers and mount the component alongside the chat. The payload guard validates data before displaying it. The computed view captures the pause's `id` when Angular renders the controls; its callback retains that `id` even if an old control is invoked later.

```typescript
import { Component, computed, signal } from '@angular/core';
import { injectAgent } from '@threadplane/angular';
import { decisionState, type Session } from '@threadplane/ag-ui';

interface RefundApproval {
  kind: 'refund_approval';
  amount: number;
  customer_id: string;
  reason: string;
}

function isRefund(value: unknown): value is RefundApproval {
  if (typeof value !== 'object' || value === null) return false;
  const item = value as Record<string, unknown>;
  return item['kind'] === 'refund_approval' &&
    typeof item['amount'] === 'number' && Number.isFinite(item['amount']) &&
    typeof item['customer_id'] === 'string' &&
    typeof item['reason'] === 'string';
}

@Component({
  selector: 'app-refund-decision',
  standalone: true,
  template: `
    @if (!hydrated()) { <p>Loading saved approval…</p> }
    @if (error() || agent.error()?.message; as message) {
      <p role="alert">{{ message }}</p>
    }
    @if (busy() || agent.status() === 'running') { <p role="status">Working…</p> }
    @if (hydrated()) {
      @if (decision(); as view) {
        <p>{{ view.payload.customer_id }}: {{ view.payload.amount }}</p>
        <p>{{ view.payload.reason }}</p>
        <button [disabled]="busy() || agent.status() === 'running'"
          (click)="view.answer(true)">Approve</button>
        <button [disabled]="busy() || agent.status() === 'running'"
          (click)="view.answer(false)">Cancel</button>
      }
    }
  `,
})
export class RefundDecisionComponent {
  readonly agent = injectAgent<Session>();
  readonly hydrated = signal(false);
  readonly busy = signal(false);
  readonly error = signal('');
  readonly decision = computed(() => {
    const pending = decisionState({
      decision: this.agent.decision(),
      run: this.agent.run(),
    });
    if (pending?.kind !== 'native' || pending.phase !== 'ready') return undefined;
    const [interrupt] = pending.interrupts;
    const payload = interrupt?.value;
    if (!interrupt || !isRefund(payload)) return undefined;
    const pause = pending.id;
    return {
      payload,
      answer: (approved: boolean) => this.answer(interrupt.id, approved, pause),
    };
  });

  constructor() { void this.hydrate(); }

  private async hydrate(): Promise<void> {
    try {
      await this.agent.ready;
      this.hydrated.set(true);
    } catch (error) {
      this.error.set(error instanceof Error ? error.message : 'Restoration failed');
    }
  }

  private async answer(interruptId: string, approved: boolean, pause: string): Promise<void> {
    if (this.busy()) return;
    this.busy.set(true);
    this.error.set('');
    try {
      await this.agent.resume(
        [{ interruptId, status: 'resolved', value: { approved } }],
        { pause },
      );
    } catch (error) {
      this.error.set(error instanceof Error ? error.message : 'Decision failed');
    } finally {
      this.busy.set(false);
    }
  }
}
```

`approved: false` is this application's rejection decision. It is not a protocol-level cancelled entry. An unrecognized payload intentionally produces no refund controls; route other payload kinds to their own renderer.

### Cancelling a native batch

This complete helper requires the protocol's own interrupt outcome and a session that answers it natively: the default `'protocol'` transport, or `'auto'`. Call it while building the rendered view and bind the returned callback to its Cancel button; do not recreate it inside the click handler. Handle its rejected promise and disable the control while submitting, as in the component above.

```typescript
import type { Agent } from '@threadplane/angular';
import { interruptSession, type Session } from '@threadplane/ag-ui';

export function cancellationForRenderedBatch(agent: Agent<Session>) {
  const pending = interruptSession({
    decision: agent.decision(),
    run: agent.run(),
  });
  if (pending.phase !== 'pending' || pending.command || pending.interrupts.length === 0) {
    throw new Error('A pending native interrupt batch is required');
  }
  const responses = pending.interrupts.map(({ id }) => ({
    interruptId: id,
    status: 'cancelled' as const,
  }));
  return () => agent.resume(responses, { pause: pending.id });
}
```

Every observed ID appears exactly once, cancellation carries no value, and a stale pause is rejected. This protocol cancellation differs from sending the Mastra application's `{ approved: false }` decision through `mastra-command`.

## Failures, retry, and restoration

After a failed resume the session keeps the latest local state and history. There is no rollback, and nothing on the client can undo work already performed on the server.

An answer is sent again in exactly one case: its request provably reached no run. It was never made, or the backend refused it with its own `RUN_ERROR` before any `RUN_STARTED`. The pause is then pending again, `error().recovery` is `'retry'`, and `retry()` sends the same answers under a new run id. An answering run that reported `RUN_STARTED` and then failed, a response that was not OK, a lost connection, and a transport's own claim that a request did not leave are not proof: the decision stays `uncertain`, `retry()` rejects, and that answer is never sent twice.

Restoration is opt-in through `replay` or `persistence` in the `createSession()` options. A `replay` source loads the thread's protocol events from a server that kept them and restores a paused last run as a pending interrupt that `resume` answers; when it returns no events, or fails, hydration falls back to `persistence`. See [Restoring a thread from the server](/docs/angular/ag-ui/guides/deployment#restoring-a-thread-from-the-server). For `persistence`, the application supplies a stable `threadId`, a scoped `namespace`, and a store with `load(key)` and atomic `compareAndSwap(key, expectedRevision, next)` methods. A missing record uses `expectedRevision: null`. A write that loses its compare-and-swap is not retried, because another writer owns the thread: the session then reads `inputBlocked: { reason: 'storage' }` until reconciliation succeeds. The record retains the transcript, the state, the ended child agents, and the pending pause with its answer when one was sent. No browser storage backend is bundled.

Atomic storage claims coordinate clients sharing that store. Preventing duplicate backend side effects also requires server-side idempotency; a retained attempt alone cannot establish that guarantee.

Await `agent.ready` before rendering restored approval controls; commands also wait for hydration. A pause restored without an answer is ready. A pause restored with its answer is `uncertain`, because the record cannot say how that run ended: `resume` rejects, `submit` is refused, and only reconciliation continues. Configure `persistence.reconcile(record)` to obtain an authoritative backend outcome and call `agent.reconcileInterrupt()` to apply it. The callback returns `unknown`, or `pending`, `acknowledged`, or `completed` with the thread as it now stands. An unknown outcome keeps recovery blocked. The package does not provide a backend reconciliation endpoint, and stored client state cannot recreate a checkpoint lost by a restarted `MemorySaver` process.

`inputBlocked()` says why ordinary chat input is refused: `'hydrating'` while the thread is restored, `'checking'` during a status check, `'storage'` after a storage failure, and `'decision'` from a pause until its answer succeeds. The built-in composer disables itself while it is set and preserves drafts; approval controls still answer through `resume`.

### Test-only compare-and-swap store

This complete TypeScript example is non-durable and single-process. Its comparison and replacement run synchronously with no intervening `await`, which makes them atomic only among callers sharing this store instance. It loses all records when the process exits. Production storage must enforce the comparison and write atomically across the clients it coordinates; a `localStorage` read followed by a write does not provide that guarantee across tabs.

```typescript
import type { SessionPersistence, ThreadRecord } from '@threadplane/ag-ui';

export function createTestOnlyStore(): SessionPersistence['store'] {
  const records = new Map<string, ThreadRecord>();
  return {
    async load(key) {
      return structuredClone(records.get(key) ?? null);
    },
    async compareAndSwap(key, expectedRevision, next) {
      const currentRevision = records.get(key)?.revision ?? null;
      if (currentRevision !== expectedRevision) return false;
      const nextRevision = expectedRevision === null ? 0 : expectedRevision + 1;
      if (next.revision !== nextRevision) throw new Error('Invalid next revision');
      records.set(key, structuredClone(next));
      return true;
    },
  };
}

export async function demonstrateSingleWinner(): Promise<void> {
  const store = createTestOnlyStore();
  const record: ThreadRecord = {
    version: 1,
    namespace: 'test-only',
    threadId: 'thread-1',
    revision: 0,
    messages: [],
  };
  const key = JSON.stringify([record.namespace, record.threadId]);
  const results = await Promise.all([
    store.compareAndSwap(key, null, record),
    store.compareAndSwap(key, null, record),
  ]);
  if (results.filter(Boolean).length !== 1) throw new Error('Expected one winner');
  const saved = await store.load(key);
  if (saved?.revision !== 0) throw new Error('Unexpected saved revision');
}
```

The session creates the namespace/thread key and increments record revisions. This example demonstrates client storage ownership only; it makes no claim about backend execution occurring exactly once.

### Authoritative reconciliation

The result union is the exported `ReconcileAnswer`. This complete type-and-configuration helper leaves the authoritative lookup to your application:

```typescript
import type {
  ReconcileAnswer,
  SessionPersistence,
  ThreadRecord,
} from '@threadplane/ag-ui';

// ReconcileAnswer is:
//   | { status: 'unknown' }
//   | { status: 'pending' | 'acknowledged' | 'completed';
//       messages; state?; subagents?; pause? }

export function persistenceForApplication(
  namespace: string,
  store: SessionPersistence['store'],
  reconcile: (record: ThreadRecord) => Promise<ReconcileAnswer>,
): SessionPersistence {
  return { namespace, store, reconcile };
}
```

Your backend's durable execution/checkpoint records must establish the outcome and supply enough information for your application to report the thread as it now stands. Do not manufacture `pending` from a failed fetch or simply return the stored client record as proof. Return `unknown` when the outcome cannot be established; recovery remains blocked. Threadplane supplies no reconciliation HTTP endpoint.

`pending` means the pause still waits and no answer arrived: its `pause` has no `attempt`. `acknowledged` means the answer arrived and its run started, and how it ended is not known: its `pause` keeps the `attempt`. `completed` means the answer's run ended: `pause` is absent, or is a new pause from another run. An answer that does not fit its status is rejected and nothing is written. A completed old action must never be resubmitted to answer a new pause.

### Recovery controls

The standalone component above already awaits `agent.ready` and displays hydration and submission errors. To add explicit reconciliation and retry, place these **component-member fragments** inside that class; they reuse its `agent`, `hydrated`, `busy`, and `error` fields and its `computed` import. Configure persistence with an authoritative reconciler first.

```typescript
readonly canRetry = computed(() => this.agent.error()?.recovery === 'retry');

async reconcile(): Promise<void> {
  if (this.busy() || this.agent.status() === 'running') return;
  this.busy.set(true);
  this.error.set('');
  try {
    await this.agent.reconcileInterrupt?.();
    this.hydrated.set(true);
  } catch (error) {
    this.error.set(error instanceof Error ? error.message : 'Recovery failed');
  } finally {
    this.busy.set(false);
  }
}

async retrySaved(): Promise<void> {
  if (this.busy() || !this.canRetry()) return;
  this.busy.set(true);
  this.error.set('');
  try {
    await this.agent.retry?.();
  } catch (error) {
    this.error.set(error instanceof Error ? error.message : 'Retry failed');
  } finally {
    this.busy.set(false);
  }
}
```

Add this **template fragment** to that component's template. Reconciliation adopts what the backend reports and never submits a decision itself: when it reports `pending`, the approval controls render again. The retry button appears only for an answer that provably reached no run.

```html
<button [disabled]="busy() || agent.status() === 'running'"
  (click)="reconcile()">Check backend outcome</button>
@if (canRetry()) {
  <button [disabled]="busy() || agent.status() === 'running'"
    (click)="retrySaved()">Retry saved decision</button>
}
```

`agent.checkStatus()` is the narrower control for an error whose `recovery` is `'check'`. It is present when `persistence.reconcile` is configured, settles only on `completed` or `pending`, and never sends the answer again.

The provider disposes the agent's session with its injector. If you create a session with `createSession()` directly, call `session.dispose()` when finished. Disposal releases listeners and stops local work; it does not delete or cancel backend checkpoints.

### Migration note

Install `@ag-ui/client` at `1.0.1` or later. The 1.0 client translates streams from older servers itself, so the backend does not have to move at the same time.

`interruptTransport` now defaults to `'protocol'`, where it used to default to `'auto'`. A backend that announces a pause only with a `CUSTOM on_interrupt` notice, as the `ag-ui-langgraph` wrapper does, needs `'auto'` or `'legacy-command'`, and Mastra needs `'mastra-command'`. Without one, the notice produces no approval.

The single `interrupt()` signal is gone: read `interrupts()` and take its first entry. `submit({ resume })` is `resume(responses)`, with one response per pending ID and the decision under `value`. The `interruptGeneration` option is `resume(responses, { pause })`, and `interruptSession()` is the `interruptSession(snapshot)` selector. A transport error marked `requestNotDispatched` is no longer read; `retry()` resends an answer only on the proof described above. Persistence records use a new format, and records written by earlier versions are not read.

## Cross-adapter parity

The basic demo card uses the core display and decision contract. Its session factory changes when moving to LangGraph:

```diff
- import { createSession } from '@threadplane/ag-ui';
+ import { createSession } from '@threadplane/langgraph';
```

The `interrupts()` signal and `resume(responses)` are part of the core session contract, and `<chat-approval-card>` is written against it. Configure the matching session and preserve the backend's payload contract. The lifecycle-aware examples on this page additionally use AG-UI's `interruptSession()`, `decisionState()`, the `pause` option, `ready`, and `reconcileInterrupt()`; those are not interchangeable with LangGraph APIs. LangGraph restoration uses server checkpoints rather than an application-owned store. The [LangGraph interrupts guide](/docs/angular/langgraph/guides/interrupts) covers its typed payloads, multi-step approvals, and timeout strategies.
