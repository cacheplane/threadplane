# Testing

Three test doubles cover an AG-UI application, smallest scope first:

- **`mockAgent()`** (from `@threadplane/angular/chat/testing`) — an `Agent` with writable fields and recorded commands, for component and unit tests that need no injector.
- **`provideFakeAgent()`** (from `@threadplane/angular/testing`, re-exported by `@threadplane/angular/chat/testing`) — the real injected `Agent` over an in-memory session that streams canned tokens. No server, no LLM, no AG-UI event.
- **`FakeAgent`** (from `@threadplane/ag-ui`) — an in-process AG-UI source. Hand it to `createSession({ agent })` and the real AG-UI session runs its whole event pipeline over a canned or scripted stream.

See [Choosing an adapter → Testing](/docs/choosing-an-adapter#testing) for when to use each test double.

## Fake backend: `provideFakeAgent()`

`provideFakeAgent({ tokens, reasoningTokens, delayMs })` wires a fake backend into Angular DI in one call. It exercises the **real injected agent** — `injectAgent()`, status transitions, message accumulation, thread switching — over an in-memory session, so there is no server and no LLM. Use it for component-integration tests, in-browser demos, and offline development.

It drops in exactly where `provideAgent()` would go — the call shape is the same whichever backend the application uses:

<Tabs>
<Tab label="app.config.ts">

```typescript
import { ApplicationConfig } from '@angular/core';
import { provideFakeAgent } from '@threadplane/angular/testing';

export const appConfig: ApplicationConfig = {
  providers: [
    provideFakeAgent({ tokens: ['Hello'] }),
  ],
};
```

</Tab>
<Tab label="chat.component.ts">

```typescript
import { ChangeDetectionStrategy, Component } from '@angular/core';
import { ChatComponent } from '@threadplane/angular/chat';
import { injectAgent } from '@threadplane/angular';

@Component({
  selector: 'app-chat',
  imports: [ChatComponent],
  template: `<chat [agent]="agent" />`,
  changeDetection: ChangeDetectionStrategy.OnPush,
})
export class ChatHost {
  protected readonly agent = injectAgent();
}
```

</Tab>
</Tabs>

The component is byte-identical to production — only the provider changes. `provideFakeAgent()` accepts `FakeAgentConfig`:

| Option | Type | Notes |
| --- | --- | --- |
| `tokens` | `string[]` | The assistant reply, streamed one entry at a time. |
| `reasoningTokens` | `string[]` | Reasoning text streamed before the reply, to exercise reasoning UI. |
| `delayMs` | `number` | Delay between entries. `0` streams without timers. |
| `threadId` | `string \| null \| Signal` | The thread to start on. |
| `session` | `FakeAgentSessionInit` | Initial snapshot fields and handlers for every fake session. See [Testing tool calls, state, and custom events](#testing-tool-calls-state-and-custom-events). |

For the `FakeAgent` class and its canned event sequence, see [Fake Agent](/docs/angular/ag-ui/guides/fake-agent).

### A runnable spec

Set `delayMs: 0` to stream without timers, drive `submit()`, then assert the streamed assistant content shows up on `agent.messages()`. Awaiting `submit()` is what guarantees the run finished — it resolves with the run's outcome once the canned stream completes:

```typescript
import { describe, it, expect } from 'vitest';
import { TestBed } from '@angular/core/testing';
import { injectAgent } from '@threadplane/angular';
import { provideFakeAgent } from '@threadplane/angular/testing';

describe('chat via provideFakeAgent', () => {
  it('streams the canned tokens onto the agent', async () => {
    TestBed.configureTestingModule({
      providers: [provideFakeAgent({ tokens: ['Hello'], delayMs: 0 })],
    });

    const agent = TestBed.runInInjectionContext(() => injectAgent());
    await agent.submit({ message: 'hi' });

    const assistant = agent.messages().find((m) => m.role === 'assistant');
    expect(assistant?.content).toBe('Hello');
  });
});
```

`injectAgent()` needs an injection context, so resolve it through `TestBed.runInInjectionContext()`. With `delayMs: 0` the reply is complete by the time the awaited `submit()` resolves, so no fake-timer flushing is required. `injectFakeAgentSession()`, from the same entry, returns a signal of the current fake session's controls (`push`, `stream`, `setError`, `submits` and the rest) for a test to drive.

## Contract mock: `mockAgent()`

For component and unit tests where you do not need a streaming pipeline at all, use `mockAgent(options)` from `@threadplane/angular/chat/testing`. It returns the agent's own shape with every snapshot field **writable** — set state directly and assert your component reacts. It needs no transport and no injection context.

`mockAgent()` covers the core `Agent` surface, including `customEvents`, `subagents` and `interrupts`. A component that reads the fields only an AG-UI session has (`decision`, `run`, `transcript`) needs a scripted `FakeAgent` instead.

```typescript
import { mockAgent } from '@threadplane/angular/chat/testing';

const m = mockAgent({ status: 'running' });
m.messages.set([{ id: '1', role: 'assistant', content: 'Hello!' }]);

expect(m.messages()[0].content).toBe('Hello!');
expect(m.status()).toBe('running');
```

### Captured actions and optional surfaces

The mock records submissions and counts stops so component tests can assert what the UI requested:

```typescript
const agent = mockAgent();
await agent.submit({ message: 'Hello' });
expect(agent.submitCalls[0].input).toEqual({ message: 'Hello' });
await agent.stop();
expect(agent.stopCount).toBe(1);
```

`submit` appends the user message, as a session does. The fake session underneath is reachable as `agent.fake`: `agent.fake.stream()` streams a reply, and `agent.fake.resumes`, `agent.fake.regenerates` and `agent.fake.retryCount` record the other commands. The mock carries `regenerate`, `retry` and `onCustomEvent` by default, and `resume` always; pass `commands` to add `checkStatus`, `runWithoutMessage` or `clientTools`, or to leave some out so a view under test offers no control for them.

The lifecycle marks are writable signals, so drive them directly with `agent.lifecycle.streamStartedAt.set(Date.now())`. Interrupts, child agents and custom events are set the same way as any other field:

```typescript
const agent = mockAgent();

agent.interrupts.set([{ id: 'approval-1', value: { question: 'Continue?' } }]);
agent.subagents.set([]);
agent.emitCustomEvent('analysis_progress', { pct: 100 });
```

These fields do not model AG-UI protocol events or session-specific behavior.

## Testing tool calls, state, and custom events

`provideFakeAgent()` streams text and reasoning only. To exercise what the AG-UI session does with the rest of the protocol — tool-call rendering, shared state, citations, custom events, interrupts — give the real session a `FakeAgent` with a `script` of raw events. `provideAgent()` takes the session factory, so the whole surface stays reachable through DI:

```typescript
import { describe, it, expect } from 'vitest';
import { TestBed } from '@angular/core/testing';
import { EventType, type BaseEvent } from '@ag-ui/client';
import { injectAgent, provideAgent } from '@threadplane/angular';
import { createSession, FakeAgent } from '@threadplane/ag-ui';

describe('scripted FakeAgent', () => {
  it('projects tool calls, state, and custom events', async () => {
    TestBed.configureTestingModule({
      providers: [
        provideAgent({
          createSession: async () =>
            createSession({
              agent: new FakeAgent({
                delayMs: 0,
                script: [
                  {
                    when: 'initial',
                    events: [
                      {
                        type: EventType.TOOL_CALL_START,
                        toolCallId: 'search-1',
                        toolCallName: 'search',
                      } as BaseEvent,
                      {
                        type: EventType.TOOL_CALL_ARGS,
                        toolCallId: 'search-1',
                        delta: '{"q":"Angular"}',
                      } as BaseEvent,
                      { type: EventType.TOOL_CALL_END, toolCallId: 'search-1' } as BaseEvent,
                      {
                        type: EventType.STATE_SNAPSHOT,
                        snapshot: { topic: 'billing' },
                      } as BaseEvent,
                      {
                        type: EventType.CUSTOM,
                        name: 'analysis_progress',
                        value: { pct: 100 },
                      } as BaseEvent,
                    ],
                  },
                ],
              }),
            }),
        }),
      ],
    });

    const agent = TestBed.runInInjectionContext(() => injectAgent());
    await agent.submit({ message: 'find docs' });

    expect(agent.toolCalls()[0]).toMatchObject({ name: 'search', args: { q: 'Angular' } });
    expect(agent.state()).toMatchObject({ topic: 'billing' });
    expect(agent.customEvents()).toContainEqual({ name: 'analysis_progress', data: { pct: 100 } });
  });
});
```

The tool call ends this run without a result, so its status is `pending`. A `CUSTOM` event named `on_interrupt` populates `agent.interrupts()` instead of `customEvents()`, provided the session is created with an `interruptTransport` that answers notices, such as `'auto'`; see the [Interrupts guide](/docs/angular/ag-ui/guides/interrupts). A second branch keyed `{ toolMessageFor: 'search-1' }` plays on the follow-up run that resolving a client tool starts, so an approve-then-continue turn is scriptable end to end.

A host that folds the protocol stream itself can assert against the same script: name the session type with `injectAgent<Session>()`, register `agent.onRawEvent(listener)` before `submit()`, and it receives `RUN_STARTED`, each scripted event, then `RUN_FINISHED`, in order.

When you need control the script does not give you — per-event timing, mid-stream errors, an observable you drive by hand — script your own `AbstractAgent` and pass it to `createSession({ agent })`. The session applies those events the same way.

```typescript
import { describe, it, expect } from 'vitest';
import {
  AbstractAgent,
  EventType,
  type BaseEvent,
  type RunAgentInput,
} from '@ag-ui/client';
import { Observable } from 'rxjs';
import { createSession } from '@threadplane/ag-ui';

/** Emits a scripted tool-call + custom-event sequence, no backend. */
class ScriptedAgent extends AbstractAgent {
  run(input: RunAgentInput): Observable<BaseEvent> {
    const events: BaseEvent[] = [
      { type: EventType.RUN_STARTED, threadId: input.threadId, runId: input.runId } as BaseEvent,
      { type: EventType.TOOL_CALL_START, toolCallId: 'search-1', toolCallName: 'search' } as BaseEvent,
      { type: EventType.TOOL_CALL_ARGS, toolCallId: 'search-1', delta: '{"q":"Angular"}' } as BaseEvent,
      { type: EventType.TOOL_CALL_END, toolCallId: 'search-1' } as BaseEvent,
      { type: EventType.STATE_SNAPSHOT, snapshot: { topic: 'billing' } } as BaseEvent,
      { type: EventType.CUSTOM, name: 'analysis_progress', value: { pct: 100 } } as BaseEvent,
      { type: EventType.RUN_FINISHED, threadId: input.threadId, runId: input.runId } as BaseEvent,
    ];
    return new Observable<BaseEvent>((observer) => {
      for (const event of events) observer.next(event);
      observer.complete();
    });
  }
}

describe('scripted AG-UI events', () => {
  it('projects tool calls, state, and custom events', async () => {
    const session = createSession({ agent: new ScriptedAgent() });
    const custom: { name: string; data: unknown }[] = [];
    session.onCustomEvent?.((event) => custom.push(event));

    await session.submit({ message: 'find docs' });

    const snapshot = session.getSnapshot();
    expect(snapshot.toolCalls[0]).toMatchObject({ name: 'search', args: { q: 'Angular' } });
    expect(snapshot.state).toMatchObject({ topic: 'billing' });
    expect(custom).toContainEqual({ name: 'analysis_progress', data: { pct: 100 } });
    await session.dispose();
  });
});
```

A session is framework-neutral, so this spec needs no `TestBed`. The retained `customEvents()` list is something the injected Angular agent adds; a bare session delivers each event to `onCustomEvent` listeners and keeps none.

## Verify Mastra approval and cancellation with aimock

The Mastra browser suite checks each decision at three points: the outgoing command contains the decision and observed correlation IDs, the backend tool result matches that decision, and the visible assistant reply agrees with the tool result. A disappearing approval card alone is insufficient evidence of completion.

Run the six scenarios from the repository root with deterministic aimock replay:

```sh
npx nx e2e cockpit-runtimes-mastra-angular
```

The application creates its session with `createSession({ url, interruptTransport: 'mastra-command' })`, and both buttons answer with `agent.resume(responses)`. Approval sends `command.resume: { approved: true }`; cancellation sends `{ approved: false }`. Both carry `command.interruptEvent: { toolCallId, runId }` under `forwardedProps`, using the suspended run's observed identifiers.

Keep these continuation entries separate inside an aimock fixture's `fixtures` array:

```json
[
  {
    "match": {
      "userMessage": "reserve",
      "hasToolResult": true,
      "toolResultContains": "Reserved North Pines"
    },
    "response": { "content": "North Pines is reserved for 2 nights — confirmation TP-0288." }
  },
  {
    "match": {
      "userMessage": "reserve",
      "hasToolResult": true,
      "toolResultContains": "Nothing was booked."
    },
    "response": { "content": "The reservation for the North Pines campsite was not booked." }
  }
]
```

The initial tool-call fixture must set `hasToolResult: false`. Matching a continuation only by the user prompt and presence of a tool result can replay an approval after cancellation. Match the backend outcome with `toolResultContains` so the two decisions cannot share a reply.

For live-model verification, configure `OPENAI_API_KEY` in the environment and run each decision in a fresh process with a fresh capture directory:

```sh
# Use new directories for every verification session.
AIMOCK_MODE=record AIMOCK_RECORD_DIR=/tmp/public-docs-approve-recordings \
  npx nx e2e cockpit-runtimes-mastra-angular --grep='Approve sends'
AIMOCK_MODE=record AIMOCK_RECORD_DIR=/tmp/public-docs-cancel-recordings \
  npx nx e2e cockpit-runtimes-mastra-angular --grep='Cancel sends'
```

Aimock can reuse newly recorded matches within a process, and generated matchers do not distinguish the two tool-result payloads. Separate processes and unused capture directories prevent the second decision from reusing the first decision's response. Each test run also uses a fresh local database. Confirm new upstream captures for each decision before treating a passing run as live-model evidence; replay alone demonstrates deterministic integration behavior.

The verified scenario is North Pines for two nights, totaling $90. The local tool returns a synthetic confirmation on approval or `Nothing was booked.` on cancellation; it never contacts an external reservation service. Check both the backend result and the visible reply. Live provider wording varies, while replay wording is deterministic. The cancellation continuation was captured from `gpt-4o-mini` through aimock record mode on 2026-09-09.
