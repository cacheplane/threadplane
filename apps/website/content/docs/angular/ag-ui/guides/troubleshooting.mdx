# Troubleshooting

Most AG-UI integration issues are event-shape problems. Start by checking what your backend actually emits against the [Event Mapping](/docs/angular/ag-ui/reference/event-mapping).

## Nothing renders

Check the provider first.

```ts
import { provideAgent } from '@threadplane/angular';
import { createSession } from '@threadplane/ag-ui';

providers: [
  provideAgent({
    createSession: async (context) =>
      createSession({ ...context, url: '/api/agent' }),
  }),
]
```

Then make sure the component uses the provided agent:

```ts
import { Component } from '@angular/core';
import { ChatComponent } from '@threadplane/angular/chat';
import { injectAgent } from '@threadplane/angular';

@Component({
  standalone: true,
  imports: [ChatComponent],
  template: `<chat [agent]="agent" />`,
})
export class ChatPage {
  protected readonly agent = injectAgent();
}
```

If you call `injectAgent()`, the agent must have been provided via `provideAgent()` from `@threadplane/angular` in the same Angular injector tree. `@threadplane/ag-ui` no longer exports a provider of its own.

## User messages appear, but no assistant response

`submit()` publishes the user message with the new run before the request is sent. If the user message appears and the assistant does not, the UI path is working. The next place to inspect is the AG-UI event stream.

The backend must emit at least:

```ts
{ type: 'RUN_STARTED', threadId, runId }
{ type: 'TEXT_MESSAGE_START', messageId: 'm1', role: 'assistant' }
{ type: 'TEXT_MESSAGE_CONTENT', messageId: 'm1', delta: 'Hello' }
{ type: 'TEXT_MESSAGE_END', messageId: 'm1' }
{ type: 'RUN_FINISHED', threadId, runId }
```

`RUN_STARTED` and `RUN_FINISHED` must carry the `threadId` and `runId` of the request; a mismatch fails the run. If `TEXT_MESSAGE_CONTENT` uses a different `messageId` than `TEXT_MESSAGE_START`, the AG-UI client's verification rejects the sequence and the run fails. `agent.errorDiagnostic()` then names the event that was rejected.

## Loading never stops

There is no separate loading flag: a run is going while `agent.status()` is `'running'`. The session sets it when a command is admitted.

`status()` leaves `'running'` on:

- `RUN_FINISHED`, including one carrying `outcome: { type: 'interrupt' }`, which pauses the run
- `RUN_ERROR`
- a transport failure, or a stream that closes without a terminal event
- `stop()`, which aborts the active run

If loading never stops, the response is still open and your backend has not emitted a terminal event. For a custom `AbstractAgent`, check that the Observable its `run()` returns completes or errors.

## Errors are not visible

Protocol errors should come through `RUN_ERROR`.

```ts
{ type: 'RUN_ERROR', message: 'Model quota exceeded' }
```

Transport or runtime failures are not protocol events. The session classifies them into `agent.error()`, keeps a description of what was thrown in `agent.errorDiagnostic()`, and sets `status` to `error`.

Your UI still needs to render error state. The base chat composition handles common error display, but custom layouts should read:

```ts
agent.status();
agent.error();
```

## Tool call args are empty

`TOOL_CALL_ARGS` appends each event `delta` to the tool call's accumulated argument text. A call enters `agent.toolCalls()` once its arguments are final.

This can arrive as one complete payload:

```ts
{ type: 'TOOL_CALL_ARGS', toolCallId: 't1', delta: '{"query":"Angular"}' }
```

Or as fragments:

```ts
{ type: 'TOOL_CALL_ARGS', toolCallId: 't1', delta: '{"query":' }
{ type: 'TOOL_CALL_ARGS', toolCallId: 't1', delta: '"Angular"}' }
```

While the text is still arriving, the call is listed in `agent.streamingToolCalls()` instead, with the text so far in `argsText` and a best-effort `args`. If the final text is not JSON, the call becomes an `error`. Empty argument text is a call without input: `args` is undefined.

## Citations do not show up

Check three things:

1. Citations must live under `state.citations`.
2. The citation key must match the assistant message id.
3. A `STATE_SNAPSHOT` or `STATE_DELTA` must carry the citation data.

Example:

```ts
{
  type: 'STATE_SNAPSHOT',
  snapshot: {
    citations: {
      m1: [{ title: 'Policy', url: 'https://example.com/policy' }],
    },
  },
}
```

The order does not matter: citations that arrive before their message exists appear once the message does. A backend that renames a message in its closing `MESSAGES_SNAPSHOT` must key the citations by the saved id. See [Citations](/docs/angular/ag-ui/guides/citations).

## Stop does not cancel the run

`agent.stop()` ends the run locally. A session created with `url` aborts its HTTP request. A session created with `agent` unsubscribes from the stream and calls the agent's `abortRun()`.

Cancellation beyond that depends on the AG-UI source implementation. A custom `AbstractAgent` subclass needs to implement cancellation itself.

## Regenerate throws

`regenerate(messageId)` rejects when:

- Another run is already going.
- A decision is waiting.
- The target id is not an assistant message.
- There is no previous user message to rerun from.

Pass the `id` of the assistant message you want to replace, not the user message, and not its index.

## Retry does nothing

`retry()` sends the last submission again after its run failed with a backend `RUN_ERROR`. It resolves `'aborted'` without sending in three cases: a run is already going, nothing failed, or the last run was not a failed submission. None of them throws and none sets `error`, so a retry button that appears to do nothing usually means one of the three. It rejects, also without sending, when the failure leaves the backend outcome open. Show the button only while `agent.error()?.retryable` is true.

## No Retry button after a dropped stream

This is deliberate. A stream that closed without terminal evidence settles as an `interrupted` error, and the session does not offer Retry for it: the server may have processed the original request before its response was lost. No observed event is not proof of no dispatch or no backend effect. Retry is offered when the backend reported its own `RUN_ERROR`, which settles that the run failed.

Read `error()?.recovery`: `retry` permits sending the request again, `check` means a read-only status check of a sent answer is available through `checkStatus()`, and `none` means the outcome cannot be verified. In the last case, show `error()?.detail`. Partial content and approval state are preserved.

## History or time-travel does not work

Checkpoint browsing and time-travel are not implemented by the AG-UI session today. Restoring a saved conversation is supported through `replay` and `persistence`; see [Restoring a thread from the server](/docs/angular/ag-ui/guides/deployment#restoring-a-thread-from-the-server).

Current scope is messages, status/loading/error, tool calls, state/custom events, reasoning messages, message snapshots, interrupts from `CUSTOM` `on_interrupt` events and from `RUN_FINISHED` interrupt outcomes, subagent progress from `SUBAGENT_*` and `ACTIVITY_*` events, and citations from state.

Use `@threadplane/langgraph` if you need LangGraph Platform thread history APIs, or write a session of your own against the `AgentSession` contract from `@threadplane/core` if you need AG-UI plus product-specific behavior.

## Isolate with FakeAgent

When you are unsure whether the issue is UI wiring or backend events, swap in the fake provider:

```ts
import { provideFakeAgent } from '@threadplane/angular/testing';

providers: [
  provideFakeAgent({
    tokens: ['Fake', ' response.'],
    delayMs: 20,
  }),
]
```

If the UI works with the fake provider, the Angular wiring is fine. To check the AG-UI session as well, hand it the `FakeAgent` class with `createSession({ agent: new FakeAgent() })`; see [Fake Agent](/docs/angular/ag-ui/guides/fake-agent). If both work, focus on the backend event stream.
