# Architecture

`@threadplane/ag-ui` is a backend package. It does not replace `@threadplane/angular/chat`, and it contains no UI framework code.

The package posts each run to an AG-UI endpoint (or calls an AG-UI `AbstractAgent` you built), reads the protocol events, and publishes them as a framework-neutral session. `@threadplane/angular` puts that session behind the injected `Agent` that the chat components already understand.

## The boundary

The important boundary is the injected `Agent` from `@threadplane/angular`.

Your components should depend on `Agent`, not on AG-UI transport details. That keeps the UI portable across AG-UI, LangGraph, and sessions of your own.

`createSession(options)` is the low-level boundary. It takes an AG-UI HTTP endpoint, or any AG-UI `AbstractAgent` implementation:

```ts
import { createSession } from '@threadplane/ag-ui';
import { HttpAgent } from '@ag-ui/client';

const overHttp = createSession({ url: '/api/agent' });
const overAgent = createSession({ agent: new HttpAgent({ url: '/api/agent' }) });
```

A session is a plain object with `getSnapshot()`, `subscribe()` and commands. It starts no run until a command is called.

Angular apps hand that factory to DI:

```ts
import { ApplicationConfig } from '@angular/core';
import { provideAgent } from '@threadplane/angular';
import { createSession } from '@threadplane/ag-ui';

export const appConfig: ApplicationConfig = {
  providers: [
    provideAgent({
      createSession: (context) =>
        createSession({
          ...context,
          url: '/api/agent',
        }),
    }),
  ],
};
```

`provideAgent()` builds one `Agent` from the sessions the factory creates and registers it under an internal DI token. Retrieve it with `injectAgent()`.

```ts
import { Component } from '@angular/core';
import { ChatComponent } from '@threadplane/angular/chat';
import { injectAgent } from '@threadplane/angular';

@Component({
  standalone: true,
  imports: [ChatComponent],
  template: `<chat [agent]="agent" />`,
})
export class ChatPage {
  protected readonly agent = injectAgent();
}
```

Without a type argument the agent is typed by the core contract. Name the AG-UI session type to reach the fields and commands only this backend has, such as `decision()`, `run()`, `onRawEvent` and `ready`:

```ts
import { injectAgent } from '@threadplane/angular';
import type { Session } from '@threadplane/ag-ui';

const agent = injectAgent<Session>();
```

## Runtime data flow

Each request goes through the same stages the AG-UI client's own `runAgent` applies: retired event shapes are translated, unknown events are dropped, chunk events are expanded, and the sequence is verified. The session then applies each event to its snapshot.

Every snapshot field is a read-only signal on the injected agent:

- `messages` for user, assistant, tool and system messages, with reasoning attached to the assistant message it precedes.
- `status` and `error` for run lifecycle. `status()` is `'idle'`, `'running'` or `'error'`.
- `toolCalls` for tool calls whose arguments are final, and `streamingToolCalls` for calls whose arguments are still arriving.
- `state` for AG-UI state snapshots and JSON Patch deltas, and `plan` for a `todos` list in that state.
- `interrupts` for what a paused run waits on: a `RUN_FINISHED` carrying `outcome: { type: 'interrupt' }`, or a `CUSTOM` `on_interrupt` notice when `interruptTransport` selects a profile that answers notices.
- `inputBlocked` for why an ordinary submission is refused right now.
- `subagents` for `SUBAGENT_*` events and for `ACTIVITY_*` records with `activityType: 'subagent'`.

Custom events are not state. `agent.onCustomEvent(listener)` delivers each non-`on_interrupt` `CUSTOM` event as it arrives, and `agent.customEvents()` retains the current run's events for live a2ui and app-specific reactive UI.

When the user submits input, the session builds a user message, merges any state patch, and publishes the message, the state and the new run together before it sends the request. The request carries the complete history and state.

The user message therefore appears immediately while the backend starts the run.

## Live a2ui streaming via `customEvents`

The injected agent exposes a `customEvents` signal, accumulating every
non-`on_interrupt` `CUSTOM` AG-UI event for the current run (empty again when
the next run starts and when the agent switches threads). The chat
composition does not read this signal for A2UI: it renders a2ui surfaces from
the assistant message content, through the renderer bound to `<chat [a2ui]>`.
An application that wants progressive rendering from `a2ui-partial` events
reads `customEvents` itself.

How the chat composition renders A2UI content lives in chat's [A2UI overview](/docs/angular/chat/a2ui/overview).

## Browser client tools

`agent.clientTools` is the core client-tool capability consumed by `<chat [clientTools]>`. The chat composition declares the browser catalog with `setCatalog()`; the session sends that catalog as the `tools` of every later request, lists unresolved browser-owned tool calls in `agent.pendingClientTools()` once the run has ended, and sends the browser result back as a tool message before continuing the run.

See chat's [Client Tools guide](/docs/angular/chat/guides/client-tools) for declaring `action()`, `view()`, and `ask()` tools. With AG-UI, the backend must bind the supplied AG-UI tool specs and finish the turn without emitting `TOOL_CALL_RESULT` for browser-owned tools so the client can resolve them.

## Provider choices

Use `provideAgent()` with `createSession({ url })` when you have a real AG-UI HTTP endpoint.

```ts
provideAgent({
  createSession: (context) =>
    createSession({
      ...context,
      url: '/api/agent',
      agentId: 'support-agent',
      headers: { Authorization: `Bearer ${token}` },
    }),
});
```

`url`, `headers` and `fetch` are the AG-UI `HttpAgent` options the session sends with. The rest belong to the session:

| Option | Type | Description |
|---|---|---|
| `url` | `string` | AG-UI backend HTTP/SSE endpoint. Required unless `agent` is given. |
| `agent` | `AbstractAgent` | An AG-UI client agent you built, in place of `url`. Passing both throws. |
| `agentId` | `string` | Optional. Names the agent when an endpoint serves more than one. The protocol does not put it on the wire. |
| `threadId` | `string` | Optional. The thread this session owns. Absent, the session uses the handed agent's own `threadId`, or else generates one. |
| `headers` | `Record<string, string>` | Optional. Custom request headers (auth, tracing). |
| `interruptTransport` | `'protocol' \| 'auto' \| 'legacy-command' \| 'mastra-command'` | Optional. How a pause is answered. Defaults to `'protocol'`. |
| `replay` | `ReplaySource` | Optional. Loads the thread's events from your server when the session is created. |
| `persistence` | `SessionPersistence` | Optional. Application-owned storage for the thread. Needs a `threadId` the application chose. |
| `a2uiClientCapabilities` | `{ supportedCatalogIds, inlineCatalogs? }` | Optional. Advertises A2UI catalog support to the agent in every request's state. |
| `telemetry` | `SessionTelemetrySink \| false` | Optional. App-owned sink for session lifecycle events. |

### Factory config for route params and DI

`provideAgent()` also accepts a `() => AgentConfig` factory. The factory runs once inside an Angular injection context, so it can call `inject()` to read services when it builds the config:

```ts
import { inject } from '@angular/core';
import { provideAgent } from '@threadplane/angular';
import { createSession } from '@threadplane/ag-ui';
import { SessionService } from './session.service';

providers: [
  provideAgent(() => {
    const session = inject(SessionService);
    return {
      createSession: (context) =>
        createSession({
          ...context,
          url: '/api/agent',
          headers: { Authorization: `Bearer ${session.accessToken()}` },
        }),
    };
  }),
];
```

`createSession` itself also runs in the agent's injection context, each time the agent needs a session.

A session belongs to one thread. The `threadId` in the provider config is where the agent starts: a string, `null`, or a signal the agent follows. `agent.switchThread(id)`, or a change of that signal to a different id, asks the factory for a new session with `context.threadId` set, stops and disposes the old one, and keeps every signal and command on the agent the same reference. `agent.threadId()` is the thread the agent is on, and `agent.isThreadLoading()` is true while the selected thread's history is read.

A session that is given no `threadId` names the new conversation's thread itself, publishes it as `session.threadId`, and reports it through `context.onThreadId`, so `agent.threadId()` is set from the first run. A factory that spreads the context passes that callback on; one that names fields must pass `onThreadId` itself.

The AG-UI protocol carries events, not snapshots, and defines no server-side endpoint for "fetch the messages of thread X". A new session for an existing thread therefore starts empty unless you give it a source to restore from:

- **Configure `replay`.** When your server can return a thread's recorded events, pass `replay` (for example `httpReplay({ url })`) and each new session rebuilds the thread from them, as the live view showed it; disposing a session aborts its replay. Otherwise prior history comes from your application-owned `persistence` store, which restores the transcript, state, ended child agents and a pending pause, or from your own host service. See [Restoring a thread from the server](/docs/angular/ag-ui/guides/deployment#restoring-a-thread-from-the-server).
- **Use the LangGraph backend instead.** A `@threadplane/langgraph` session reads a thread's saved history from the server that owns it. See its [Persistence guide](/docs/angular/langgraph/guides/persistence). Use AG-UI when your runtime publishes events without checkpoint storage; use LangGraph when the server owns durable thread state.

### Typed state and several agents at one level

`provideAgent()` has a second overload that takes an `AgentRef` first. The ref carries the session type, and with it the state shape, from the provider to `injectAgent(ref)`, and it registers the agent under the ref's own token, so more than one agent can be provided at a single injector level:

```ts
import { createAgentRef, injectAgent, provideAgent } from '@threadplane/angular';
import { createSession, type Session } from '@threadplane/ag-ui';
import { type } from '@threadplane/core';

export const TRIP = createAgentRef<Session<TripState>>('trip');
export const SUPPORT = createAgentRef<Session<SupportState>>('support');

providers: [
  provideAgent(TRIP, {
    createSession: (context) =>
      createSession({
        ...context,
        url: '/api/trip',
        stateType: type<TripState>(),
      }),
  }),
  provideAgent(SUPPORT, {
    createSession: (context) =>
      createSession({
        ...context,
        url: '/api/support',
        stateType: type<SupportState>(),
      }),
  }),
];

// component
const trip = injectAgent(TRIP);       // Agent<Session<TripState>>
const support = injectAgent(SUPPORT); // Agent<Session<SupportState>>
```

`type<T>()` declares the state type and checks nothing. Pass a Standard Schema, such as a Zod object, as `stateType` to check each state document as well.

The ref form also aliases the shared token that the no-argument `injectAgent()` reads. That token can only point at one agent, so when several refs are provided at the same level the **last** `provideAgent(ref, …)` call wins — inject by ref whenever an injector provides more than one agent. In development mode, resolving the ref-less `injectAgent()` logs a `console.warn` naming the refs involved, so the aliasing is visible while you build.

Use `provideFakeAgent()` when you need the UI to run without a backend:

```ts
import { provideFakeAgent } from '@threadplane/angular/testing';

providers: [
  provideFakeAgent({
    tokens: ['Offline', ' demo', ' response.'],
    delayMs: 40,
  }),
];
```

Use `createSession({ agent })` when you own a custom `AbstractAgent` subclass or need to test a specific event stream.

## Lifecycle gotchas

The injected `Agent` owns its sessions. It disposes the old session on a thread switch and the last one with its injector, so `getSnapshot`, `subscribe` and `dispose` are not exposed on it.

In Angular apps, prefer the provider API so the agent instance is scoped by DI. If you create a session yourself, call `session.dispose()` when you are finished with it.

A session does not take over an `AbstractAgent` it is handed. It calls the agent's `run(input)` with each request's full input, and neither reads nor changes the agent's own `messages` and `state`.

`stop()` ends the current run locally. For the `url` form it aborts the request. For a handed agent it unsubscribes from the stream and calls the agent's `abortRun()`; the actual cancellation behavior then depends on that agent.

`retry()` sends the last submission again after its run failed with a backend `RUN_ERROR`, without adding a second user message. It resolves `'aborted'` without sending while a run is active, when nothing failed, or when the last run was not a failed submission, and it rejects when the failure leaves open whether the backend did the work.

`regenerate(messageId)` takes the `id` of an assistant message. It keeps the history up to and including the user message before that message, drops everything after it, and runs again with the current state. It rejects while a run is active, while a decision is waiting, for an id that is not an assistant message, and when no user message precedes it.

## Current scope

The AG-UI session currently covers:

- Streaming assistant messages from `TEXT_MESSAGE_*`.
- Reasoning messages from `REASONING_MESSAGE_*`.
- Run status and errors from `RUN_*`.
- Tool calls from `TOOL_CALL_*`.
- Shared state from `STATE_SNAPSHOT` and `STATE_DELTA`.
- Message replacement from `MESSAGES_SNAPSHOT`.
- Custom events from non-`on_interrupt` `CUSTOM` events, surfaced through both `onCustomEvent` and `customEvents`.
- Interrupts from a `RUN_FINISHED` carrying `outcome: { type: 'interrupt' }`, and from `CUSTOM` events named `on_interrupt` under an `interruptTransport` that answers them.
- Browser client tools via `agent.clientTools`.
- Child agents from `SUBAGENT_STARTED`/`SUBAGENT_FINISHED`/`SUBAGENT_ERROR` events with `subagentRunId`-attributed content, and from `ACTIVITY_SNAPSHOT`/`ACTIVITY_DELTA` records whose `activityType` is `subagent`.
- Citations stored under `state.citations`.

These features are intentionally out of scope for the AG-UI session today:

- **Checkpoints and time-travel.** AG-UI names runs and threads, and nothing in it lists saved points of a thread with the state at each, so the session publishes no `checkpoints`. It also defines no server-side "fetch state of thread X" endpoint, so a session cannot read prior messages for a `threadId` the way a checkpoint-aware runtime can. The [Provider choices](#provider-choices) section above describes the two patterns AG-UI consumers use to work around this.

If server-side history or time-travel is central to your product, use the LangGraph backend for that surface or write a session of your own against the `AgentSession` contract. The [Writing an Adapter guide](/docs/angular/chat/guides/writing-an-adapter) walks through that design choice in detail.
